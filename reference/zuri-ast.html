The Zuri Standard Library

zuri.ast

import zuri

Everything here is re-exported by zuri, so import zuri is enough and the names are called as zuri.*. Importing zuri.ast on its own works too and reaches the same definitions.

The Node type zuri.parse() returns: a generic representation of one AST node, tagged by kind ('Binary', 'If', 'Function', …) with a fields dict holding whatever that kind carries. There is one Node class rather than one class per grammar rule, since the grammar has roughly fifty expression/statement/declaration shapes, and a dedicated class per shape would mean fifty near- identical classes to maintain in lockstep with the parser forever after. A fields entry that’s itself node-shaped (or a list of node-shaped entries) is already wrapped into a Node recursively, so you never need to call Node.from_dict() yourself.

import zuri

for node in zuri.parse('def add(a, b) { return a + b }') {
  echo node.kind
}
# Function

Comments and doc blocks

parse()’s whole point, beyond exposing the grammar itself, is that its result is complete enough to rebuild the source file from. Every #-comment and doc block comment in the file comes back as its own 'Comment'/'DocBlock'-kind node, sitting exactly where it appeared: as a sibling in the surrounding statement/declaration list, at the top level, inside a { } block, or between two class members.

A comment written inside an expression is NOT lost, but it isn’t attached inside that expression’s own node either. There’s no Node kind for “a comment sitting between two call arguments”, and there never will be, since CLAUDE.md’s own Zuri style guide never places a comment there in the first place (a comment is always its own whole line, between statements/declarations/class members, not mid-expression). What actually happens: the comment is captured as a standalone 'Comment'/'DocBlock' node and placed as a sibling of the SMALLEST enclosing statement/declaration/class-member, in that same surrounding list, immediately after it (before whatever real node follows in that list, or at the list’s own end if nothing does). It stays exactly as deeply nested as the statement that contained it; a comment inside an if body three blocks deep comes back three blocks deep too, never hoisted to the top.

import zuri

var source = "def foo() {\n  echo bar(a, # x\n  b)\n  echo 2\n}\n"
var body = zuri.parse(source)[0].fields.body.fields.statements
echo body[0].kind        # Echo, the statement the comment sat inside
echo body[1].kind        # Comment, landed right after it, not inside it
echo body[1].fields.text # ' x'
echo body[2].kind        # Echo, the "echo 2" line, unaffected

Source written against CLAUDE.md’s own comment-placement convention is completely unaffected by this: every comment in real, style-conformant Zuri source is already its own whole line between statements, which is exactly the case parse() places correctly, in its original position. This only matters for source that breaks that convention, and even then, nothing is thrown away; the comment’s line/col still point at where it actually appeared, it’s just not a descendant of the expression node it visually sat inside.

import zuri

var source = "# a helper function\ndef add(a, b) {\n  return a + b\n}\n"
var nodes = zuri.parse(source)
echo nodes[0].kind        # Comment
echo nodes[0].fields.text # " a helper function"
echo nodes[1].kind        # Function

A class body’s fields and methods are two separate lists (Decl::Class’s own shape, mirrored here as a Class node’s properties/methods fields), so a comment between a field and a method lands in methods, whichever list the member right after it belongs to, and a comment between two fields lands in properties. See Node’s own field-by-field notes below. Code that wants the true interleaved order across both lists, to rebuild a class body exactly as written, should merge properties ++ methods and sort by (line, col).

Functions

parse()

zuri.parse(source) -> list[Node]

Parses source in full and returns its top-level declarations as a list of Node. See this module’s own doc comment for the exact shape, and in particular for what is and isn’t preserved around comments.

Raises (rather than returning a partial result) on a syntax error, since there is no meaningful AST to hand back for source the parser itself couldn’t make sense of.

Parameters

  • source (string) — The Zuri source to parse

Returns list[Node]

Raises Error if source has a syntax error

parse_file()

zuri.parse_file(path) -> list[Node]

Reads the file at path and parses its contents; exactly parse(file(path).read()), for the common case of parsing a real file rather than a source string you’ve already got in hand.

Parameters

  • path (string) — Path to the Zuri source file to parse

Returns list[Node]

Raises Error if path can’t be opened or read, or has a syntax error

dump_file()

zuri.dump_file(path) -> string

Reads, parses, and dumps the file at path in one call: the fastest way to answer “what does this file’s AST actually look like”. Equivalent to parsing path and joining every resulting top-level node’s own dump() with a blank line between them.

import zuri
echo zuri.dump_file('main.zu')

Parameters

  • path (string) — Path to the Zuri source file to parse and dump

Returns string

Raises Error if path can’t be opened or read, or has a syntax error

walk_nodes()

zuri.walk_nodes(nodes, visitor)

Recursively visits every node reachable from nodes (typically zuri.parse()’s own result, or any single Node plucked out of it), in the order they appear, calling visitor for each one. This is the tool for “do something with every X”: most real uses of an AST are a walk, not manual field-by-field navigation.

visitor is either a plain function, called with every node (visitor(node)), or a dict from kind name to function, where only a node of that kind gets called (visitor[node.kind](node)). Reach for the dict form when you only care about one or two kinds; it reads as a small dispatch table instead of a chain of if node.kind == ... checks inside a single function.

Always visits the whole tree; there’s no way for visitor to skip descending into a particular node’s children.

import zuri

var nodes = zuri.parse(source)

# every function name declared anywhere in the file, including
# nested/inner functions
var names = []
zuri.walk_nodes(nodes, {
  Function: @(node) { names.append(node.fields.name) },
})

Parameters

  • Node|list[Node] — nodes
  • visitor (function|dict)

find_nodes()

zuri.find_nodes(nodes, kind) -> list[Node]

Every node reachable from nodes whose kind is kind, in the order they appear. Shorthand for the common “just give me a flat list of these” case walk_nodes() itself is built on.

import zuri

var nodes = zuri.parse(source)
for comment in zuri.find_nodes(nodes, 'Comment') {
  echo comment.fields.text
}

Parameters

  • Node|list[Node] — nodes
  • kind (string)

Returns list[Node]

Classes

Node

class zuri.Node

One AST node: an expression, statement, declaration, type hint, or a standalone comment/doc block sitting between two of those.

  • printable — has a to_string(), so echo and interpolation show something useful

Constructor

zuri.Node(kind, line, col, fields)

Returns a new instance of a Node directly, from already-wrapped field values. Ordinary Zuri code should use Node.from_dict() or zuri.parse() instead, since this constructor does no wrapping of its own.

Parameters

  • kind (string) — The node’s kind, e.g. 'Binary', 'If'
  • line (?number) — The node’s source line, or nil if this kind of node carries no position (see from_dict’s own docs)
  • col (?number) — The node’s source column, or nil
  • fields (dict) — This kind’s own fields, already wrapped

Node.from_dict()

zuri.Node.from_dict(data)

Builds a Node from the raw dict zuri.parse()’s native backing produces ({ kind, line, col, fields }), recursively wrapping any node-shaped entry inside fields, a single nested node or a list of them, into its own Node. A fields entry that isn’t node-shaped (a string, a number, a bool, nil, or a plain dict like a Var node’s type_hint when there isn’t one) passes through unchanged.

line/col are best-effort, not guaranteed on every node. Most AST shapes carry a full position (an identifier, an operator, a declaration’s own name); a few (Binary, Call, Index, and other operator/delimiter-driven expressions) only ever carry a bare source line, with col always nil; and a handful of purely structural nodes (an empty Block, None) carry neither, coming back with line/col both nil. None of this affects what fields contains, since position is a convenience for pointing at where something is, not part of the information rebuilding source needs.

Parameters

  • data (dict) — { kind, line, col, fields }

Returns — Node

Node.is_trivia()

zuri.Node.is_trivia() -> bool

Is this node a standalone comment or doc block (as opposed to a real expression/statement/declaration)? See this module’s own doc comment for exactly where these can and can’t appear.

Returns bool

Node.to_string()

zuri.Node.to_string() -> string

This node as kind@line:col, e.g. 'Binary@3:5'; kind@line when a position exists but has no column (some AST shapes only ever carry a bare source line, never a column: see from_dict’s own docs); or just kind when it carries no position at all. A one-line summary; use dump() to actually see what’s inside a node.

Returns string

Node.dump()

zuri.Node.dump() -> string

A readable, indented, multi-line dump of this node and everything inside it, recursively. This is the actual way to find out what a fields entry is called for a kind you haven’t looked up yet: echo node.dump() and read it, rather than guessing a key name and checking whether it happens to exist.

import zuri

var nodes = zuri.parse('def add(a, b) { return a + b }')
echo nodes[0].dump()
