Concurrency

isolate

Runs code in parallel on a pool of operating system threads.

How isolates work

Each isolate runs in a virtual machine of its own, with its own garbage-collected heap, call stack and copy of every module it imports. Isolates run at the same time on different CPU cores, but they never share heap objects with each other or with the main thread. The design is closer to Erlang processes and Dart isolates than to threads that share memory.

Values move between isolates by being copied. When you pass a value to spawn(), return one from an isolate's function or send one through a Channel, Zuri copies the whole object graph into the receiving isolate's heap. The copy keeps cycles, objects that appear more than once in the value, and the classes of instances.

Tasks and the thread pool

isolate.spawn() doesn't start a thread. It packages the function and its arguments into a task, which is a copy that doesn't depend on the caller's heap, and adds the task to a shared queue. The threads in the pool take tasks from the queue and run them one after another, each in a virtual machine that the thread keeps from one task to the next.

The pool has at most one thread for each CPU core, unless you set a different limit with configure(). A thread is only started when a task is waiting and every existing thread is busy, so the pool never runs more threads than the work needs.

Because a queued task is a copy of some values, not a suspended thread, you can queue a large number of tasks at once, 100,000 or more, without paying for a stack or a heap for each one. Each task takes a few hundred bytes for its place in the queue and its handle, plus whatever its arguments take up.

Garbage collection

Each isolate collects its own garbage, in its own nursery and old generation, on its own thread. A collection in one isolate never pauses another isolate or the main thread. That's why allocation-heavy work, such as building trees, multiplying matrices or rendering images in parallel, speeds up almost in proportion to the number of cores.

Data races

Two isolates can never modify the same object, because no object is ever in two heaps. Data races on Zuri values can't happen, and you don't need locks around your own data structures.

When you pass a closure to an isolate, the variables it captures and the globals it refers to are copied when it's spawned. The isolate works on its own copy, so later changes made by the caller don't affect the isolate, and changes the isolate makes never reach the caller.

Compared with Go

Go runs goroutines on a small number of OS threads, and they all share one heap. Zuri runs isolates on a pool of OS threads, gives each one a heap of its own, and copies values between them.

Go goroutines Zuri isolates
Model Green threads multiplexed onto OS threads, sharing one heap A pool of OS threads, with a separate heap for each isolate
Memory safety Memory is shared, so data races are possible without locks Heaps are separate, so data races can't happen
Garbage collection One collector for the whole program A separate collector for each isolate, with no pauses across threads
Cost per task About 2 KB of stack per goroutine A few hundred bytes for the queue entry and handle, with threads reused
Communication Channels that pass pointers, or locks Copied values, or native resources that are moved
Best at Very large numbers of concurrent network connections Parallel computation and task pipelines

Values that can be passed between isolates

Almost every kind of value can be passed to another isolate:

  • Primitives: nil, bool, number, bigint, string, bytes and range.
  • Lists and dictionaries, including nested and cyclic ones.
  • Class instances, classes, with their static fields, superclasses and methods, and bound methods.
  • Functions, closures with their captured variables, anonymous functions and top-level scripts.
  • Modules, including a module that a closure captured.
  • Native handles: Ptr handles, which are moved, and Channel and Isolate handles.

A module isn't copied. It's loaded again in the receiving isolate, so the receiver gets its own instance of the module, with its own top-level state.

An open file handle, from file(...), can't be passed to another isolate. Trying to do so raises an IsolateError.

Native resources

A Ptr wraps a native resource such as a database connection, a socket or a compression stream, and those can't safely be duplicated across threads. A Ptr is therefore moved instead of copied:

  • When a Ptr is passed to spawn(), returned to join() or sent through a Channel, the receiver becomes its owner, and the sender's handle stops working.
  • Using a handle that has stopped working raises an error.
  • Channel and Isolate handles are different. They're safe to use from several threads, and any number of isolates can share them.

Failures

An error in one isolate stays in that isolate. It never stops other isolates, damages the pool or crashes the process.

  • An error that an isolate's function doesn't catch is raised again as an IsolateError, with the original file, line and stack trace, when you call join() or try_join().
  • If the runtime itself fails inside an isolate, that isolate's virtual machine is discarded and replaced with a new one, so the pool keeps its full size.
  • If an isolate fails and its handle is dropped without ever being joined, a warning is printed, so that the error isn't lost.

Cancellation

Call Isolate.cancel() to cancel an isolate that's running or still queued.

  • If the isolate is waiting in Channel.send(), Channel.recv(), Isolate.join(), select(), wait_any() or wait_all(), the call is interrupted and raises an IsolateCancelledError.
  • Code that's busy computing isn't interrupted. It should check isolate.is_cancelled() from time to time and return when it's set.

Structured concurrency

Isolates that outlive the code that started them can leave tasks running, resources open and errors unnoticed. isolate.scope(body) and its Scope handle prevent that:

  • Every isolate started with s.spawn() inside a scope() call finishes before scope() returns.
  • If body raises an error, or any of the isolates fails, all the other isolates in the scope are cancelled, so that they don't keep working for nothing.
  • scope() waits for the cancelled isolates to finish before it raises the original error to the caller.

scope()

Runs body(s) inside a structured concurrency scope.

Every isolate started with s.spawn() or s.spawn_named() finishes before scope() returns.

Errors and cancellation

  1. scope() waits until body(s) returns and every isolate in the scope has finished. 2. If body raises an error, or any isolate in the scope fails, all the isolates that are still running are cancelled with cancel(). 3. scope() waits for the cancelled isolates to finish before it returns or raises an error. 4. If body raised an error, that error is raised again. Otherwise, the first failure among the isolates is raised, not counting the IsolateCancelledError errors that the cancellation caused.

Parameters

  • body (function) — a function, def(s), that receives a new Scope

Returns — any: whatever body(s) returns

Raises IsolateError if an isolate in the scope failed and body didn't raise an error

Raises any: any error raised by body(s)

configure()

Sets the largest number of threads that the pool can run at once. This has no effect once the pool has started, because its size is fixed as soon as the first isolate runs.

The size is a maximum. A thread is only started when an isolate is waiting and every thread that's already running is busy, so a pool sized for peak load only uses as many threads as the load actually needs.

Parameters

  • threads (int)

Returns — bool: true if the size was set, or false if the pool had already started

Raises ValueError if threads is less than 1

pool_size()

The largest number of threads that the pool can run at once. If the pool hasn't started yet, this starts it, with the size set by configure(), or with one thread per CPU if configure() wasn't called.

Returns int

started_count()

The number of threads the pool has started so far. Threads are started as isolates need them, so this number follows the highest number of isolates that have been waiting at the same time, and it never goes above pool_size().

Returns int

cpu_count()

Returns — int: the number of logical CPUs this machine reports.

shutdown()

Stops the pool from accepting any more spawn() calls, then waits until every isolate that has already been spawned, whether it's still queued or already running, has finished. Nothing that's in progress is abandoned.

This is permanent. After it's called, every spawn() for the rest of the process raises an IsolateError, even if this call later times out.

Parameters

  • timeout (number) — the number of seconds to wait before giving up. If it's left out, this waits indefinitely.

Raises IsolateTimeoutError if timeout passes while isolates are still running

active_count()

Returns — int: the number of isolates that are running right now. Isolates still waiting in the queue, which queued_count() counts, aren't included.

queued_count()

Returns — int: the number of isolates that have been spawned but haven't started running yet

is_shutdown()

Returns — bool: true if shutdown() has been called.

wait_any()

Waits until at least one of isolates finishes, and returns it. Use this to respond to whichever of several tasks finishes first, instead of joining them one at a time in a fixed order.

Parameters

  • isolates ([Isolate]) — the isolates to wait for. The list must not be empty.
  • timeout (number) — the number of seconds to wait before giving up. If it's left out, this waits indefinitely.

Returns — Isolate: the one that finished first

Raises ValueError if isolates is empty

Raises IsolateTimeoutError if timeout passes before any of them finishes

Raises IsolateCancelledError if the calling isolate is cancelled while waiting here

wait_all()

Waits until every one of isolates has finished, then returns their results, in the same order as isolates.

Parameters

  • isolates ([Isolate]) — the isolates to wait for. If the list is empty, this returns [].
  • timeout (number) — the number of seconds to wait for all of them together, not for each one. If it's left out, this waits indefinitely.

Returns list

Raises IsolateError from the first isolate in the list whose function raised an error, once all of them have finished

Raises IsolateTimeoutError if timeout passes before all of them have finished

Raises IsolateCancelledError if the calling isolate is cancelled while waiting here

map()

Calls fn once for each item in items, in parallel on the isolate pool, and returns the results in the same order as items. This is the same as spawning one isolate per item and passing the handles to wait_all().

Parameters

  • fn (function) — a closure, bound method or class method
  • items (list)
  • timeout (number) — the number of seconds to wait for the whole batch. If it's left out, this waits indefinitely.

Returns list

Raises IsolateError from the first item in the list whose call raised an error, once every call has finished

Raises IsolateTimeoutError if timeout passes before every call has finished

Raises IsolateCancelledError if the calling isolate is cancelled while waiting here

is_cancelled()

Whether the isolate that's running this code has been asked to stop with cancel(). Long-running code, and loops in particular, should check this from time to time so that they can return early.

Outside an isolate, in the main script or on another thread, this always returns false.

Returns bool

Isolate.cancel()

Asks the isolate to stop. This has no effect on an isolate that has already finished.

If the isolate is waiting in Channel.send(), Channel.recv(), Isolate.join(), wait_any(), wait_all() or select(), that call is interrupted within about 50 milliseconds and raises an IsolateCancelledError.

Otherwise, cancellation is cooperative, and code that's running isn't interrupted. The isolate's function has to check isolate.is_cancelled() and return by itself.

Isolate.is_cancelled()

Returns — bool: true if cancel() has been called on this isolate.

Isolate.name()

Returns — ?string: the name given via spawn_named(), or nil if this isolate was started with plain spawn().

Isolate.try_join()

Returns the isolate's result, or nil if it hasn't finished yet. This doesn't block.

Returns any

Raises IsolateError if the isolate's function raised an error that it didn't catch

Note: An isolate that returns nil can't be told apart from one that's still running. Use is_done() to tell the difference.

Isolate.is_done()

Returns — bool: true if the isolate has finished.

Isolate.status()

The isolate's current state.

Unlike try_join(), this never marks a failure as handled. You can call it as often as you like to check on progress, and the warning for a failure that's never passed to join() or try_join() is still printed. See "Failures" in the module documentation.

Returns — string: 'pending' while the isolate is running, 'done' once it has finished successfully, or 'error' once it has finished with an error it didn't catch

Isolate.handle()

The isolate's native handle. wait_any() needs it to work on a plain list of Isolate objects from outside the class, and it isn't meant to be used directly.

Scope

Supervises a group of isolates started inside a call to isolate.scope().

A Scope guarantees three things:

  1. Every isolate started with s.spawn() or s.spawn_named() is tracked by the scope, and none of them can outlive the scope(body) call. 2. If any of the isolates raises an error that it doesn't catch, or if the body of the scope fails, all the remaining isolates are cancelled with cancel(), so that they don't keep working for nothing.
  2. scope() waits for every isolate, including the cancelled ones, to finish before it raises the original error or returns the body's result.

You can't create a Scope yourself. isolate.scope(body) creates one and passes it to body.
