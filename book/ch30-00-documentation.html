Documenting a Project

zuri doc turns a directory of Markdown into a website: a page for each chapter with the contents beside it, a search box, a page that prints the whole book, light and dark themes, and every code block coloured. This book is built with it, and so is the standard library reference.

What it writes is a directory of plain files. Any web server can serve it, GitHub Pages can publish it as it is, and a browser can read it straight from disk.

Starting a Book

Inside a project, zuri doc init starts a book in its docs directory:

The book takes the project's name as its title, and --title gives it another. Outside a project it starts in the current directory, and naming a directory starts it there instead: zuri doc init manual.

A book is laid out like this:

Every command finds the book the same way: the directory named on the command line, or else the current directory when it holds a doc.toml, or else the docs directory of the project you are in. So zuri doc build works from anywhere inside the project.

The Contents

src/SUMMARY.md lists the pages in the order they are read. A page it does not list is not in the book.

  • The first heading is the summary's own title, and is not shown. Every other heading starts a part: a titled group of chapters, which the contents mark with a colour of its own.
  • A link in a list is a numbered chapter. A list inside its item holds its sections, numbered beneath it as 1.1 and 1.2.
  • A link outside any list is an unnumbered chapter, such as an introduction before the numbered ones or a changelog after them.
  • A link with no address, like [Alerts](), is a draft. It is listed, greyed out, until it has a page.
  • --- draws a line across the contents.
  • {.unnumbered} after a part's heading leaves that part's chapters unnumbered, which suits appendices. After a single link, as in [Settings](settings.md){.unnumbered}, it does the same for that chapter and its sections.

Each page is written where its Markdown file is, with .html in place of .md, so getting-started/installing.md becomes getting-started/installing.html. A README.md becomes its directory's index.html. The front page, index.html, is the first chapter.

Writing Pages

Pages are CommonMark, with GitHub's additions: tables, task lists, strikethrough, footnotes, addresses made into links, emoji shortcodes such as :rocket:, and notes written as > [!NOTE], > [!TIP], > [!IMPORTANT], > [!WARNING] or > [!CAUTION]. HTML can be written into a page as it is.

Every heading gets an id: lower case, with each space made a dash and other punctuation dropped, so ## Running in Production is #running-in-production, the same id GitHub gives it. A heading that repeats an earlier one gets -1 after it, then -2. Braces after a heading give it an id of your choosing, and classes:

Hovering over a heading shows a § that links to it, and the headings of a page are listed beside it under "On this page".

The [markdown] table in doc.toml changes how pages are read. Its keys are the options of the standard library's markdown module, so smart = true gives curly quotes and real dashes, and math = true reads $...$ as mathematics and typesets it on the page. The markdown page of the library reference lists them all.

Links and Files

Link to another page by its Markdown file, as you would on GitHub: [the units](settings.md#units). The link is pointed at the page when the site is built, so it works on GitHub and on the site alike.

Images, and any other file in src that is not Markdown, are copied into the site beside the pages at the same paths, so an image written as ![a chart](images/rain.png) shows in both places too.

Building checks every link that stays inside the book, and reports one that leads to a page SUMMARY.md does not list, to a heading a page does not have, or to a file that is not there, with the line it is on.

Code

Code blocks are coloured as the site is built, so a page reads the same with scripts turned off. The first word of the fence names the language:

Language Fence
Zuri zuri
A REPL session zuri-repl
HTML and Wire html, wire
XML xml, svg
JSON json
Shell scripts sh, bash, shell
Terminal sessions console, terminal
TOML toml
INI and .env files ini, env
JavaScript and CSS js, css

Anything after that first word is left alone, so a block fenced zuri,ignore is coloured as Zuri. A block in any other language is shown as it is, labelled with the name its fence gives.

In a console block, a line starting with a $ prompt is a command, and is coloured as one. Every other line is what the commands printed. A console block with no prompt in it at all is a program's output on its own, and when it follows a code block directly the two are shown joined, as the code and what it printed. Every example in this book is written that way, a zuri block and then a console block:

A paragraph holding nothing but <span class="filename">Filename: main.zu</span>, written just before a code block, becomes a caption on the block naming the file it shows.

Every block of code has a button that copies it. On a terminal session it copies the commands alone, without their prompts or what they printed.

Including Files

{{#include path}} is replaced by the file at path, relative to the page. Written as the only line inside a code block, it makes the block show that file, so an example is always the same as the file it comes from and cannot drift from code that is tested elsewhere:

A colon after the path takes part of the file: forecast.zu:12 is line 12 alone, forecast.zu:5:20 lines 5 to 20, forecast.zu:5: line 5 on, and forecast.zu::20 up to line 20. A name instead of numbers, forecast.zu:today, takes the lines between two comments in the file that mark them, so the file stays a whole program that runs:

The marking lines are never included themselves, whichever part of the file is taken.

{{#title text}} gives a page the title its browser tab shows, in place of the one the contents give it. A backslash in front, as in \{{#include x}}, writes either of them as it is.

Building and Serving

zuri doc build writes the site:

When a link inside the book leads nowhere, it says where:

Without --strict the warnings are printed and the build succeeds. With it the command fails, which is how a CI job keeps a book's links whole. --out writes the site somewhere other than where doc.toml says, and --open opens it in a browser once it is built.

While you write, zuri doc serve builds the site, serves it on this machine, and builds it again each time the book changes:

A page open in a browser reloads itself after every rebuild. A build that fails says why and leaves the last good site in place, and the next save tries again. --port serves somewhere other than 3000, --host 0.0.0.0 lets other machines read it, and --open opens it.

zuri doc clean removes the built site.

Settings

doc.toml has four tables, and every key in them is optional. A key a table does not have, or a value of the wrong type, stops the build with the key named.

[book] says what the book is:

Key Default What it is
title the directory's name the book's title, shown at the top of every page
description none one sentence, for search engines
authors none the authors' names
language "en" the language the book is written in
source "src" the directory of pages
output "site" where the site is written
create-missing false write an empty page for a chapter whose file is missing, rather than stopping

[site] says how the site looks and where it lives:

Key Default What it is
url none the address the site is published at
repository none the source repository, linked from every page
edit none an address for editing a page, with {path} for the page's file
logo none an image shown beside the title
favicon none the icon a browser tab shows
theme "system" how a page first appears: "system", "light" or "dark"
fold false how many levels of the contents start open; false opens every level
numbers true whether chapters are numbered
search true whether the site can be searched
print true whether the site has a page that prints the whole book
css [] stylesheets added to every page
js [] scripts added to every page
cname none the domain GitHub Pages serves the site at

The contents always open as far as the page being read, whatever fold says. [site.home] puts a link back to a site above the book beside its title, and each [[site.links]] adds a link to the top of every page; an address that is not absolute is relative to the book's own front page. [markdown] is described under Writing Pages, and [redirects] keeps an old address working by sending it on to a new one.

Every path in the file is relative to the directory holding it.

Changing the Look

A reader picks light or dark, or follows their system, from the menu at the top of every page, and the choice is remembered. The theme setting decides only how a page looks before they have chosen.

Every page is written through one Wire template, page.html, styled by doc.css and given its behaviour by doc.js. A directory called theme beside doc.toml replaces any of the three with a file of the same name. The ones zuri doc uses are in cmds/doc/theme beside the zuri executable, and a copy of one is the place to start from. The css and js settings add to them instead, which is all most books need:

Publishing

The site is a directory of plain files with nothing to run, so publishing it is copying it somewhere a web server reads.

GitHub Pages serves it as it is. zuri doc writes the .nojekyll file that stops GitHub from leaving out files it does not expect, and a CNAME file when cname is set. Set url as well: it gives every page its canonical address, writes a sitemap.xml for search engines, and lets 404.html, the page a missing address is answered with, work at any depth of the site rather than only at its top.

Every site can be read without a mouse: /, s, or Ctrl+K and ⌘K on a Mac open the search box, the arrow keys move through what it finds, and the left and right arrow keys turn to the previous and next chapter.
