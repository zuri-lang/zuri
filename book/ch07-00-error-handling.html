Error Handling

Things go wrong. A file is missing, a number arrives as text, or a server on the network stops responding. Zuri handles all of these with one mechanism: an Error object that you raise with raise and handle with catch. There's no try, no finally and no checked exceptions.

This chapter covers raising errors, the three forms of catch, what an error contains, the built-in error classes, writing your own, and what to use instead of finally.

Raising Errors

raise only accepts an instance of Error or one of its subclasses. Raising a plain string or number is itself a TypeError:

This is a small inconvenience, but it means that every error has a type, a message and a stack trace, because there's no way to raise anything else.

Catching Errors

The code in the catch block runs. If anything inside it raises an error, execution jumps to the handler, with the error assigned to e. If nothing raises an error, the handler doesn't run.

There are three forms of catch, and each one behaves differently.

catch { ... }, with nothing after it, discards the error and continues:

Only use this when the failure really doesn't matter.

catch { ... } as e, without a handler block, assigns the error to a variable that's still available after the statement. If nothing went wrong, e is nil:

Use this form when the recovery code doesn't belong inside a handler, for example when you want to check several things one after another.

catch { ... } as e { ... } is the full form, and the one you'll use most often.

What an Error Contains

  • message is the error message.
  • type is the name of the error's class, as a string.
  • stacktrace is a list of stack frames, starting with the innermost one. Each frame names a file, a line and a function.

The stack trace is recorded where the error was raised, not where it was caught, so it always points to where the error started, however many frames it passed through:

There are three frames: inner, middle and the top level of the script. Printing the stack trace is often the quickest way to find out how the program got to a certain point, especially in code you didn't write.

Built-in Error Classes

Each of these is a class, and they all inherit from Error:

Class Raised when
Error The base class, for general failures
TypeError An operation received a value of the wrong type
ValueError The type was right, but the value wasn't
NumericError An arithmetic operation failed
ArgumentError A function received the wrong number of arguments
NotImplementedError A method that should have been overridden wasn't
RangeError An index or bound was out of range
AccessError A permission or access check failed
AssertError An assert failed
PropertyError Code read a member that doesn't exist
UndefinedError Code read a name that isn't defined
ModuleNotFoundError An import couldn't be resolved

Since they all inherit from Error, catching Error catches all of them, and a parameter annotated as Error accepts any of them.

This way, close() is written once and always runs, and then you decide explicitly whether to raise the error again. It's the nearest thing Zuri has to finally, built from ordinary statements rather than a separate construct:

Line Purpose
catch { ... } as e Runs the block and records any error, without jumping
handle.close() Cleans up, whichever path was taken
if e { raise e } Passes the error on, unchanged

There are two things to keep in mind.

e is nil when nothing went wrong, so if e { raise e } is all you need to decide what to do. When there's no error, the cleanup runs and the function continues as normal.

Raising e itself again keeps the original stack trace, which points to the line that actually failed rather than to your raise statement. Only wrap it in a new error when you have something to add, as shown in Nesting and Re-raising.

Use the form with a handler when you need to handle the error, and this form when you only need to clean up afterwards.

assert or raise?

assert raises an AssertError when its condition is falsy. The message is optional.

Here's how to decide between them. Use raise for things that can happen, such as a missing file, a number that doesn't parse or a network timeout. The caller is expected to deal with these. Use assert for things that should never happen, such as an invariant that your own code is responsible for keeping. If an assertion fails, the program has a bug. It doesn't mean something outside the program went wrong.

Example: Loading a File

There are four things worth pointing out.

Every failure the caller might reasonably handle is reported as a single error type, StoreError, so the catch on the calling side needs one branch instead of three.

The message always includes the path. A log line that says "file is corrupt" without saying which file can cost someone an hour.

handle.close() is called on both paths: once in the handler before the error is raised again, and once after the block. There's no finally to do this for you, and forgetting the call in the handler is the most common way Zuri code leaks resources.

Finally, the check on the file's contents at the end uses raise, not assert. A file on disk with the wrong contents is a problem with the outside world, not a bug in this function.
