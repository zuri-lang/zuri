Chapter 16 · The Big Modules

Imagine

The imagine module is Zuri's image library. It decodes, draws on, transforms and encodes raster images.

It covers everything a program might do with an image. A photo arrives as an upload, is checked, rotated the right way up, resized and sharpened, gets a watermark, and is sent back out as a WebP. A chart is drawn from nothing but shapes and text. An avatar is cropped to a square, given rounded corners and cached as a data URL. You can do all of this with the standard library alone.

Every image in this chapter was produced by the code next to it, using docs/book/src/imagine/figures.zu. If you run that script again, the figures are regenerated to match what the module currently does.

Copying and Mutation

There's one rule in this module that's worth learning before anything else, because everything else follows from it:

Operations that change the size of an image return a new image. Everything else changes the image in place.

resize(), crop(), rotate(), flip(), transpose() and pad() all leave the original image unchanged and return a new one. Drawing, filters and compositing all change the image you call them on, and return it so you can keep chaining.

This means a chain that mixes both kinds of operation works as you'd expect, and that you should call clone() when you want to keep a copy of an image before applying a filter.

Colors

Writing a Color

Wherever a color is expected, you can write it in five different ways. These all mean the same red:

Hexadecimal strings can have any of the four lengths CSS allows, with or without the leading #: #f00, #f00c, #ff0000 and #ff0000cc. Color names come from the full CSS Color Level 4 list, and they're matched regardless of case, spaces and hyphens, so 'Dark Sea Green' and 'darkseagreen' are the same color.

Alpha ranges from 0 (transparent) to 255 (opaque), as in CSS and PNG.

The Color Class

Color is an immutable value type. Every method that would change a color returns a new one instead, so it's safe to pass a color stored in a variable to other code.

Color Spaces

The conversions come from the colors module, so they follow the same conventions that module and CSS use: hue in degrees, and everything else in percentage points from 0 to 100.

Lab is the right color space for interpolating between two colors when the steps in between need to look evenly spaced. CMYK here is a simple conversion without an output profile, so it's fine for generating colors but not for predicting what a printing press will produce.

Checking Before Decoding

A decoded image takes four bytes per pixel, so a 6000x4000 photo takes up 96 MB in memory, however small the file was. For any image that comes from outside your program, read the header first:

probe() returns {format, width, height}, or nil. It only reads the header, which takes microseconds, while decoding the same file takes tens of milliseconds. If you only need the format name, use imagine.detect().

Format Reference

Format Read Write Alpha Notes
PNG Yes Yes Yes Lossless. The safe default.
JPEG Yes Yes No Lossy. Best for photos.
WebP Yes Yes Yes Written losslessly, so smaller than PNG but larger than a lossy WebP.
AVIF No Yes Yes Smallest files, slowest to encode.
GIF Yes Yes 1-bit 256 colors. The only animated format that can be written.
BMP Yes Yes Yes Uncompressed and very large.
TIFF Yes Yes Yes Common in printing and scanning.
TGA Yes Yes Yes No signature, so it needs an extension or an explicit format.
QOI Yes Yes Yes Lossless, and several times faster than PNG.
ICO Yes Yes Yes Icon container.
PNM Yes Yes No Very simple, and very large.
WBMP Yes Yes No One bit per pixel.

Three of these need some explanation.

AVIF can only be written. Opening an AVIF file raises a DecodeError.

TGA has no magic number, so the only ways to identify it are by its file extension or by naming the format explicitly.

WebP is written losslessly. Reading supports both lossy and lossless WebP, but the encoder only writes lossless WebP. That means quality has no effect, and a photo saved as WebP will be larger than one saved by a tool that writes lossy WebP. For photos where file size matters, JPEG or AVIF is a better choice. Here, WebP is best used as a lossless format with alpha that produces smaller files than PNG.

Rather than assuming which formats are available, ask:

decode, encode and animated are each a list of format names, so you can use contains() to check for the format you need.

Encoding Options

Option Formats Meaning
quality JPEG, AVIF From 1 to 100. The default is 85 for JPEG and 80 for AVIF.
compression PNG 'fast', 'default' or 'best'. All of them are lossless.

Data URLs

Base64 encoding makes the data about a third larger than the raw image, so data URLs are best for icons and small graphics, not photos.

Resizing and Reshaping

Choosing a Resize

There are six ways to resize an image, and choosing the right one is most of the work:

Method Keeps the aspect ratio Enlarges Result
resize(w, h) No Yes Exactly w x h, possibly distorted
scale(factor) Yes Yes The same image, scaled by factor
thumbnail(w, h) Yes No Fits inside the box
fit(w, h) Yes Yes Fits inside the box
cover(w, h) Yes Yes Fills the box, cropping whatever doesn't fit
contain(w, h) Yes Yes Fits inside the box, padding the rest

For thumbnails, thumbnail() is usually what you want, precisely because it never enlarges. Scaling a small image up to fill a thumbnail box only makes it blurry. Use fit() when you do want small images scaled up.

cover() and contain() both produce exactly the size you ask for. The difference is what they give up. cover() cuts off part of the image, while contain() adds bars:

Here's the same 320x180 image resized to 120x120 in four different ways:

thumbnail() keeps the proportions and doesn't fill the box. cover() fills the box and cuts off the sides. contain() fills the box and adds bars. resize() fills the box by distorting the image.

The anchors are TOP_LEFT, TOP, TOP_RIGHT, LEFT, CENTER, RIGHT, BOTTOM_LEFT, BOTTOM and BOTTOM_RIGHT. CENTER is the default. Use TOP for photos of people, since faces are rarely in the bottom third.

NEAREST Fastest Pixel art, QR codes and anything whose edges must stay sharp.
BILINEAR Fast Cases where speed matters more than sharpness.
BICUBIC Moderate Photos, as a good general choice.
GAUSSIAN Moderate Softer results, for noisy images or before sharpening.
LANCZOS Slowest Thumbnails and any large reduction. This is the default.

Here's a 16x16 sprite enlarged seven times, so that the differences are easy to see:

In this case, NEAREST is the right choice and the others are wrong. When you shrink a photo, the opposite is true.

LANCZOS is the default because most resizing makes images smaller, which is where its extra cost pays off. It can produce faint ringing next to edges with very high contrast, which is the price of its sharpness. If that's visible, use BICUBIC instead.

Cropping, Padding and Trimming

crop() requires the rectangle to fit inside the image, and raises a BoundsError if it doesn't. If a crop that went past the edge were clamped instead, you'd get back different dimensions from the ones you asked for, which would be more surprising than an error. If the region really is meant to extend past the edge, pad the image first.

trim() takes the border color from the top-left pixel, unless you specify one. Scanned documents and screenshots nearly always need a tolerance, because a "white" border saved in a lossy format isn't exactly white.

Rotating and Mirroring

Quarter turns are exact, because every pixel is moved without being resampled. Any other angle uses interpolation, and enlarges the canvas to fit the rotated corners, filling the gaps with background.

EXIF Orientation

Phone cameras usually record the camera's orientation in the file instead of rotating the pixels, so a photo whose pixels are sideways is meant to be displayed upright. Image.open() and Image.decode() take care of this for you.

All eight orientation values are supported, including the four mirrored ones produced by scanners and some front-facing cameras.

Filters

Filters change the image in place and return it, so you can chain them.

Tone and Exposure

levels() is the most useful single correction for a flat or washed-out photo. Everything at or below the black point becomes black, everything at or above the white point becomes white, and the range in between is stretched to cover the full scale.

Note the difference between posterize() and quantize(). posterize() spaces its levels evenly, while quantize() chooses colors that suit the image, so a photo still looks good with far fewer colors.

auto_levels() does the same job as levels(), but works out the black and white points for you. It's shown alongside the detail filters below.

Color

grayscale() weights each channel according to how bright it looks to the eye, so a bright yellow becomes light gray and a deep blue becomes dark gray. That's different from saturate(0), which keeps the HSL lightness and turns both into a medium gray.

Blur, Sharpen and Detail

blur() is a true separable Gaussian blur, so its cost grows linearly with the radius rather than with its square. The argument is the standard deviation: about two thirds of each pixel's influence falls within that distance, and the visible spread is roughly three times as far.

Alpha is premultiplied while the blur runs, so blurring a shape on a transparent background doesn't add a dark halo around its edge.

Writing Your Own Filter

Almost every filter above is built from one of three basic operations with different numbers plugged in, and you can use all three directly.

A lookup table handles any tone curve applied to each channel. The table is built once, whatever the size of the image, and then applied at memory speed.

A color matrix handles anything that mixes channels, such as saturation, hue rotation, swapping channels or tinting. It's the same 4x5 matrix that SVG and CSS filters use, written row by row, and the last entry in each row is a constant in units from 0 to 255.

Applying several matrices one after another is both slower and less accurate than combining them and applying the result once:

A convolution kernel handles anything that reads the neighbors of each pixel.

The kernel must be square, with an odd number of rows and columns. The default divisor of 0 means "divide by the sum of the kernel", which is what almost every published kernel expects.

There's one trap to be aware of. The alpha channel goes through the kernel along with the color channels. That's right for a blur, but wrong for any kernel whose weights don't add up to one. Applied to an image that's completely opaque, a Laplacian kernel adds up to zero, which would make the entire result invisible:

The built-in edges(), emboss(), sharpen() and mean_removal() already handle this.

Here are the S-curve and the channel-swap matrix from this section, applied to the same image:

edge controls what happens beyond the border of the image. EDGE_CLAMP, the default, repeats the nearest pixel on the edge. EDGE_TRANSPARENT treats the area outside as empty, and EDGE_WRAP wraps around to the opposite side, for images that are meant to tile.

Drawing

Shapes

Coordinates start at the top-left corner. Whole-number coordinates fall on the corners of pixels, not their centers, so a rectangle from (0, 0) to (10, 10) covers exactly the first ten pixels in each direction.

Angles are in degrees, measured clockwise from three o'clock, which matches the direction of the y axis.

Drawing outside the image is never an error, because anything outside is simply clipped. That makes it safe to draw a shape that only partly overlaps the image.

Strokes and Anti-aliasing

Both are set on the image rather than passed to each call, although a single call can override the thickness:

Strokes are centered on the path, so a thickness of 4 puts 2 pixels on each side. The corners and the ends of an open path are rounded.

Anti-aliasing is on by default. Turn it off when the output has to be exact to the pixel, such as for barcodes, QR codes, or anything you'll apply a threshold to later.

Paths and Polygons

Every filled shape in this module is turned into a polygon and drawn by the same scanline rasterizer, and every outline is turned into the polygon around its stroke and drawn the same way. To draw a shape that isn't listed above, provide its points:

The points can be a list of [x, y] pairs or a flat list of alternating x and y values. Depending on where the points came from, one or the other will be more convenient. The outline is closed for you, so the last point doesn't need to repeat the first.

Outlines that cross themselves are filled using the nonzero winding rule, which fills a five-pointed star completely. Pass { even_odd: true } to use the other rule, which leaves the middle of the star empty.

Filling Areas

Gradients are described in their own section below.

fill() replaces pixels rather than blending with them, so filling with a transparent color clears the image instead of leaving it unchanged.

A flood fill spreads in four directions (up, down, left and right, but not diagonally) through pixels whose color is within tolerance of the color at the starting point. A tolerance of 0 only spreads through pixels that are exactly the same color, so for a photo or anything anti-aliased, you'll need a higher value.

Gradients

A linear gradient runs along the line from the first point to the second. Everything before that line gets the color of the first stop, and everything after it gets the color of the last stop, so a short line across a large area produces a sharp transition with solid bands on either side.

The stops can be plain colors, which are spaced evenly, or [offset, color] pairs, where the offset ranges from 0 to 1:

By default, a gradient replaces what's already there. Pass { blend: true } to blend it with the image instead, which is how you make overlays and vignettes:

{ rect: {x, y, width, height} } limits the gradient to a rectangle instead of covering the whole image.

Clipping

A clip limits every drawing operation to a region until you clear it. It doesn't affect reading, so get_pixel() can see the whole image either way.

Text

The Built-in Font

imagine doesn't include any font files, so everything in the next section depends on the fonts installed on the machine, and it can fail. One font always works:

Font.builtin(size) gives you the same font, under a name you'll find on Font.

It isn't a font file. Every glyph is defined as geometry, using center-line strokes instead of filled outlines, in libs/imagine/strokefont.zu, and it's drawn with the same anti-aliased rasterizer as everything else. That means it scales cleanly to any size, and its weight is a parameter rather than part of the design:

Here's the complete character set:

What it's for. Labels, chart axes, watermarks, diagrams, placeholder text, and any output that has to work on a machine without fonts installed. It looks geometric and has a single weight, more like a technical drawing than a typeface, because that's what center-line strokes naturally produce.

What it's not for. Body text, headlines or anything where the shapes of the letters matter. Load a real font for those.

It covers printable ASCII, from the space character to ~. Any other character is drawn as the empty box that fonts use for missing glyphs, so text in another script is visibly missing rather than silently blank.

A StrokeFont has the same interface as a Font, with size(), metrics(), measure(), render() and wrap(), so you can use either one anywhere a font is accepted.

Loading a Font

Font.load() reads a TrueType or OpenType file and caches the parsed font by its path, so loading the same file twice in one process only parses it once. Font.system() searches the platform's font directories for a family name, ignoring case, spaces and hyphens.

Font.sans() finds whichever common sans-serif font is installed. It's handy for scripts and tests, but don't rely on it for output that has to look the same everywhere, because the font it finds depends on the machine, and a container image without fonts won't have any to find. In that case, it raises a FontError that suggests Font.builtin(), which never depends on what's installed.

A Font is immutable and cheap to copy. size() returns the same font at a different size, sharing the parsed data:

Drawing Text

x and y are the top-left corner of the text's bounding box, not its baseline, because the corner is what you usually know when you place text in a layout. Pass { baseline: true } if you want y to be the baseline of the first line instead.

A \n starts a new line.

align positions the lines relative to each other, not relative to the image. line_height is a multiplier applied to the font's recommended line spacing, and tracking adds space between characters, in pixels.

Measuring and Positioning

Measuring text takes a fraction of the time it takes to draw it, so measure first when you lay out text, whether you're centering it, wrapping it or sizing a background to fit.

Wrapping

The width option wraps the text to that many pixels before drawing it. text_size() accepts the same option, so measuring wrapped text gives you the size of the box it will actually take up.

To get the wrapped text itself, so you can store it or draw it in pieces, call wrap() on the font:

Newlines in the text are kept as paragraph breaks, and runs of spaces are collapsed into one. Words are kept whole where possible. A single word that's too long for the width is broken between characters instead of being allowed to overflow, because text that runs off the edge of an image can't be scrolled into view.

Text Layout Limitations

Glyphs are positioned by their advance widths, with kerning applied. That works for Latin, Greek, Cyrillic and any other script written left to right without contextual shaping.

Complex shaping isn't supported. Arabic letters won't join, Indic clusters won't be reordered, and ligatures aren't substituted. All of those need a shaping engine.

Compositing

Drawing One Image Onto Another

The source image is clipped to the destination, and its position can be negative, so a sprite that hangs off the top-left corner is drawn correctly. You can composite an image onto itself, because it's copied first.

Blend Modes

Mode Effect
BLEND_NORMAL Ordinary alpha compositing. This is the default.
BLEND_MULTIPLY Never lighter than either input. Good for shadows.
BLEND_SCREEN Never darker than either input. Good for glows.
BLEND_OVERLAY Multiply in the shadows, screen in the highlights.
BLEND_DARKEN / BLEND_LIGHTEN Keeps the darker or lighter value of each channel.
BLEND_COLOR_DODGE / BLEND_COLOR_BURN Strong brightening or darkening.
BLEND_HARD_LIGHT / BLEND_SOFT_LIGHT Overlay with the roles of the two images reversed, and a gentler version of it.
BLEND_DIFFERENCE / BLEND_EXCLUSION The absolute difference, and a version with lower contrast.
BLEND_ADD / BLEND_SUBTRACT Adds or subtracts, clamping the result.

The formulas come from the CSS compositing specification, which is also what image editors use.

BLEND_DIFFERENCE gives you a quick visual diff, because two identical images blended this way produce black.

Here's a red circle drawn onto a gradient with eight of the modes:

Drawing operations such as lines, shapes and text always use ordinary alpha compositing. To draw a shape with a blend mode, draw it on a layer and then composite the layer.

Masks

Each pixel keeps its color and takes its transparency from the mask. Opaque white lets the image show through completely, black or transparent hides it, and shades of gray make it partly transparent. The mask's own alpha channel is taken into account, so a shape drawn on a transparent background works as a mask without being filled in first.

The mask has to be the same size as the image.

Layers

layer() returns a transparent image of the same size. Building a composite from layers lets you create effects that a single pass can't, and it's the way to apply a blend mode or an opacity to a group of operations instead of just one:

Inspecting an Image

Apart from the dimensions, there are four methods that tell you about the contents of an image.

histogram() counts how many pixels have each value, and returns four lists of 256 entries: red, green, blue and luma. Completely transparent pixels are skipped, since you can't see their color. A histogram tells you whether an image is underexposed (most values at the low end), flat (most values in the middle) or clipped (a spike at 0 or 255).

auto_levels() is an automatic version of levels(). It finds the black and white points from the brightness histogram and stretches the range between them, ignoring a small fraction at each end so that a few stray pixels can't affect the result.

average_color() returns the average color, weighting each pixel by its alpha, so a mostly transparent image reports the color of the part you can see.

dominant_colors() returns the colors that take up the largest part of the image, starting with the most common. The image is first shrunk and reduced to a small palette, so this costs about the same whatever the size of the original.

difference() measures how different two images are, from 0 (identical) to 1, which makes it useful in tests that check rendered output:

Animation

Frames are returned already composited onto the frames before them, so you can use frame 5 on its own without replaying the first four. You never have to deal with the disposal and transparency rules that animated GIFs are built from.

Creating and transforming animations:

map() copies each frame before passing it to the function, so a chain of filters works directly as the function body and the original animation isn't changed. Because of that copy, map() needs as much memory again as the animation itself. To filter frames in place, loop over frames() and change each image directly.

Both animated GIF and animated WebP can be read, but only GIF can be written. A still image is decoded as an animation with one frame instead of raising an error, so code that handles both doesn't need separate branches.

Every frame must be the same size, because animated formats have a single canvas that each frame is drawn onto.

Working With Pixels Directly

pixels() returns the live pixel buffer. It's 8-bit RGBA with straight (not premultiplied) alpha, stored row by row without padding, so pixel (x, y) starts at byte (y * width + x) * 4.

This is intentional, and it's much faster than calling a method for every pixel, so you can still write efficient Zuri code for operations this module doesn't provide. Adding type annotations to the function's parameters helps here:

set_pixels() takes a buffer back, which lets you save a copy before applying a destructive filter and restore it afterwards:

Image.from_pixels() creates an image from a buffer that came from somewhere else entirely.

Errors

Errors fall into two groups. An argument of the wrong type raises a TypeError, from the parameter's own type annotation. Every other error is a subclass of ImageError, so one catch handles all of them:

Error Raised when
ImageError The base class. It's also raised directly for invalid arguments.
DecodeError The data isn't an image, is in a format this build can't read, or is truncated.
EncodeError The image can't be written in the requested format.
FormatError A format name or file extension isn't one this module recognizes.
BoundsError A rectangle, crop or resize goes outside the image, or a dimension is less than 1.
FontError A font can't be parsed, found or used for layout.

Two kinds of failure are intentionally outside that hierarchy.

An argument of the wrong type raises a TypeError. Parameters declare their types, so the check happens when the method is called, and the message names the parameter:

An invalid color raises a ValueError, because that's what the colors module raises for it, and changing the error type would lose the distinction between "not a color" and "not a string":

A value of the right type that's out of range still raises a subclass of ImageError, because that's a judgment this module makes, not a type the runtime can check:

You should always be prepared for DecodeError, because any image that comes from outside your program can cause it.

Drawing operations don't raise BoundsError. A line that runs off the edge of the canvas is clipped, as in any drawing API. Only operations that have to return an image of an exact size have no sensible way to continue.

Performance and Memory

Every pixel takes four bytes. A 6000x4000 photo takes up 96 MB once decoded, however small the file was, and an animation of 100 frames at 500x500 takes up 100 MB. Call probe() before decoding any image whose size you don't control.

Here's some rough guidance on what each kind of operation costs:

  • Decoding and encoding take most of the time in almost every pipeline. PNG with 'best' compression is several times slower than with 'default', and saves only a few percent in size. AVIF is slower still.
  • Resizing costs roughly in proportion to the size of the output, so shrinking is cheap and enlarging isn't. LANCZOS costs a few times as much as NEAREST.
  • Blurring costs time in proportion to the radius rather than its square, because the blur is separable. A 3x3 convolve() is cheaper than blur(1), but by blur(5), the Gaussian blur is much faster.
  • Lookup tables and color matrices are limited by memory speed, and they're about as fast as anything that touches every pixel can be. You can chain as many as you like, but combine matrices with combine_matrices() instead of applying them one at a time. That's both faster and more accurate, because the intermediate result is never rounded back to 8 bits.
  • Drawing costs in proportion to the area covered, and anti-aliasing samples each row of pixels four times. Turning anti-aliasing off makes a real difference for very large fills.

If the result is going to be smaller anyway, resize before you apply filters. Filtering a 24-megapixel photo and then shrinking it to a thumbnail gives the same visual result at forty times the cost.
