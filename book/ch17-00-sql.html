Chapter 17 · The Big Modules

Databases

The sql module is how a Zuri program works with a relational database. There's a single module rather than one for each database engine, and that's the core of its design. sql defines what a database adapter has to provide, supplies everything that works the same way regardless of the engine, and chooses the adapter based on the connection string.

It comes with three adapters that support four major database engines: SQLite, PostgreSQL, MySQL and MariaDB. SQLite is a file-based database with no server to run and nothing to configure, which makes it a good fit for applications that ship with their own data and for test suites that need a real database for each run. PostgreSQL, MySQL and MariaDB are database servers for anything that outgrows a single file. The MySQL adapter works with MariaDB as well.

To switch from one database to another, you change the connection string, plus any SQL that the two engines really do write differently.

Introduction

A database library usually ties a program to a single engine. Its functions are named after that engine, its placeholders follow that engine's syntax, and its errors use that engine's error numbers, so switching to another database means rewriting every call.

sql keeps the parts that are the same for every engine in one place, so you write a statement once:

If you change the first line to postgres://localhost/app or mysql://localhost/app, the rest runs unchanged. On PostgreSQL, the ? becomes $1, because that's what PostgreSQL expects, and on MySQL it stays ?, because that's what MySQL expects. An insert that asks for its new ID gets a RETURNING clause on PostgreSQL, because PostgreSQL has no "last insert ID" and the other two do. A duplicate key is reported as a UniqueViolation by all three.

What sql doesn't do is pretend that the engines are the same. They differ on auto-incrementing keys, on which functions are available and on a lot of other SQL. sql translates what it can and is explicit about the rest.

Rows, Columns and Types

A row is a dictionary keyed by column name, which is why you can write post.title.

Two columns with the same name collapse into one entry in a dictionary, so keep that in mind before you select id from both sides of a join. Give one of them an alias to fix it, or use tuples() if you can't.

Values are converted like this:

Zuri Database
nil NULL
bool A boolean, where the engine has one, and 0 or 1 otherwise
number An integer if the value is a whole number, and a float otherwise
bigint A 64-bit integer, for values too large for a double
string Text
bytes A blob
date.Date A timestamp
sql.Time A TIME interval, on engines that have one
sql.Decimal An exact decimal
list, dict JSON

Not every engine has all of these types. PostgreSQL has a real boolean type and MySQL doesn't, so a true written to MySQL is read back as 1. Use db.supports() to find out about this kind of difference instead of guessing. Each engine's section below describes where it differs.

An integer that's too large for a double is returned as a bigint instead of being silently rounded:

SQLite stores five kinds of value and doesn't record what you meant, so a boolean is stored as 1 and would be read back as the number 1. What SQLite does keep is the type each column was declared with, and the adapter uses that to convert values when it reads them:

A column without a declared type is an expression, and its value is returned exactly as it was stored.

Exact Decimals

A number is a double, which can only store 0.1 approximately. That isn't good enough for money, so sql.Decimal stores a value exactly:

PostgreSQL's numeric, MySQL's DECIMAL, and SQLite's DECIMAL and NUMERIC columns are read and written as Decimal values. SQLite stores a decimal as a double, which holds 15 significant digits exactly, so a decimal column in SQLite can hold at most 15 digits, and table.decimal() rejects a larger precision on SQLite. An aggregate such as sum() doesn't have a declared type, so its result is returned as a number.

CRUD Helpers

Four methods on a connection let you work with rows without writing any SQL. insert(), update(), delete() and find() take a table name and dictionaries, build the statement for whichever engine you're connected to, and bind every value as a parameter.

They exist because the statements they replace are the ones least worth writing by hand. Those statements are repetitive, they differ between dialects in small ways that only show up in production, and building them by joining strings is how SQL injection gets in. Anything more complex than a simple list of conditions is still written in SQL, and you can mix the two freely on the same connection.

Inserting Rows and Getting Their IDs

insert() takes a table name and a dictionary, and returns the ID of the new row:

This method hides the biggest difference between the engines. SQLite and MySQL report the ID of the row that was just inserted, but PostgreSQL doesn't, so an insert that needs the ID has to ask for it with a RETURNING clause that names the primary key. MariaDB supports both and uses RETURNING. insert() does whichever applies, and finds the primary key by asking the schema rather than assuming it's called id.

Writing Filters

The type of a condition's value determines what it means. A plain value means equality, a list means IN, an empty list matches nothing, and nil means IS NULL rather than = NULL, which no row would ever match.

Several conditions in the same dictionary are combined with AND. There's no way to express OR, so that's usually the first thing you'll need to write in SQL:

Passing nil as the whole filter matches every row. You have to ask for that explicitly, rather than it happening because a dictionary turned out to be empty. That's what prevents a filter built from user input from turning into an UPDATE without a WHERE.

Using the Helpers in a Transaction

A Transaction has all of the same methods, and they work the same way. A read inside a transaction sees what that transaction has written, even though nobody else has committed it yet:

Rolling back undoes those changes, and a transaction that has already been committed rejects these calls, just as it rejects everything else.

Limitations of the Helpers

The helpers only support a simple list of equality conditions. There are no joins, no OR and no expression trees, because SQL is a better language for those than any chain of method calls. For a query that needs one, use query() or fetch_all() on the same connection, alongside the helpers.

Transactions

With the closure form, the transaction is committed when the body returns and rolled back when it raises an error, so there's no way to leave a transaction open by accident:

A failure undoes everything in the transaction:

A transaction() called inside another one becomes a savepoint, so a helper that opens a transaction works the same way whether it's called on its own or as part of a larger piece of work. Only the outermost transaction commits, and a failure inside an inner one only undoes that inner piece:

On SQLite and PostgreSQL, schema changes are part of the transaction, so if a series of create table statements fails halfway through, nothing is left behind. MySQL and MariaDB commit any open transaction on every create, alter and drop, so on those engines, a transaction() whose body changes the schema raises a TransactionError when it tries to commit. db.supports('transactional_ddl') tells you which behavior applies, so a program that migrates its own schema can run each change inside a transaction where that works, and on its own where it doesn't.

You can request an isolation level. If an engine can't provide the level you ask for, it says so instead of quietly giving you a weaker one:

Level Support
sql.READ_UNCOMMITTED MySQL supports it. PostgreSQL accepts it, but gives you read committed.
sql.READ_COMMITTED Supported everywhere
sql.REPEATABLE_READ Supported everywhere, and the default on MySQL
sql.SERIALIZABLE Supported everywhere

begin() starts a transaction that you commit or roll back yourself, for a transaction that doesn't fit inside a single block. The closure form is safer, so use it when you can.

Streaming Large Results

query() builds the entire result in memory. That's fine for the hundreds of rows most queries return, but not for the millions that some return. stream() reads the same result one row at a time:

Reading to the end closes the cursor. If a loop stops early, the cursor isn't closed, so any loop that might break needs to close it:

take(n) reads a batch of rows at a time, for work that naturally happens in batches:

On PostgreSQL, this uses a server-side portal, and on MySQL a server-side cursor. Both fetch rows in batches, whose size you can set with { batch: n }. On SQLite, the engine itself computes rows as they're requested, so only the current row is held in memory.

A server-side cursor keeps its connection busy while it's open, because the server is partway through sending the result. If you run another statement on that connection before the cursor has been read to the end or closed, an error is raised, so the two exchanges can't get mixed up.

Prepared Statements

Compiling a statement is the expensive part of running it, so a statement that runs in a loop should only be compiled once:

The placeholders are translated once, when the statement is prepared, so the loop doesn't do any string processing at all. A prepared statement has the same query and fetch methods as a connection.

A prepared statement belongs to the connection that prepared it. Closing the connection also closes the statement and any cursor still open on it, and using either of them afterwards raises a ClosedError.

Connection Pools

Opening a connection is expensive. For PostgreSQL and MySQL, it involves a TCP connection, a TLS handshake and an authentication exchange, all before the first statement runs. A server that opened a new connection for every request would spend most of its time connecting.

Used like this, the pool takes a connection, runs the statement and returns the connection to the pool. When several statements have to run on the same connection, as they do in a transaction, with_connection() holds onto one connection and releases it however the block ends:

transaction() on the pool does the same thing in a single call.

Setting Meaning
max The maximum number of connections to open. The default is ten.
min The number of connections to open in advance. The default is none.
idle_timeout How long an idle connection is kept
max_lifetime How long a connection is kept before it's replaced
validate_on_acquire Whether to check that a connection still works before handing it out
on_connect A function to run on each new connection

Keep a pool as small as your workload allows. Connections have a cost on the database side too, and a pool that's larger than the database can usefully handle just moves a queue from your application into the database, where it's harder to see.

A pool belongs to the isolate that created it, which has two consequences. An isolate that needs database access creates its own pool. And a call never waits when the pool is empty, because nothing else could release a connection while the call is running, so running out of connections is reported as an error rather than waited out.

Errors

Every error is a sql.SqlError. Catch that to handle anything that can go wrong with a database, and use the subclasses to handle particular kinds of error differently.

The error classes are the same on every engine, and that's the point. A unique constraint violation is SQLSTATE 23505 on PostgreSQL, error number 1062 on MySQL and extended result code 2067 on SQLite. None of these numbers mean anything to the other engines, so code that checked for any of them would stop working as soon as you changed adapters.

The engine's own information is kept rather than thrown away. code holds the code the engine reported, sqlstate holds the five-character SQLSTATE code where there is one, and query holds the statement that failed:

SerializationError and DeadlockError are the two errors worth retrying. Both mean that the engine abandoned a transaction to keep its guarantees, and running the whole transaction again usually succeeds.

Schema Introspection

db.schema tells you what's in the database. The queries it runs are completely different for each engine, but the results have the same structure.

Every method takes an optional schema name. PostgreSQL has schemas inside each database, and finds the default through search_path. MySQL calls a database a schema and has no level above it, so naming a schema there names a database. SQLite has neither, and ignores the argument.

Each column is described in the same way, whichever engine you're using:

indexes() and foreign_keys() describe the rest of the table:

This is also what makes insert() portable. On an engine without a "last insert ID", the insert needs a RETURNING clause, and the column to return is the table's primary key, which is looked up here.

One thing to watch for when moving a schema between engines: MySQL parses a references clause on a column and then ignores it, so a foreign key declared that way exists on the other two engines but not on MySQL. If you declare it at the table level instead, it exists on all three.

Creating, changing and dropping tables, using one description that works for every engine, is covered in Changing the Schema.

Three things had to be written separately for each engine, and they're the three things that really are different:

  • The connection string, which is the whole idea.
  • An auto-incrementing key, which isn't part of standard SQL. PostgreSQL uses serial, MySQL uses auto_increment, and SQLite uses integer primary key.
  • Any SQL that only one engine supports. sql doesn't parse or rewrite statements beyond their placeholders, so a PostgreSQL array operator, a MySQL on duplicate key update or a SQLite json_extract is passed through unchanged.

SQLite Features

db.native() gives you the adapter underneath, which is where the engine's own features are.

A SQLite database is a file, except for :memory:, which isn't. An in-memory database belongs to the connection that opened it, so a second connection to :memory: opens a second, empty database, not another handle to the same data.

Foreign keys are enforced. By default, SQLite doesn't enforce them, separately for each connection, for compatibility with databases created before it supported foreign keys. A database that declares foreign keys almost certainly wants them enforced, so the adapter turns enforcement on. Pass foreign_keys: false to turn it off.

SQLite doesn't have a timestamp type, so a date.Date is stored as ISO 8601 text in UTC, whatever time zone offset it had. Text in that format sorts and compares in chronological order, so order by and < on such a column agree with the clock. When a date is read back, it represents the same moment, in UTC.

Functions Written in Zuri

PostgreSQL Features

The adapter uses version 3 of the PostgreSQL wire protocol, over TCP or a Unix domain socket, with optional TLS.

A host that starts with a slash is a socket directory, as it is in libpq, and the socket inside it is named after the port. So /var/run/postgresql with port 5432 means /var/run/postgresql/.s.PGSQL.5432. A path that already names the socket file is used as it is. TLS isn't used over a socket, because there's nothing in between to protect against, so sslmode is ignored in that case.

sslmode controls how TLS is used: disable never uses it, prefer uses it when the server supports it, and require always uses it and fails if the server refuses. Only require verifies the server's identity.

Statements are sent using the extended query protocol, which compiles them on the server and binds values rather than substituting them into the text. Values are sent in the server's own binary format whenever the adapter has a codec for the type, and as text otherwise, so even a type it doesn't know about arrives in readable form instead of as raw bytes.

numeric columns are read as sql.Decimal values, arrays as lists, jsonb as dictionaries, and timestamps as date.Date values.

Listening for Notifications

LISTEN and NOTIFY are PostgreSQL's built-in publish and subscribe mechanism. A connection that has run LISTEN channel receives a message whenever anyone runs NOTIFY channel.

Notifications arrive in between other messages, so a connection that's busy running statements collects them along the way, and poll() returns whatever has built up.

MySQL Features

The adapter implements the MySQL client/server protocol directly, over TCP or a Unix domain socket, with optional TLS, and doesn't depend on any client library. MariaDB uses the same protocol, and the same adapter works with it.

A socket option names a socket, and so does a host that starts with a slash. Unlike with PostgreSQL, the path names the socket file itself, not the directory it's in:

TLS isn't used over a socket, because there's nothing in between to protect against. The connection is treated as private, which lets caching_sha2_password and sha256_password send the password directly instead of encrypting it with the server's public key.

A statement without values is sent as text, which takes one round trip. A statement with values is prepared, so the values are sent in the server's binary format instead of being written into the SQL, and quoting is never an issue. Compiled statements are kept and reused, so a query that runs in a loop is only compiled once.

MySQL leaves ? as it's written, and it reports the ID of an inserted row instead of returning it, so insert() reads the reported ID instead of adding a RETURNING clause. MariaDB differs in two ways that affect the SQL generated by the layers above: it supports RETURNING, and it doesn't have a JSON type. Which behavior applies depends on the server, not the scheme, so for a MariaDB server reached through mysql://, db.driver_name() returns 'mariadb' and db.supports('json') returns false.

How Column Types Are Read

DECIMAL columns are read as sql.Decimal values, JSON as lists and dictionaries, DATE, DATETIME and TIMESTAMP as date.Date values, and TIME as sql.Time values.

MySQL doesn't have a boolean type. BOOLEAN is another name for TINYINT(1), so a value written as true is read back as 1, and db.supports('booleans') returns false to reflect that.

BLOB and TEXT have the same type in the protocol, and the only way to tell them apart is the column's collation, which the adapter checks. A binary column is read as bytes and a text column as a string. BIT and GEOMETRY are read as bytes, because Zuri has no natural way to represent them. SET is read as the comma-separated text that the server stores, not as a list, because a list written back would be encoded as JSON and the column would silently stop matching.

MySQL writes a missing date as zeros, but 0000-00-00 isn't a date in any calendar, so it's read as nil.

TIME Values Are Durations

A TIME column ranges from -838:59:59.999999 to 838:59:59.999999. It's a duration rather than a time of day, so it can be negative and can be longer than 24 hours, and neither of those would survive being read into a date.Date. sql.Time holds it instead:

Time zones

A DATETIME doesn't store a time zone, and a TIMESTAMP is converted to and from the session's time zone. That means the session's time zone determines what a timestamp means, and if it were left to the server's configuration, the same database could give different results on two different machines.

The adapter sets the session's time zone to UTC when it connects. Every timestamp is then read in UTC, and a date.Date that's written back is converted from whatever offset it has. To keep the server's own setting, pass nil as time_zone, or pass the name of the time zone you want to use:

Authentication

The supported methods are caching_sha2_password, which is the default from MySQL 8.0 onward, mysql_native_password, sha256_password, mysql_clear_password and MariaDB's client_ed25519.

Two of these need the actual password, rather than proof of it, the first time an account authenticates. Over TLS, the password is sent as is. Over an unencrypted connection, it's encrypted with a public key that the server sends first, so it can never be read in transit. mysql_clear_password has no such fallback, so it's rejected on any connection that isn't private, because it sends the password without any protection.

TLS

sslmode controls how TLS is used:

Mode Meaning
disable Never use TLS.
prefer Use TLS when the server supports it, without verifying the server's identity. This is the default.
require Always use TLS, without verifying the server's identity.
verify Always use TLS, and verify the server's certificate and host name.

MySQL's own names are accepted too. DISABLED, PREFERRED and REQUIRED mean what they say, and VERIFY_CA and VERIFY_IDENTITY both become verify. That makes VERIFY_CA stricter here than in the MySQL command-line client, which checks the certificate but not the host name. The difference can only ever cause a connection to be refused, never cause a server to be wrongly trusted.

ssl_ca names a certificate authority to trust, and ssl_cert and ssl_key provide a client certificate.

Compression

The protocol can compress everything after the handshake:

Compression is worthwhile for large results over a slow network, but costs more than it saves over a local socket, so it's off unless you turn it on. Packets that are too small to benefit are always sent uncompressed, which the protocol allows.

Sending a File to the Server

With LOAD DATA LOCAL INFILE, the server names a file and the client sends it. The file is read from the machine the program is running on, but the server chooses which file, so a malicious or compromised server could ask for any file the process can read. For that reason, it's refused unless you provide a reader:

The reader decides what can be sent, which is where that decision belongs. When a request is refused, the server still gets an answer, so the connection can still be used afterwards instead of waiting for a file that will never arrive.

Statements With Several Results

A stored procedure sends one result set for each select inside it, followed by an OK packet. query() returns the first result set and reads the others, because leaving them unread wouldn't discard them. They would be returned to the next statement, which would then get this statement's rows.

The body of a stored routine contains semicolons, and exec_script() splits a script at every semicolon. So send a create procedure statement through exec() as a single statement, not through exec_script().

Accessing the Adapter

Writing Your Own Adapter

An adapter for another engine implements four classes: a Driver that reads a connection string and opens a connection, a DriverConnection that runs statements, a DriverStatement and a DriverCursor.

Everything above the adapter comes for free, including connection pools, transactions and savepoints, the CRUD helpers, placeholder translation, cursors, the error hierarchy and models. The adapter only has to provide access to the engine.

Schema changes and migrations need one more thing: how the engine writes table definitions. An adapter provides this by subclassing sql.DdlAdapter, which already writes standard SQL, and overriding whatever the engine does differently, such as type_name() for each column type and key_definition() for an id() column. It then returns an instance of that class from its driver's ddl() method. A driver that doesn't provide one rejects schema changes with a NotSupportedError.

The base classes raise NotImplementedError for anything that hasn't been implemented, so an unfinished adapter fails exactly where the gap is. An engine that really can't support a feature raises NotSupportedError instead. The two errors are deliberately different: the first means the adapter is unfinished, and the second means the engine has a genuine limitation.

Design Limits

Rows are dictionaries. A connection returns rows, never objects. Models are provided by sql.model, which is built on top of sql and only loaded by programs that use it.

It doesn't write joins for you. The CRUD helpers support a simple list of equality conditions, and models support their own columns and associations. Anything beyond that is written in SQL.

It doesn't translate SQL. Placeholders are rewritten, but statements aren't parsed, so a function that only one engine supports still only works on that engine.

It doesn't hide differences by guessing. When an engine can't do what was asked, you get a NotSupportedError that names the adapter and the feature, instead of an approximation you didn't ask for.

Module Reference

The standard library reference documents every class and method. Here's an overview of the module:

Function Description
sql.open(dsn, options) Opens a connection
sql.pool(dsn, options) Opens a connection pool
sql.register(driver) Registers an adapter
sql.drivers() Lists the registered adapters
sql.raw(fragment) Marks SQL to be used exactly as written
sql.Decimal(text) Creates an exact decimal
sql.time(h, m, s) Creates a signed duration, like a value in a TIME column
sql.parse_time(text) Reads a duration from text
sql.blueprint Table definitions that work for every engine
sql.migrate Versioned schema changes, and the Migrator that applies them
sql.model Models: Model, Query and the errors they raise

Methods of a Connection:

Method Purpose
query, exec, exec_script Run statements
fetch_one, fetch_all, fetch_value, fetch_column Read results
stream, prepare Create a cursor or a compiled statement
insert, insert_many, update, delete, find, find_one, count Run the common statements without writing SQL
transaction, begin, in_transaction Work with transactions
schema Introspection, plus create_table, alter_table, rename_table and drop_table
model Query a model's rows
driver, driver_name, capabilities, supports Describe the engine
native The adapter underneath
ping, close, is_closed Manage the connection itself

Method Purpose
query, exec Run statements
fetch_one, fetch_all, fetch_value Read results
insert, insert_many, update, delete, find, find_one, count The same helpers a connection has
schema, model The connection's schema and models, inside the transaction
commit, rollback, is_finished End the transaction
connection, nested The connection it's running on, and whether it's a savepoint
