Metaprogramming and Reflection

Zuri programs have access to Zuri's own compiler. The zuri module provides the lexer, the parser and the bytecode compiler as ordinary functions, along with a reflection API for working with live functions, classes, modules and instances.

That's an unusual amount of the language to expose, so it's worth being clear about what it's for. These are the tools behind documentation generators, linters, plugin loaders, serializers, debuggers and editor tooling, which are all programs that work with other programs. They aren't meant for everyday code, and the chapter ends with the one thing they intentionally can't do.

Reflection and the Compiler API

The module is divided into two clear halves, and confusing them is the most common mistake:

Reflection The compiler API
Works with Objects that exist right now Source code
Entry points zuri.reflect.* tokenize(), parse(), compile()
Can tell you A function's arity, a class's fields, an instance's values A doc block, a comment, a line number, what the compiler produced
Can't tell you Anything about the source code it came from Anything about a running value

A function's arity is a run-time fact. The function object stores it, and reflection reads it. The same function's doc block is a fact about the source code. It only exists in the file, and only the parser can find it. No function bridges the two, which is why a documentation generator parses files instead of importing them.

A Common Structure

tokenize(), parse() and compile() all return results with the same structure: a flat list of small records, each tagged in the same way.

Function Returns Tag Data
tokenize(source) A list of Token kind value, text
parse(source) A list of Node kind fields
compile(source) A list of Instr op fields

There's a single Token class, a single Node class and a single Instr class, rather than one class for each kind of token, grammar rule or opcode. The grammar has about fifty node types and the instruction set has about sixty opcodes, so a class for each would mean more than a hundred nearly identical classes that would have to be kept in sync with the compiler forever.

The downside of this choice is real: nothing tells you which fields a particular kind has. Your editor can't autocomplete a Binary node's left, op and right. Instead, the module relies on a different habit, which is to run it and look:

Everything about that node is right there. It's a Stmt that wraps a Var, the initializer is a Binary node whose op is the string 'Plus', and the literal 1 is an Integer node rather than a generic literal. Each header shows where the node starts, and name_span shows exactly where the name total is. You didn't have to look anything up.

dump() is the quickest way to learn the structure of any node, and it's the first thing to try whenever you're unsure. zuri.dump_file(path) does the same for a whole file.

Runtime Reflection

Reflection answers questions about a value you have. Every reflection function is in zuri.reflect.

What Kind of Value Is This?

kind() is a more literal version of typeof(). Note the last line: a built-in native function reports 'function', as do closures and bound methods, because as far as the language is concerned, all three can be called in exactly the same way.

Functions

function_info() returns { name, arity, variadic, is_method, owning_class_name, source_path }. The last field is the only one that refers back to the source code, and it's a path, not the content. To read the function's doc block, you still have to parse that file.

Classes

Four things in that output are worth a closer look.

fields includes name, which was never declared with var. It was created by self.name = name inside @new. Reflection reports the class's actual structure, not just what the var lines said.

statics is separate from fields, because a static field belongs to the class, while a field belongs to each instance.

Decorated methods are listed under their @ names. @new and @to_json appear in methods alongside the ordinary methods.

_secret is listed. Reflection can see private members, as explained below.

Each entry in methods is a complete function_info, so info.methods.area.arity works without another call.

Instances

get_props() lists the names of the fields an instance actually has. get_prop(), set_prop(), has_prop() and del_prop() read and write fields by a computed name. They're the reflection equivalents of the getprop family of built-in functions from Chapter 6.

They can't create a field. Classes are sealed, so set_prop() with a name that the class never declared returns false and doesn't change anything.

class_of() works in the other direction. Given an instance, it returns the class it was created from, as the class itself:

typeof() returns the class's name, and two classes with the same name declared in different modules return the same name. Only the class itself can tell them apart, and only the class can be called, passed to class_info() or used as a dictionary key. That's how a library can store something for each class. For example, sql.model stores each model's definition this way.

Reflection Can See Private Members

All of the functions above ignore the leading underscore rule:

This is intentional, and it's the same choice getprop() makes. A serializer has to see every field, or it writes an incomplete record, and a debugger has to see every field, or it shows misleading information. Hiding private fields would defeat the only purpose these functions have.

The lesson here is that reflection is for building tools, not for getting around encapsulation. If code uses get_prop() to read a private field it couldn't otherwise read, it hasn't found a clever loophole. It has written something the next person to read it won't expect.

Modules

module_info() returns a module's name, its path and the members it exports.

import takes its path exactly as written, so it can't import a file whose name the program only learns while it's running. zuri.import_file() can. It imports the module at a given path, just as an import naming that file would, and returns it:

That's how you build a plugin loader: import a directory of modules, check whether each one has a known function, and call the ones that do. A relative path is resolved from the working directory. The module comes from the same cache that import uses, so its top level only runs once, however many times and in whatever way it's imported, and two imports of the same file return the same module, which are equal (==) to each other. sql.migrate loads its migrations this way.

The Garbage Collector

The garbage collector runs automatically as a program allocates memory. gc() runs a full collection immediately:

Every unreachable object is freed before gc() returns, and anything that releases a resource when it's collected does so at that point. For example, an ffi pointer taken over with own() runs its destructor. The freed memory is also returned to the operating system before gc() returns. No program needs to call gc() to work correctly. It's for situations where timing matters, such as releasing native resources at a known point, or a test that checks what garbage collection does. A full collection visits every live object, so calling it in a loop is slow.

Tokens

tokenize() is the first stage. It takes source text and returns a flat list of tokens.

Nothing is filtered out. Comments, doc blocks and newlines are all returned as tokens, and the list always ends with a single Eof token. The parser skips comments and whitespace when it runs, but tokenize() reports everything the lexer saw, which is exactly what a formatter or a syntax highlighter needs.

Each Token has these fields:

Field Description
kind The lexer's own name for the token type, such as 'Identifier', 'Plus' or 'Comment'
line, column The position, starting from 1. column counts characters, not bytes.
start, end The character offsets of the token's exact text
text The exact source text, including any delimiters
value The token's data, where it has any, such as a literal's value, an identifier's name or a comment's content

start and end make it possible to edit source code. They let you recover or replace a token's original text without running the lexer again, which is how a rename tool or a code formatter works.

The Lexer Never Raises an Error

Invalid input doesn't raise an error. Instead, it produces a token of kind 'Error' that describes what went wrong:

That means tokenize() accepts any input at all, which makes it safe to use on a file you didn't write, or on a half-written buffer in an editor. Neither parse() nor compile() works like that. Both raise an error for invalid input, because neither can produce a meaningful result from it.

The Syntax Tree

parse() is the second stage. It turns tokens into a tree.

A Node has a kind, a position and a fields dictionary. The fields contain other nodes, plain lists, plain dictionaries or simple values and nothing else, so you can walk through the tree in the same way, whatever node you're looking at.

Node Positions

A node's position covers all of the source it was parsed from. start and end are character offsets, of the first character and of the character just after the last one, so slicing the source with them gives you the node's own text. line and col give the start of the node, and end_line and end_col give its end, all counted from 1:

A declaration starts at its keyword, so a function starts at def, and its name has its own name_span. That's everything a tool needs to underline a mistake, jump to a definition or select a whole statement.

This is what makes documentation tools possible. Comments and doc blocks are kept in the tree, in their original positions, as nodes of their own:

Most parsers throw comments away. Keeping them is what lets you build a formatter or a documentation generator on top of a parser, rather than only an interpreter.

Bytecode

compile() is the third stage. It turns the tree into VM instructions.

An Instr has an op, a line and a fields dictionary, which is the same structure a Node has, and walk_instrs() and find_instrs() work exactly like the tree walkers.

Notice the AddImm instruction. The compiler included the constant 2 in the add instruction instead of loading it separately. Questions like this can only be answered by the bytecode, and reading it is the most direct way to find out what the compiler actually did with your code:

The power comes before the multiplication, because ** binds more tightly than *. One line of bytecode settles a question that reading the expression might not.

Resolved Operands

Several opcodes only contain an index into the compiler's constant pool, which doesn't tell you much by itself. Instead of making every caller fetch and match up a table of constants, each of these fields comes with the resolved value next to the index:

const_idx is the index, value is the constant it refers to, and dst is the register the result is stored in. The same pairing appears on GetGlobal, GetField, Invoke and the other opcodes like them.

The resolved value of a Closure instruction is a nested function prototype ({ name, arity, variadic, instructions }), whose own instructions are wrapped in the same way, all the way down. So when you compile a file that contains functions, you can see their bodies too, not only the code around them.

Line Numbers Only, Not Columns

Every instruction records the source line it came from, but never a column, because the compiler only tracks lines. Both Token and Node have accurate column information from the lexer, but Instr doesn't.

Checking Source Without Running It

parse() and compile() raise an error at the first sign of invalid source, which is the right behavior for a tool that needs the complete program. A tool that works on source while it's being written, half a statement at a time, needs the opposite: everything that can be read, and a precise description of what's wrong.

parse_partial() reads as much as it can. When a statement fails, the parser reports it, skips ahead to the start of the next statement and continues, so each mistake only affects one statement and is reported once:

Each error is a Diagnostic, which has a message and the same six-part position that a node has, so you can underline it precisely. The statement that failed is still in the tree, with an empty string where its missing name should be.

check() goes one step further. Source that parses successfully is passed on to the compiler, which catches problems that the grammar can't see, such as a break outside a loop or a name declared twice in the same scope:

If check() returns an empty list, the source compiles. Neither function runs any code or raises an error for invalid source, so you can use both of them on whatever an editor's buffer contains at any moment.

Reading Files

Each of these functions has a _file version that reads a file first:

Source string File
tokenize(source) tokenize_file(path)
parse(source) parse_file(path)
compile(source) compile_file(path)
parse_partial(source) parse_partial_file(path)
check(source) check_file(path)

There's also one with no string version: dump_file(path) reads and parses a file, and returns the dump() of every top-level node. It's usually the quickest way to find out what's actually in a file.

Example: Extracting Documentation

Here's the technique that this book's own reference appendices are built with. It takes source code and returns every documented function in it, pairing each declaration with the doc block above it.

The key is that zuri.parse() keeps comments in the tree. A doc block is returned as a DocBlock node of its own, placed as a sibling immediately before whatever it documents. zuri.doc.attach() walks through a list of siblings and pairs each one with the doc block directly above it, and zuri.doc parses the contents of each block into its text and its @ tags:

undocumented doesn't appear in the output. attach() returns it with documented set to false, because there's no doc block above it.

There are several reasons to prefer this approach over scanning the text yourself.

The parser knows what a declaration is. A function named def_handler, a def inside a string literal and a doc block inside a block comment would all confuse a text scan, but none of them confuse the parser.

Parameter names and types come from the actual nodes. A parameter's type_hint node contains its types and whether it accepts nil, so a generated signature matches what the runtime will actually enforce, rather than what the source code seemed to say.

It stays up to date. When the grammar gains a new feature, so does the parser, and a tool built this way keeps working.

The tags are parsed for you. zuri.doc joins a tag's wrapped lines, reads its type and the name it documents, and treats @return as @returns. It's the same parsing that this book's own reference is generated with, so a block is read the same way here as it is there.

Example: A Linter

The other common use for this module is checking code rather than generating something from it. Here's the kind of rule a team builds up over time: report every function that has more than a certain number of parameters.

There are three reasons to do this with the parser rather than with a regular expression over the text.

It can't be fooled by text that looks like code. A function named def_handler, the word def inside a string literal and a commented-out declaration aren't Function nodes, so none of them are counted.

It reports the correct line. node.line comes from the lexer, so the message points to the declaration, however the code around it is formatted.

It keeps working. When the grammar gains a new feature, so does the parser, and a rule written this way doesn't silently stop matching.

The dictionary form of the visitor is important here. Only Function nodes are passed to the handler, so you don't need an if node.kind == ... check, and you can't accidentally match a kind you didn't mean to.

Telling Watch Mode Which Files a Program Reads

zuri run --watch restarts a program when a file it depends on changes. The runtime automatically reports every Zuri source file the program reads. A library that reads other files that affect the program's behavior declares each one with zuri.watch.depends_on(), which is how Wire gets its templates watched:

Outside watch mode, depends_on() does nothing and active() returns false, so a library can always call it. zuri.watch is a separate module from the rest of zuri, so importing it doesn't load the parser and the compiler.

Other Uses

Plugin systems. Load modules from a directory, check whether each one has the function your program expects, and call the ones that do. module_info() lets you check without having to import modules blindly and hope for the best.

Editor tooling. tokenize(), parse_partial() and check() never raise errors, so you can run them on a half-written buffer. Every token and node has start and end offsets, so a rename or reformat can rewrite exact ranges of text, and you can underline every problem check() finds exactly where it is.

Understanding the compiler. Calling zuri.compile() on a snippet is quicker than reading the compiler's source code, and it always matches the version of the compiler you're actually running.

Generating parts of this book. Appendices D and E are generated from libs/ using exactly the techniques described above, and the audit that checks those stubs works the same way.

What You Can't Do

There's no eval(). You can compile source code to bytecode and inspect it, but you can't run a string as code.

Zuri leaves it out for security reasons. eval() blurs the line between data and code, and sooner or later, every program that uses it runs a string it didn't intend to, such as a form field, a query parameter, a configuration value or a webhook payload. As soon as one of those reaches eval(), whoever provided it can run code with your program's full permissions. That code can read your files, open network connections and send your secrets wherever it likes. This is the most damaging class of vulnerability in dynamic languages, and it keeps happening because the dangerous call looks harmless in a code review: a single function, a few characters of input, and nothing in the language warns you.

So Zuri doesn't provide eval(), and every task people usually use it for has a better solution:

Instead of Use
Evaluating an expression entered by a user A dictionary of handlers keyed by the input
Calling a method whose name you computed zuri.reflect.bind_method()
Changing behavior at run time Pass in a function
Turning text into data json.decode()

Each of these does the job with a fixed set of possible outcomes that you can review. That's the difference between a program that handles its input and a program that does whatever its input tells it to.

Classes are sealed, so reflection can't add a method to a class at run time either. Techniques from other languages that depend on monkey patching don't carry over to Zuri. Instead, express the variation as a subclass, or as a function that you pass in.
