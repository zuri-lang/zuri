Testing

A test is a program that runs your program and tells you whether it did the right thing. The test module provides everything you need for this: a way to name and group tests, a way to state what you expect, and a report that tells you which expectation failed and where.

There's nothing to install. Just write import test and you can start.

A First Test

Run it the same way you run anything else:

There are three things to notice right away.

import test { * }. A test file needs describe, it, expect and the rest available directly, not behind a module name. import test on its own also works, and gives you test.describe, test.expect and so on. Use that form in code that isn't itself a test file.

Nothing tells the tests to run. describe and it don't run anything. They build a tree, which runs once the file has finished declaring it, through os.at_exit(). That separation is what lets the framework count the tests before the first one starts, focus on a single test, filter tests by name and run them in random order. run() exists for when you want to pass options or read the result, which Controlling a Run covers.

@{ ... } is a function. it('name', @{ ... }) gives the framework a body to call later, which is why the framework can also choose not to call it.

Expectations

expect(value) returns an object that has every matcher on it.

.not negates any matcher. The same implementation handles both directions, so to_contain and not.to_contain can never disagree about what "contains" means.

Choosing Between to_be and to_equal

to_be uses Zuri's == operator. That already compares lists, dictionaries and bytes by their contents, so it's the right matcher for most values:

However, it compares two instances by identity, unless their class defines @eq, because that's what == does:

to_equal compares structures. It goes through an instance field by field, treats NaN as equal to itself, and can handle a value that contains itself. Use it whenever the objects on both sides of the comparison are created separately.

Setup and Teardown

These are the rules:

  • before_all runs once, just before the first test in its suite that's actually going to run. If every test in a suite was filtered out, before_all never runs, so nothing connects to anything.
  • after_all runs after the last test, and only if before_all ran. It also runs if before_all raised an error, because a setup that failed partway through might already have opened a connection or started a server. Write it so that it can cope with however far the setup got.
  • before_each hooks run starting with the outermost suite, and after_each hooks run starting with the innermost, so teardown undoes setup in the reverse order.
  • after_each runs even when the test failed, which is exactly when you need it.

A hook that raises an error is reported as a hook failure for the test it was preparing, instead of stopping the whole run. If a before_all raises an error, every test in its suite fails, because none of them got the setup they depend on.

Focusing, Skipping and To-Do Tests

As soon as anything is marked with only, everything else is skipped, but still listed, so you can't forget that it's turned on.

A to-do is a test without a body, and it('name') with nothing after it means the same thing. It doesn't count towards anything, and appears in the report as a reminder that stays there after you commit it.

Two options change what a failure means:

failing: true makes the test pass when the body fails and fail when the body passes, so on the day someone fixes the bug, the test tells you. retries runs the body again if it fails, and a test that passes on a later attempt is reported as flaky instead of being quietly counted as a pass.

Running a Test With Several Inputs

Each row becomes a separate test, with its own name and its own entry in the report, so one bad row doesn't hide the others. $0, $1 and so on stand for the row's values, and $# for the row number. describe_each does the same for whole suites, which is how you run one set of tests against several implementations of the same interface.

Test Doubles

mock() gives you a function that records how it was called and does whatever you tell it to.

mock() returns a Mock, and mock.fn is the plain function that you pass to the code under test. The matchers accept either one, so expect(operation) and expect(operation.fn) mean the same thing.

Behavior is used in order. Everything you queue with a _once method runs first, one call each, and after that the standing behavior takes over.

Method Effect
returns(v) / returns_once(v) Returns v
raises(e) / raises_once(e) Raises e
implements(fn) / implements_once(fn) Runs fn with the actual arguments
reset() Forgets the recorded calls
clear_behaviour() Forgets the configured behavior

Spying on an Existing Function

spy_on replaces a function in place and gives you a Mock that both records calls and stands in for the original:

A spy calls the original function unless you tell it otherwise, and it's restored automatically after the test that installed it, even if the test failed partway through. You don't need to undo anything yourself.

It works on a dictionary entry, and on an instance property that holds a function. It doesn't work on a class method or a module function, because Zuri classes can't be changed after they're declared, and a module's members can't be assigned from outside the module. If you want to be able to substitute something in tests, have the code take its collaborators as arguments or store them in properties, which is a good design anyway.

This works because the runtime can redirect everything Zuri writes to standard output. The same mechanism keeps output from passing tests out of the report. Running Several Files

A real project has a whole directory of test files:

zuri test runs all of them:

You don't need to write anything for this. The command finds the tests directory where you ran it, and exits with status 1 if anything failed, so a CI job doesn't need any extra setup either.

Each file runs in a separate process. That's more than an implementation detail, because it gives you several guarantees:

  • A file that loops forever is stopped, and the other files still run. Use --timeout 30s to set how long is too long.
  • A file that crashes, or calls os.exit() partway through, is reported as a file that didn't report back, instead of bringing down the whole run.
  • Global state, modules loaded for their side effects and changes to the working directory never leak from one file to the next.

Files are reported in the order they were found, whatever order they finish in, so --jobs 4 makes a large suite faster without the report jumping around.

A test file doesn't need anything special to run this way. It declares its tests, and you can still run it on its own.

Command-Line Flags

Flag What it does
-j, --jobs <count> The number of files to run at once. auto runs one per CPU. The default is 1.
-t, --timeout <duration> How long a single file can run before it's stopped, such as 500ms, 30s, 2m or 1h, or a plain number of milliseconds. By default, there's no limit.
-b, --bail [count] Stops after this many files have failed. Without a count, stops at the first failure.
-m, --match <pattern...> File name patterns to run, instead of *.zu
-i, --ignore <pattern...> File name patterns to skip, instead of _*, .* and index.zu
--no-recursive Only runs the files directly inside the directory
-e, --env <assignment...> Sets extra environment variables for every test process, written as KEY=VALUE
-l, --list Prints the files that would run, one per line, and stops

--bail and the two pattern flags take every word that follows them, so put the file name before them, or end the list with --:

For the same reason, a count for --bail has to be attached, as in --bail=3, because a count written as a separate word can't be told apart from a file name.

Running a Suite Yourself

conduct() is the function that zuri test is built on, and a project that wants to control the run itself can call it directly. When you pass a directory to zuri run, it runs that directory's index.zu, so a single file lets you run the suite with zuri run tests:

It accepts the same settings as the command-line flags, as a dictionary, and returns the run's results instead of only reporting them. conduct leaves index.zu out when it looks for test files, and never runs the script that called it, so the index can't end up running itself.

Controlling a Run

Call run() yourself when you want to change how the run behaves, or to read the results. It takes a dictionary of options, and calling it replaces the automatic run, so nothing runs twice.

These are the options you're most likely to use:

Option What it does
filter Only runs tests whose full name contains this text, or matches it as a regular expression
bail Stops after this many failures
shuffle / seed Runs the tests in random order, and lets you reproduce that order later
reporter One of spec, dot, tap, junit, json, ndjson or silent
exit Exits the process with the run's status when it finishes

You can also set filter and reporter with ZURI_TEST_FILTER and ZURI_TEST_REPORTER, which lets you point the same command at a single test without editing the file.

Shuffling is worth turning on deliberately. Tests that only pass because an earlier test left something behind are a real and common problem, and running them in a different order every time is how you find them:

The seed is printed along with the summary, and passing it back reproduces exactly the same order.

Running Tests in CI

You don't need to add anything. A test file exits with 0 when everything passed and 1 when something didn't, whether or not it called run().

If your CI system needs a machine-readable report, { reporter: 'junit' } writes JUnit XML to standard output, and { reporter: 'tap' } writes TAP version 14.

Writing Your Own Reporter

The runner doesn't know anything about output. It walks the tree of tests and calls methods on a reporter, and every method has a default that does nothing:

The objects passed to the reporter are the same ones the built-in reporters receive: Case, Suite, Failure and Summary, which are documented in test.result.

Two Things to Keep in Mind

A test's timeout is checked after the body returns. Zuri runs synchronously, so a test runs to completion and then its time is checked. That catches a test that has become too slow, but it can't stop one that hangs. Handling a hang needs a process boundary, which is exactly what conduct puts around each file, and why its timeout is the one that's enforced.

All the tests in a file share the same interpreter. Reset whatever you change in before_each, and use shuffle to find out whether you've missed anything.
