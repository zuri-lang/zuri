4.1 · Learning the Language

Strings

A Zuri string is UTF-8 text. Indexing, slicing and length() all work in characters rather than bytes, so a string of emoji behaves the way you'd expect.

You'll probably work with strings more than any other type, so this section starts with how to write them (quoting, escape sequences and interpolation) before moving on to what you can do with them.

String Literals

A string literal is written in single or double quotes:

The two styles are identical. Unlike in some other languages, they don't mean different things. Both process escape sequences, both support interpolation, and both can span several lines. The only difference is which quote character ends the string:

Choose whichever one saves you from escaping. A string that contains an apostrophe is easiest to write in double quotes, and one that contains a double quote is easiest in single quotes:

Most Zuri code, including the whole standard library, uses single quotes by default and switches to double quotes when the content needs it.

Multi-line Strings

A string literal can contain newlines directly. There's no special triple-quoted syntax and no line continuation character:

Everything between the quotes is part of the string, including indentation. If you indent a long string inside a function, the leading spaces on each line end up in the string too. For that reason, code that builds indented text is usually better off assembling it with join() than writing one long literal.

Escape Sequences

A backslash starts an escape sequence. These are all of them:

Escape Produces
\0 The null character, U+0000
\a The alert (bell) character, U+0007
\b Backspace, U+0008
\t Horizontal tab, U+0009
\n Line feed, U+000A
\v Vertical tab, U+000B
\f Form feed, U+000C
\r Carriage return, U+000D
\\ A single backslash
\' A single quote
\" A double quote
\${ A literal ${, with no interpolation
\xNN The byte with the hexadecimal value NN
\uNNNN The code point U+NNNN
\UNNNNNNNN The code point U+NNNNNNNN

The three numeric forms take exactly the number of hex digits shown (two, four and eight), and the digits can be uppercase or lowercase:

\u covers code points up to U+FFFF. Anything higher, such as emoji, most historic scripts and mathematical alphanumerics, needs \U with eight digits. Pad the value with leading zeros to fill them.

Unknown Escape Sequences

A backslash followed by a character that isn't in the table above is not an error, and it isn't silently removed either. Both the backslash and the character stay in the string:

The first line comes through unchanged. \d and \w aren't escape sequences, so both backslashes are kept, and that's why you can write regular expressions as ordinary strings.

The second line doesn't. \t is an escape sequence, so C:\temp becomes C: followed by a tab and emp. \n is an escape sequence too, so \notes becomes a newline followed by otes. That's two silent substitutions in a single path. The rule is simple but easy to forget: unknown escape sequences are left alone and known ones aren't, and nothing in the way you write them tells you which is which.

Windows paths and regular expressions are where this usually causes trouble. In both, double the backslashes:

Escaping Quotes

You only need to escape the quote character that would otherwise end the string:

Escaping the other quote character doesn't do anything useful. Since it isn't a known escape sequence, the backslash stays in the result:

That's another reason to pick the quote style that lets you write the text without escaping anything.

Interpolation

${...} inside a string evaluates the expression between the braces and inserts its text into the string:

Interpolation works with both quote styles, and it's how most Zuri code builds strings. Two sections from now, we'll look at +, which does the same job with more punctuation.

Using Any Expression

The braces can contain any expression, not just a variable name. Arithmetic, method calls, indexing, comparisons and conditional expressions all work:

Look at the third line. The quotes inside ${...} are the same quote character that started the string, and it still works. That's because the expression inside the braces is read as code, not as part of the text. You don't need to switch quote styles or escape anything to put a string literal inside an interpolation.

How Values Are Displayed

Interpolation displays a value the same way echo does:

There's one important exception that catches almost everyone at least once. Interpolating a class instance doesn't call its to_string() method:

You have to call the method yourself. The same applies to 'text ' + p. Neither interpolation nor + will call a method for you to get the text. If you want to_string() to run, call it. echo is the exception, through @to_string(), which is covered in Decorated Methods.

Writing a Literal ${

A backslash in front of ${ prevents interpolation, and the backslash itself is removed:

The escape sequence is a backslash, a dollar sign and a {. \\ is a separate escape sequence, so \\${x} gives you a backslash followed by the value of x. Anywhere else, \$ is an unknown escape sequence and keeps its backslash, which is how a regular expression can match a literal dollar sign:

Combining Strings

Concatenation with +

+ joins two strings together:

When one side is a string, the other side is converted to text first. This works whichever side the string is on, and for all built-in types:

Look at the second line again. 5 + 'n' gives '5n'. It's not an error, and it's not arithmetic. A string on either side turns the whole expression into concatenation. Keep this in mind when a value comes from a source you don't control:

The first line is string concatenation and the second is arithmetic, and nothing in the expression tells you which one you'll get. When a value needs to be a number, convert it as soon as it enters your program.

The one type that doesn't convert in a useful way is a class instance:

Concatenating the instance directly would give you <instance of Point>, for the same reason as with interpolation: Zuri doesn't call to_string() for you.

Concatenation or Interpolation?

Both produce the same string, so choose whichever is easier to read:

Interpolation is usually better when there's more than one value to insert. The literal text stays in one piece, you don't end up with lots of quotes, and you can't accidentally lose a separator between two + signs. Use + when you're joining just two pieces, or when one of them is a variable that already holds a complete string.

Repetition with *

* repeats a string a given number of times:

The second line shows why this operator is useful. Separators, horizontal rules, indentation and padding each become one short expression instead of a loop.

Here are the exact rules for the count:

  • A count of 1 returns the string unchanged.
  • A count of 0 returns an empty string.
  • A negative count also returns an empty string instead of raising an error.
  • A fractional count is truncated toward zero, so * 2.7 repeats the string twice.

Watch out for the negative case. '-' * (width - label.length()) quietly produces nothing when the label is longer than the width, and there's no error to tell you. When the count is calculated, clamp it:

Unlike +, the order matters for repetition. The string has to be on the left:

Building a String From Many Pieces

When you have more than a few pieces, neither operator is a good fit. Collect the pieces in a list and call join():

join() is a method of the separator, not of the list. It converts each element to text as it goes, so a list of numbers can be joined just as easily as a list of strings:

join() also puts the separator only between elements, never at the beginning or end. That's exactly the part that hand-written loops tend to get wrong for the last item.

Inspecting Strings

index_of() returns -1 when there's no match. It accepts an optional second argument that sets where the search starts.

last_index_of() searches from the end instead, which is what you want when the separator you care about is the last one:

Both methods take a second argument, and in both cases it limits where a match can start. Together, they split a string at an index: for any n, index_of(str, n) finds the first match at or after n, and last_index_of(str, n) finds the last match at or before n.

There's also a set of methods that test character classes. Each one returns true when every character in the string matches:

The full set is is_alpha, is_alnum, is_number, is_lower, is_upper and is_space, along with is_empty.

Changing Case

capitalize() converts the first character to uppercase and the rest to lowercase. title() does the same for every word.

When you compare text entered by users, use case_fold() instead of lower(). Case folding is the Unicode operation designed for case-insensitive matching, and it handles cases that simple lowercasing gets wrong:

Trimming and Padding

Called without an argument, all three methods remove whitespace: spaces, tabs, newlines, carriage returns, vertical tabs and form feeds. If you pass a string, they remove any of the characters in it, in any order, so '-=hi=-'.trim('-=') gives hi.

lpad and rpad take a target width and an optional fill character, which defaults to a space. If the string is already as wide as the target or wider, it's returned unchanged.

Splitting and Joining

join is a method of the separator, not of the list. to_list() splits a string into single characters. lines() splits on newlines, and handles both \n and \r\n.

Regular Expressions

Zuri uses PCRE2 for regular expressions, the same engine used by PHP, R and many other tools. It's the full library, not a subset, so named groups, backreferences, lookahead, lookbehind, atomic groups, possessive quantifiers, conditionals and recursion all work as the PCRE2 documentation describes.

This section explains how to write a pattern in Zuri, which methods accept patterns, what each modifier does, and the few places where Zuri behaves differently from what you might expect. It doesn't teach regular expression syntax itself, but any PCRE or Perl reference applies as it is.

Writing a Pattern

A pattern is an ordinary string. Its first character must be a non-word character, and the same character closes the pattern. Any modifier letters go after the closing delimiter:

A non-word character is anything other than a letter, a digit or an underscore. A forward slash is the usual choice, and it's what every example in this book uses, but you can pick a different delimiter. That's useful when the pattern itself contains a lot of slashes:

Because a pattern is a string, Zuri's own escape rules are applied to its backslashes first. In practice, this rarely causes problems, because \d, \w, \s, \b and \S aren't escape sequences in strings and are passed through unchanged. The exceptions are the letters that are escape sequences: \t, \n, \r, \f, \v, \a, \b, \0, \x and \u. \t and \n mean the same thing in both strings and patterns, so they're harmless. The one that will catch you out is \b, which means a word boundary in a pattern but a backspace in a string:

Whenever a pattern needs \b, write it with a double backslash.

Plain Strings Are Matched Literally

All of the methods in this section also accept a plain string, which they treat as a literal substring rather than a pattern:

The first call replaced the single period. The second call compiled . as a pattern, where it means "any character", so it replaced all three characters.

The only thing that decides this is whether the string looks like a delimited pattern. If you're working with text from elsewhere that might happen to look like one, pass false as the third argument to replace() to turn off pattern handling:

With false, the delimiters are matched as ordinary characters.

Methods That Accept Patterns

There are exactly five:

Method What it does with the pattern
match(pattern) Returns the first match and its groups, or false
matches(pattern) Returns every match, grouped by capture group
replace(pattern, with, use_regex) Replaces every match
replace_with(pattern, callback) Replaces every match with the result of a function call
split(pattern) Splits the string at every match

All the other methods, such as contains(), index_of(), count(), starts_with(), ends_with() and trim(), only accept literal strings. If you pass them something that looks like a regular expression, they search for those exact characters:

All three calls searched for the six-character string /[0-9]/, which doesn't appear in a1b. If you need a pattern in a case like this, use match() instead.

match() and matches()

match() finds the first match and returns it in a dictionary under the key 0. When nothing matches, it returns false, not nil:

Both false and nil are falsy, so if s.match(p) { ... } works as expected. Comparing the result with nil doesn't, and that's the most common regular expression mistake in Zuri code.

The dictionary also contains the pattern's capture groups, each under its number, and named groups under their names as well. A group that doesn't take part in the match is nil:

matches() finds every match and groups the results by capture group. Key 0 holds the full matches, key 1 holds the matches for the first group, and so on. Each value is a list, and the lists line up with each other:

In the second result, the first match is a1, with groups a and 1, and the second match is b2, with groups b and 2. Read down each list, not across them.

When nothing matches, matches() returns {0: []} instead of false. Since the two methods behave differently here, check the result of matches() by calling is_empty() on key zero:

Capture Groups in a Replacement

In replace(), you refer to a capture group with $1, $2 and so on:

Don't write ${1}. The braced form is Zuri's own string interpolation, and it's evaluated before replace() sees the string. The expression 2 evaluates to the number two, so by the time the replacement string reaches replace(), it's already '2, 1':

Always use the plain $1 form. This is one of the few places where Zuri's interpolation syntax clashes with another syntax, and when it goes wrong, there's no error to warn you.

Named Groups

Named groups are supported in patterns, because PCRE2 supports them:

However, the results are keyed by position, not by name. A group's name documents what it's for and lets a backreference such as \k<first> refer to it, but it doesn't change the keys in the result. To find the group you want, count the groups.

Modifiers

Modifier letters go after the closing delimiter, in any order and combination. For example, /[a-z]+/mi is both multi-line and case-insensitive.

Modifier Effect
i Case-insensitive matching.
m Multi-line mode: ^ and $ match at the start and end of every line, not just the start and end of the string.
s Dot-all mode: . also matches newlines.
x Extended mode: whitespace in the pattern is ignored unless escaped, and # starts a comment that runs to the end of the line.
u Unicode mode: \d, \w, \s and similar classes match Unicode characters instead of only ASCII.
U Ungreedy mode: quantifiers are lazy by default, and a ? after one makes it greedy.
A Anchored mode: a match is only accepted if it starts exactly where the search started.
J Allows two capture groups in the same pattern to have the same name.

Here's each of them in use:

Compare the last two results. The pattern matched when the text was at the start of the string and failed when it wasn't, which is what A is for. Without A, the second one would have matched at position one.

u deserves a closer look too. Without it, \w only matches ASCII, so é isn't a word character. With it, Unicode properties apply, and é is a word character. Matching is always done per character rather than per byte, so positions are correct on text with multi-byte characters, with or without u.

Differences From PCRE2

PCRE2's D (dollar end only) modifier has no effect in Zuri. $ always matches before a trailing newline as well as at the very end of the string, and you can't change that. The D letter is accepted rather than rejected, so a pattern that uses it still compiles and runs. It just doesn't do anything.

The same goes for any other modifier letter that Zuri doesn't recognize. It's accepted and ignored instead of raising an error. That means a typo in a modifier goes unnoticed, so keep it in mind if a pattern behaves as though one of its flags isn't set.

All the other modifiers in the table are supported and behave as the PCRE2 documentation describes.

Invalid Patterns

If PCRE2 can't compile a pattern, Zuri raises an error that includes the pattern and PCRE2's own explanation:

Patterns are compiled once and then reused, so using the same pattern repeatedly in a loop has no extra cost after the first time.

Converting Strings

to_number() accepts an optional base. ord() takes a string of exactly one character and returns its code point, and chr() converts a number back into a character.

to_number() Never Fails

This is the one conversion rule you should memorize. to_number() never raises an error, and it never returns NaN. It reads the first number in the string, and if the string doesn't contain a number at all, the result is zero:

Look at the last three lines. Anything around the number is ignored, so '12abc' gives 12, the spaces in ' 7 ' don't matter, and only the first number is read, however many follow it.

This can work for you or against you. '3 apples' giving 3 is usually what you want, but '2026-09-16' giving 2026 usually isn't. A number starts at a digit, or at a sign or decimal point immediately before a digit, so '-5' is negative five, while 'a - 42', where the sign is separated from the digits, is 42.

Since there's no error to catch and no special value to check for, an empty form field and a field containing '0' give you the same number, and so do 'eighty' and '0'. When the difference matters, check the text before you convert it:

is_number() is stricter than its name suggests. It's only true for a string made entirely of digits, so '3.5' and '-5' both fail. For anything other than unsigned integers, a regular expression is the more reliable check.

Iterating Over a String

Strings are iterable, one character at a time, and you can use the same four approaches that work for lists.

for, One Character at a Time

This is the approach to use by default. Each ch is a one-character string, not a code point number. Use ord() if you need the number.

for With Two Variables, for the Position

The key comes first and the value second. For a string, the key is the position of the character.

iter, When You Need Control Over the Position

s[i] indexes by character rather than by byte, so this works correctly on text that isn't ASCII. Use iter when you need to skip ahead, go backward, or look at s[i + 1] inside the loop.

each(), With a Function

As with the other types, the function receives the value first and the index second. Note that this is the opposite of the order used by for.

each_line() and lines(), for Line-Based Text

each_line() calls a function once for each line, and lines() gives you all of the lines as a list, so you can loop over them, filter them or count them. Both split on \n and \r\n, so they work with files written on any platform.

Comparing Strings

== compares two strings by value, which is nearly always what you want:

The ordering operators are different. <, <=, > and >= only work with numbers, and using one to compare two strings raises a TypeError. Use compare() instead, which returns -1, 0 or 1:

A three-way result like this is what a sort comparison function needs. compare() compares strings by code point, so the result is stable and doesn't depend on the locale.

Strings Are Immutable

Every method in this section returns a new string. None of them change the string in place:

It's important to keep this in mind, because it leads to the most common string mistake of all:

The first trim() call created a trimmed string and then threw it away. Assign the result to a variable, or chain another call onto it.

Because strings are immutable, you never need to copy one before passing it somewhere. Nothing you pass a string to can change the string you still have.
