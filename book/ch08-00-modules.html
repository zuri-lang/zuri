The Module System

A module is a .zu file. It runs at most once per program, it has its own global namespace, and nothing it declares is visible anywhere else until another file imports it.

That's all there is to the model. The rest of this chapter covers the syntax and the rules for finding modules.

Importing a Module

import name makes the module available under that name. Use a dot to access what's inside it.

Importing Specific Members

The members you name are bound directly, and the module name itself isn't bound.

Relative Imports

A path that starts with . or .. is resolved relative to the directory of the file that contains the import, and Zuri never looks for it anywhere else.

Each .. goes up one directory, so .. .. goes up two, and .. .. .. goes up three. You can also write the dots together, as in ....shared.config, which means the same thing: every two dots in a row go up one directory. zuri fmt keeps whichever form you used.

Each part of the path is resolved the same way as a bare name: Zuri tries name.zu first, then name/index.zu. So import .helpers finds either helpers.zu or helpers/index.zu, and import .models.user finds models/user.zu or models/user/index.zu, where models is a directory in both cases.

You can't tell from the import which of the two it found, and that's what allows a module to grow into a package. If you split helpers.zu into helpers/index.zu and a few other files, every import .helpers keeps working without changes.

Inside a package, always import a sibling module with import .sibling, not with the full path from the project root. If you write import myapp.models.user inside myapp/models/, Zuri searches the library path for it and won't find anything.

Packages

A directory that contains an index.zu is a package. Importing the directory runs its index.zu:

The same rule applies to zuri run pkg on the command line, which is why a package can be run as well as imported.

Resolving Bare Names

For an import with no leading dot, such as import http, Zuri looks in these places, in order:

  1. .zuri/libs/http in the project
  2. $ZURI_ROOT/libs/http, or libs/http next to the zuri executable, which is the standard library
  3. A built-in native module named http
  4. $ZURI_HOME/libs/http, the packages installed for your user, which are in ~/.zuri/libs unless you set ZURI_HOME to something else

At each step, http.zu is tried first, and then http/index.zu.

The project is the nearest directory containing a project.toml, found by searching upward from the script given to zuri run, or from the working directory for a command or the REPL. A program run from anywhere inside a project imports that project's packages, and a program that isn't in a project uses .zuri/libs in the working directory. The project is found once, when the program starts, so changing directory while it runs doesn't change where imports come from.

zuri install puts packages in .zuri/libs, and Packages and Nyssa covers it in full. The first step in the search is also what makes vendoring possible. A file you put in .zuri/libs/ takes priority over a standard library module with the same name:

Modules Run Only Once

A module's top-level code runs the first time the module is imported, and never again. Every later import of the same file gets the same module object:

There's one line of output for three imports. Modules are identified by their canonical file path, so two different relative paths to the same file refer to the same module.

That makes a module's top level the natural place for setup that should happen exactly once, such as opening a connection pool, reading a configuration file or registering handlers.

Circular Imports

Circular imports work. A module is registered before its body runs, so when b.zu imports a.zu while a.zu is still loading, b gets the partly loaded module instead of looping forever:

The output shows the catch: b finished loading before a did, so anything b reads from a at its top level doesn't exist yet. Reading it inside a function is fine, because by the time the function runs, a has finished loading.

If a module fails while it's loading, it's removed from the cache instead of being left half loaded, so a later import really does try again.
