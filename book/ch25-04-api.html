25.4 · The Capstone

The JSON API

The API has six routes. Each one reads from or writes to the board and returns JSON, and none of them handle errors.

The Routes

The Structure of the File

register(server, board) takes the server and the board as arguments instead of importing them. That's what lets the same routes work with a different board, such as a temporary one in a test or one filled with sample data for a demo, and it keeps any decision about where the data is stored out of this file.

Listing Tasks, With an Optional Filter

A single route answers two questions: what are all the tasks, and what are all the tasks in a particular column?

query_param('column', nil) provides the fallback, and the check is column == nil instead of if column. That distinction matters, because a query string of ?column= produces an empty string, which is falsy but present, and an empty column name should be rejected by in_column(), not silently treated as "no filter".

The response includes summary alongside tasks, because a client that displays a board needs both, and making it ask separately would mean two requests for one screen.

Fetching a Single Task

This is a single line, and it can fail. board.get() raises a NotFoundError for an unknown ID, and this handler does nothing about it, for reasons explained in the section below.

Creating a Task

request.json_body() returns nil for a request with no body, or with a body that isn't JSON. or {} turns that into an empty dictionary, so body.get('title', nil) works either way, and a missing title becomes the model's problem, which is where the message about it already lives.

The 201 is the second argument to response.json(). A newly created resource shouldn't get a 200, and getting it right only takes one argument.

The handler returns task.to_view() rather than task, for the reason explained below.

Updating and Deleting Tasks

The PATCH handler passes the decoded body straight to board.update() without filtering it. That's safe, because update() only looks at the three keys it knows about, title, notes and column, using contains(). So a body containing {"id": "hacked"} doesn't change anything. The list of allowed keys is kept in the model, once, instead of in every route that accepts a body.

DELETE returns a body instead of an empty 204, so that a client that parses every response as JSON doesn't need a special case for one route.

Why the Handlers Don't Handle Errors

This is the main point of this section, and it's easiest to see if you count: there are six handlers, and not one catch block.

board.get() raises a NotFoundError for an unknown ID. board.add() and board.update() raise a TaskError for an invalid title or an unknown column. None of the handlers catch either error, and that's why each one is only one to five lines long.

The middleware in the next section catches both errors and turns them into a 404 and a 422. Only one place in this application knows which domain error corresponds to which status code, and it isn't a route.

Think about the alternative for a moment. Six handlers would each wrap their call to the board in a catch, choose a status code and format an error response. That's thirty or so lines of duplicated code, and a seventh route added next month would probably get one of those details slightly wrong.

Notice also the two imports at the top of the file. TaskError and NotFoundError are imported but never used again in this file. They're there because the module that catches them needs them to be re-exported through routes. That's the module system doing its job, and Chapter 8 explains why the @ matters there.

Using to_view() for Responses

Every response sends the result of to_view(), never the Task itself.

That one habit means the structure of the API is decided by Task, in a single method, instead of depending on however the object happens to be laid out internally. If you add a private field to Task tomorrow, the API still returns exactly what it returned yesterday.

It's also why the responses include created_on and is_done, which aren't stored anywhere. to_view() calculates them, so every client gets a formatted date and a boolean without having to work them out.

Trying the API

The last two requests are the interesting ones. You get a 422 with a field, and a 404 with a message, from handlers that never mention status codes at all.
