17.1 · The Big Modules

Changing the Schema

db.schema reports what is in a database, and it changes it too. A table is described once, in Zuri, on a Blueprint, and the adapter turns the description into its own engine's statements. The same description creates the same table on SQLite, PostgreSQL, MySQL and MariaDB.

Creating a Table

create_table() hands its body a Blueprint, and creates the table once the body returns. Written with its type, as below, the body's table is one an editor completes the blueprint's methods on:

Every column method returns the column, and every modifier returns it again, so a column is described in one chain. timestamps() adds created_at and updated_at, each defaulting to the moment a row is inserted.

{ if_not_exists: true } as a third argument leaves a table that is already there exactly as it is, indexes included. It is what a library creating its own table on every start passes.

Each type is the same kind of value on every engine, stored the way that engine stores it best:

string() is 255 characters when no length is given. An id() is never handed out twice, even after the row holding the highest one is deleted. A decimal() on SQLite holds at most fifteen significant digits, the most a double keeps exactly, and a larger precision is refused there with NotSupportedError. references(name, table) is a big integer referring to another table's id(), with its foreign key.

The modifiers:

exact() makes a text column compare byte for byte on every engine: 'Ada' and 'ada' are two values, and so are 'é' and 'e'. SQLite compares that way already; PostgreSQL is given the "C" collation and MySQL and MariaDB utf8mb4_bin, whose default collations treat case, and on MySQL accents, as the same. A column holding a key, where two values differing only in case must not collide, wants it.

Keys and Indexes

A key or index on one column is a modifier on it. One spanning several columns is declared on the table:

Indexes, unique indexes and foreign keys are named for their table and columns: posts_author_id_index, posts_slug_unique, posts_author_id_foreign. A second argument names one otherwise. Since the name is known, an index is dropped by its columns as readily as by its name. A name past 63 characters, the longest PostgreSQL keeps, is shortened and finished with a hash of the whole, so it stays unique.

Foreign keys are always written as table constraints. MySQL parses a references clause written on a column and then ignores it, so a key declared that way exists on the other engines and not there; declared on the table, it exists on every one.

The actions a foreign key takes when the row it refers to is deleted or has its key changed are 'cascade', 'restrict', 'set null', 'set default' and 'no action', the last being what a key does when it names none.

Its indexes stay as they are.

Dropping a column drops every index, unique index and key it is part of, on every engine. A required column with no default can only be added to a table with no rows, since there is nothing to fill them with; on a table with rows the engine reports NotNullViolation.

How a Change Runs

A change made with no transaction open runs as a whole. On SQLite and PostgreSQL that means a transaction of its own, so an alteration whose third step fails leaves the first two undone with it. MySQL and MariaDB commit at every statement that changes a table's definition, whatever transaction is open, so there each statement stands once it has run.

SQLite Builds a Table Again

SQLite's ALTER TABLE adds and renames columns and very little else. For anything more, changing a column, adding or dropping a key, dropping a column an index or key uses, the adapter does what SQLite's own documentation lays out: it builds a new table with the changed definition, copies the rows across, drops the old table and renames the new one into its place, then puts back the indexes and triggers and carries over the sequence behind the id(). The new definition is the old one with only the changed parts rewritten, read from the table's own create table text, so whatever else it declared, checks and collations included, comes through as it was.

Dropping the old table deletes from it first, and with foreign keys enforced, that delete runs the on delete of every table referring to it: a rebuild with them on would take every referring row with it. So a rebuild runs only with enforcement switched off, which SQLite allows only outside a transaction. A change made with no transaction open switches it off around itself, and checks every foreign key before it commits; sql.migrate does the same around every migration.
