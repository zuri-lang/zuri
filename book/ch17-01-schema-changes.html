17.1 · The Big Modules

Changing the Schema

db.schema can change a database as well as describe it. You describe a table once, in Zuri, using a Blueprint, and the adapter turns that description into the right statements for its engine. The same description creates the same table on SQLite, PostgreSQL, MySQL and MariaDB.

Creating a Table

create_table() passes a Blueprint to its body, and creates the table when the body returns. If you annotate the body's table parameter with its type, as below, your editor can complete the blueprint's methods:

Every column method returns the column, and so does every modifier, so you can describe a column in a single chain. timestamps() adds created_at and updated_at columns, each defaulting to the time the row was inserted.

If you pass { if_not_exists: true } as a third argument, a table that already exists is left exactly as it is, indexes included. A library that creates its own table every time it starts would pass this.

Column Types

Each type holds the same kind of value on every engine, stored in whatever way suits that engine best:

string() has a length of 255 characters if you don't specify one. An id() value is never reused, even after the row with the highest ID is deleted. On SQLite, a decimal() can hold at most 15 significant digits, which is the most a double can store exactly, and a larger precision raises NotSupportedError there. references(name, table) creates a big integer column that refers to another table's id(), along with its foreign key.

The modifiers are:

exact() makes a text column compare values byte by byte on every engine, so 'Ada' and 'ada' are different values, and so are 'é' and 'e'. SQLite already compares this way. On PostgreSQL, the column gets the "C" collation, and on MySQL and MariaDB, utf8mb4_bin, because their default collations treat uppercase and lowercase letters as equal, and on MySQL, accented and unaccented letters too. Use it for a column that holds keys, where two values that only differ in case must not clash.

Keys and Indexes

A key or index on a single column is a modifier on that column. A key or index on several columns is declared on the table:

Indexes, unique indexes and foreign keys are named after their table and columns, such as posts_author_id_index, posts_slug_unique and posts_author_id_foreign. You can pass a second argument to choose a different name. Because the name is predictable, you can drop an index by its columns just as easily as by its name. A name longer than 63 characters, which is the longest PostgreSQL allows, is shortened and ends with a hash of the full name, so it stays unique.

Foreign keys are always written as table constraints. MySQL parses a references clause on a column and then ignores it, so a key declared that way would exist on the other engines but not on MySQL. Declared on the table, it exists on every engine.

The actions a foreign key can take when the row it refers to is deleted, or has its key changed, are 'cascade', 'restrict', 'set null', 'set default' and 'no action'. The last one is what a key does if you don't specify an action.

Changing a Table

alter_table() describes changes on a blueprint and applies them in the order you describe them:

A column described in alter_table() is added to the table. change() turns the description into a change to an existing column instead. The column takes the type, nullability, default and comparison you describe, whatever it had before, so you need to describe the column in full, including nullable() where it applies. Renaming and Dropping Tables

A renamed table keeps its indexes under their existing names, and foreign keys that refer to it are updated to follow it. If another table refers to a table through a foreign key, dropping it is rejected on every engine, instead of deleting the rows that refer to it as well:

How Changes Are Applied

A change made outside a transaction is applied as a single unit. On SQLite and PostgreSQL, that means it runs in a transaction of its own, so if the third step of an alteration fails, the first two are undone as well. MySQL and MariaDB commit every statement that changes a table's definition, whatever transaction is open, so on those engines each statement is permanent once it has run.

A change made inside a transaction becomes part of it, and on engines that support it, it's rolled back along with the transaction:

How SQLite Rebuilds a Table

SQLite's ALTER TABLE can add and rename columns, but not much else. For anything more, such as changing a column, adding or dropping a key, or dropping a column that an index or key uses, the adapter follows the procedure in SQLite's own documentation. It creates a new table with the changed definition, copies the rows across, drops the old table and renames the new one to take its place. It then recreates the indexes and triggers and carries over the sequence behind the id() column. The new definition is based on the table's own create table statement, with only the changed parts rewritten, so everything else it declared, including checks and collations, is kept.

Dropping the old table deletes its rows first, and when foreign keys are enforced, that delete triggers the on delete action of every table that refers to it. With enforcement on, a rebuild would therefore delete every row that refers to the table. So a rebuild only runs with enforcement turned off, which SQLite only allows outside a transaction. A change made outside a transaction turns enforcement off for its own duration, and checks every foreign key before it commits, and sql.migrate does the same for every migration. A rebuild requested inside a transaction while foreign keys are enforced raises a NotSupportedError instead of putting the rows at risk:
