Parsing the Command Line

A program started from a shell receives a list of strings and nothing else. Whatever the user meant by -v, --output report.csv or commit -m "fix the thing" has to be worked out from that list, and that's where command-line programs tend to slowly fall apart. The first version reads os.args and checks a few positions. The second adds a flag, and the checks become a chain of conditions. By the fourth version, nobody can say what -vo does without trying it, the help text no longer matches the code that reads the flags, and a typo quietly does something else instead of reporting an error.

The args module takes a declarative approach instead. You declare which options exist, what type of value each one takes and which ones are required. The module works out what the user typed, converts and validates the values, generates the help text from the same declarations, and rejects anything that doesn't match.

A First Parser

It takes three lines of declarations and one call:

parse() without an argument reads the real command line, which is what a program normally does. Throughout this chapter, it's given an explicit list instead, because that's also how you test a parser, and because an example in a book can't depend on how you ran it.

What parse() Returns

It always returns a dictionary with three keys:

options holds every option that was given on the command line or has a default. command is nil, or the subcommand that was given. indexes holds the positional arguments, in the order they were declared. The three are independent, so a program can use one of them and ignore the others.

A declared positional argument that wasn't given and has no default stays in indexes as nil, so the argument after it is still at the index where it was declared, instead of moving down one place.

Options

An option is declared by its long name. The short name is optional, and so is everything else:

--output and -o are the same option.

Passing a Value

A long option takes its value either as the next argument or attached with =. The two forms mean the same thing:

The argument is split at the first =, so --output=a=b writes to a=b instead of losing half of the name, and --output= sets the value to an empty string instead of leaving it missing. The attached form is also the only way to pass a value that starts with a dash, because in --output -5, the parser reads -5 as an option:

A short option only takes its value as the next argument, as in -o out.csv, never -oout.csv or -o=out.csv. A short option token is a group of single-character flags, and neither = nor the letters of a value are flags.

Types

The type determines what the string is converted to, and whether the option takes a value at all.

Constant The option takes The result is
args.NONE Nothing true when the option is present
args.STRING A value The string itself
args.INT A value A whole number
args.NUMBER A value A number, which can have a fractional part
args.BOOL A value A boolean
args.LIST A value, and can be repeated A list of strings
args.CHOICE A value from a fixed set The string, or the value it maps to
args.OPTIONAL A value, if there is one The string, or true

NONE is the default, and it's a plain flag. BOOL takes an explicit value, and it accepts every spelling a user is likely to try:

1, true, yes, y and on all mean true, and 0, false, no, n and off all mean false.

Defaults and Missing Options

value is the option's value when it isn't given on the command line:

If an option has no default and isn't given on the command line, it isn't in the dictionary at all. That's how you tell a flag that was left out from one that was set to false, and it's why verbose is missing from the first line instead of being false. Use options.contains('verbose') to check, or give the option a default so you don't need to.

Requiring an Option

If the option is left out, the program stops with error: required option --output is missing, followed by the usage line, and exits with status 1. Nothing else runs.

Positional Arguments

Positional arguments are declared with add_index, and they're filled in the order they were declared:

They accept type, choices, value, required and metavar, just as options do. A positional argument that wasn't declared is an error rather than being silently ignored, which means a mistyped flag fails with an error instead of being taken as a file name.

Subcommands

A program that does several different jobs can give each one a name and its own options:

add_command returns the command, so you can chain its options directly after it. A command's options are added to the same options dictionary as the global options, and command.name tells you which job the user asked for.

The order matters, and it's the same order every tool like this uses: the parser's own options come before the command name, and the command's options come after it. notes -v list works, but notes list -v doesn't, because after list, the parser is reading list's options, and -v isn't one of them.

Commands That Take a Value

A command can take a single value directly, in the way that git commit -m takes a message:

The value comes straight after the command name, before the command's own options. metavar is the word the help text shows in place of the value, so the usage line reads notes add <text> instead of notes add <value>.

End of Options

A -- on its own ends option parsing. Everything after it is a positional argument, even if it starts with a dash:

This is how a program can pass arguments on to another program without needing to understand them.

Reading Arguments From a File

An argument that starts with @ is replaced by the contents of that file, with one argument per line:

The file's contents are inserted in place, so any arguments after it still take priority. This is useful when a command line becomes too long for a shell to handle comfortably, and for arguments that a program would rather not put where ps can see them. Set parser.allow_atfile = false to turn it off, for a program that should treat a leading @ as ordinary text.

Help

The help text is generated from the declarations, so it always matches what the program accepts:

-h and --help are declared for you and work wherever they appear. After a command, they describe that command instead of the whole program. help() does the same thing when you call it directly. Both print the help text and exit with status 0.

Colors are used when standard output is a terminal and NO_COLOR isn't set, so output that's piped or redirected is plain text without escape codes. set_terminal_width() sets the width the text wraps at, which is what the example above does, so that the output is the same in every terminal. If you don't set it, the parser asks the terminal for its width, then falls back to COLUMNS, and then to 80.

If a parser's command line didn't match anything at all, it prints its help text and continues. An option with a default counts as a match, so this never happens for a parser with any defaults. To turn this behavior off completely, pass false as the second argument to args.Parser.

Errors

Every error is reported the same way: a line on standard error starting with error:, followed by the usage text, and an exit status of 1.

What happened The message
An option that wasn't declared unknown option: --color
An option that needs a value was the last argument option --name expects <name>
A required option was left out required option --output is missing
A value that isn't in choices --level must be one of quiet or loud, not "shouty"
A required positional argument was left out required positional argument <source> is missing
An argument that doesn't match anything unexpected argument: report.csv

None of these raise an exception. When a command-line program receives something it can't use, there's nothing useful left for it to do, and a stack trace in the user's terminal tells them less than a one-line message. The errors that do raise an exception are mistakes in the declarations, such as a duplicate option name, a short name that's already used, or choices that's neither a list nor a dictionary. Those are bugs in the program rather than mistakes by the user, so they raise an ArgsError or a TypeError from the add_option call that caused them.

Testing Command-Line Parsing

parse() accepts an explicit list, which is what makes it testable:

Create the parser in a function, so that each test gets a new one. A parser keeps the results of its last parse, so sharing one between tests makes them depend on the order they run in. To test the paths that end in os.exit(), which are help and every error above, you need to run a real subprocess, which is what os.exec() is for. Chapter 23 covers testing in more detail.

Module Reference

Creating a parser:

Method Description
Parser(name, default_help) Creates a new parser
add_option(name, help, opts) Adds an option, either globally or to a command
add_command(name, help, opts) Adds a subcommand and returns it, for chaining
add_index(name, help, opts) Adds a positional argument
parse(custom_args) Parses the command line, or the given list
help() Prints the help text and exits with status 0
set_terminal_width(width) Sets the width that text wraps at

Properties you can set after creating a parser:

Property Description
description, epilog Text shown before and after the options
allow_abbrev Whether unambiguous prefixes of long options are accepted. The default is true.
allow_atfile Whether @file arguments are expanded. The default is true.
terminal_width The width that text wraps at

Keys you can use in opts:

Key Description
short_name The single-character form of the option
type One of the type constants
value The value when the option isn't given
choices A list of allowed values, or a dictionary that maps keys to values
required Whether the program refuses to run without it
metavar The word the help text shows in place of the value
deprecated Prints a warning to standard error when the option is used
action For a command, the function to run after parsing

The type constants:

Constants Description
NONE, STRING, INT, NUMBER A flag, and the three plain value types
BOOL, LIST, CHOICE, OPTIONAL A yes or no answer, a repeated value, a value from a fixed set, and an optional value
