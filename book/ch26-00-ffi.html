Chapter 26 · Interoperability

Foreign Functions: C and Rust

The ffi module calls code written in C and Rust. It loads shared libraries, describes the functions in them and calls those functions with ordinary Zuri values. It turns Zuri functions into C function pointers so that a library can call back into your code. And it reads the declarations that a header file or a Rust crate already contains, so the description only has to be written once, by the people who wrote the library.

Every value that crosses the boundary is converted and checked against its C type. An integer that doesn't fit is a RangeError at the call, not a truncated argument inside the library. Memory allocated by the module knows its own size, and a read past its end is rejected before it happens. When a check isn't possible, because C returned an address without saying how much memory is behind it, the module tells you so instead of guessing.

You can use C libraries, Rust cdylib libraries, and static libraries written in either language. The layout of every struct, whether it's packed, over-aligned or full of bitfields, is the same as the platform's own compiler would give it.

Introduction

Sooner or later, every language needs to use code it didn't write, such as a database engine, a codec, a cryptography library, a scientific computing kernel, or a system call that the standard library doesn't wrap. That code already exists, it's fast and well tested, and it uses the C calling convention, which is the one convention every language agrees on, on every platform. Rust libraries can use it too, through extern "C".

Calling across that boundary means describing exactly what the other side expects: how wide each integer is, where each member of a struct is stored, and which register each value is passed in. The machine doesn't check any of this. A description that's off by a single byte silently corrupts memory, and the bug shows up later, somewhere unrelated.

ffi turns that description into a value your program can inspect. It builds the description from the source code the library's authors already wrote, lays out every type the same way the platform's compiler does, and checks every value against it as the value crosses the boundary:

Loading a Library

ffi.open() loads a shared library and returns a Library. It accepts a path, a file name, or a bare name that it completes following the platform's conventions:

A bare name is looked for first in the directories given in paths, and then in the platform's own search order. On Linux, a library's unversioned libname.so file is usually only installed with its development package, so ffi.open() also asks the dynamic loader's cache for the versioned file that the runtime package installs, such as libsqlite3.so.0. On macOS, the name is tried as a .dylib and as a framework.

ffi.find() looks for a library the same way, without loading it:

Without a name, ffi.open() returns the running process, whose symbols include the C runtime library and everything else that's already loaded globally.

Two options change how a library is loaded. lazy: true resolves its symbols when they're first used, instead of all at once. global: true makes its symbols visible to libraries loaded after it, and to the process handle, which a plugin that relies on its host's symbols needs. Both options are Unix concepts and have no effect on Windows, where every loaded module is searched whenever the process is asked for a symbol.

If a library can't be found or loaded, ffi.open() raises a LoadError that includes the loader's own explanation, such as a missing dependency, a library built for a different architecture, or a file that isn't a library.

Symbols

A Library can tell you whether it exports a symbol, and where:

symbol() returns a Pointer to the symbol. On glibc, name@VERSION requests a particular version of a versioned symbol, for the rare program that needs to pin one.

Closing a Library

close() stops a library from being used, so every function bound from it raises a LoadError from then on. The code itself is only unloaded once nothing refers to the library anymore, including the functions bound from it, so a closed library is never unloaded while a call is still running.

Numbers Across the Boundary

A Zuri number is a double, which can represent every integer up to 2^53 exactly, but no further. C integer types go up to 2^64, and with __int128, 2^128. So integers cross the boundary like this:

  • Going in, a number must be a whole number that fits in the type, and you can pass a bigint for any integer type. A fraction, a string or a bool passed for an integer raises a TypeError, and a value outside the type's range raises a RangeError. Values are never truncated or wrapped around.
  • Coming out, an integer is returned as a number if it's within 2^53 of zero, and as a bigint otherwise, so no value is ever rounded.

When a value could be either type, your program has to handle both, for example with is_bigint(value) or by comparing against a bigint, which also compares correctly with a number.

Floating-point types accept any number. long double is wider than a double on some platforms: it's 80-bit extended precision on x86-64 Linux and macOS, and 128-bit quad precision on Arm Linux. Values going in are converted exactly, and values coming out are rounded to the nearest double, as C's own conversion does.

bool accepts and returns a Zuri bool, and a C character type accepts a number or a one-character string:

A complex number is represented as a list of two numbers, [real, imaginary]. You can pass one by value wherever the C compiler supports _Complex, which is everywhere except Windows.

Declaring Functions From C

ffi.declare() reads C declarations and returns a Declarations object, which is a set of types, functions, variables and constants that isn't tied to any particular library. Binding it to a library produces a namespace:

Library.declare() does both steps at once, and it's what most programs use.

The namespace contains a function for each declared function, a Pointer for each declared variable, each constant, and each type that has a name of its own. You use it in the same way as a module. A tagged type without a typedef, such as struct stat, is accessed through the declarations instead, as in api.type('struct stat').

If a declared function isn't exported by the library, you get a SymbolError that names every missing function. With allow_missing: true, the other functions are bound and the missing ones are left out, which is useful for a header that describes several versions of a library.

What Is Read

Everything a header says about an API:

  • typedef, struct, union and enum, including forward declarations, self-referencing records, nested records, anonymous members, bitfields and flexible array members
  • Function prototypes, including variadic ones, and function pointer types nested to any depth
  • extern variables
  • _Static_assert, which is evaluated, so a header that checks its own assumptions checks them here too
  • __attribute__((packed)), aligned(n), ms_abi and sysv_abi, __declspec(align(n)), _Alignas, and asm labels that give a function a different symbol name. Other attributes are skipped.
  • extern "C" { ... }, as written in headers that are shared with C++

A function with a body, such as an inline helper in a header, is read but not bound, because the library doesn't have to export it.

The Preprocessor

Real headers contain a lot of preprocessor lines, so enough of the preprocessor is implemented to read them as they're written:

  • A #define of a value is expanded wherever the name appears, and also becomes a constant. Values can be numbers in any base with any suffix, floating-point numbers, character constants, strings, adjacent strings (which are joined), and expressions that use other constants. A value cast to a pointer type, as headers write sentinels such as ((void *) -1), becomes a Pointer of that type at that address, or nil when the address is zero. A macro can use a type that's declared after it, as C allows, since a macro only has a meaning where it's used.
  • #if, #ifdef, #ifndef, #elif, #else and #endif are evaluated, along with defined(), using the macros that the target platform's compiler predefines, such as __linux__, __APPLE__, _WIN32, __x86_64__, __aarch64__ and __LP64__. __has_include() and the other __has_ queries always return false.
  • #pragma pack applies to the records declared after it, exactly where it's written.
  • #undef removes a macro, and #error stops with its message.
  • Including a C standard header is allowed, because everything it declares is already known. Including <stdio.h> also declares FILE.

Two things are rejected, with the line and column of the problem. The first is including any other file, because declarations are read exactly as given and files are never fetched, so paste in the declarations the program needs. The second is using a function-like macro, which would require the preprocessor's full expansion rules. Defining a function-like macro is allowed and recorded, and only using one is an error.

Functions That Return Text

C has no way to say who owns a returned pointer, but it has a convention that's clear enough to follow. A function returning const char * returns text that it keeps, while one returning char * usually hands over memory to the caller. So a declared function that returns const char * returns a string, or nil for a null pointer, and one that returns char * returns a Pointer, which your program reads and then frees. The same applies to const wchar_t *.

In the real header, getenv is declared as char *getenv(const char *). Declaring it as const char * here is the program's way of saying that it won't free the result, which is correct.

Extending and Sharing Declarations

You add sources to a set one after another, and each one can see what came before it. A set can include another set and use its types without owning them, which is how two libraries can share one set of common types:

types(), functions(), variables() and constants() list what a set contains, and type() resolves any C type name against it, as in shapes.type('segment *[2]').

C and Rust declarations can go in the same set, and each can use the other's types, which suits a crate that includes a C header alongside its source code.

Pointers and Memory

A Pointer is an address, optionally with the type of the value it points to. You get memory from ffi.alloc(), which returns it zeroed and typed:

get() and set() read and write elements of the pointer's type, as ptr[i] does in C, and add() moves forward by a number of elements, as ptr + i does in C. read() and write() take their own type and a byte offset, and work on any pointer:

Memory is little-endian on every platform the module supports, as the third line shows. cast() gives a pointer a type, or removes its type.

Checked Access

Memory allocated by the module knows its size, and every access through a pointer into it is checked against that size before it happens:

If a write fails to convert its value, nothing is written, so a record is never left half updated. Freed memory rejects every access, and freeing memory twice raises an error instead of causing a double free.

A pointer returned by C code doesn't have a size, because C didn't say how much memory is behind it. The only thing that can be caught through such a pointer is a null pointer. How much memory is actually there depends on what the library's documentation says.

Other Kinds of Allocation

ffi.alloc_bytes(size, align) allocates untyped memory. ffi.malloc() allocates memory from the C allocator, for memory you'll pass to C code that frees it with free(), so it's never freed when the pointer is garbage collected. ffi.at(address, type) creates a pointer from a known address. copy_from(), fill() and compare() are the equivalents of memmove, memset and memcmp for checked memory.

Strings and Text

A string passed where a pointer to characters is expected becomes a NUL-terminated copy for the duration of the call, using the encoding implied by the character type: UTF-8 for char, UTF-16 for char16_t, UTF-32 for char32_t, and the platform's own encoding for wchar_t, which is UTF-16 on Windows and UTF-32 everywhere else.

ffi.string and ffi.wstring are pointer types that also convert values coming back. A function declared to return one of them returns a Zuri string, or nil for a null pointer.

Text that needs to last longer than a call, because it's stored in a struct or kept by the library, has to be put in memory of its own with ffi.alloc_string():

read_string() reads up to the terminator, or exactly a given number of code units, in any of the four encodings, and raises a ValueError for text that isn't valid in its encoding. write_string() writes text followed by its terminator. If a read in a block of known size finds no terminator, it's rejected instead of reading past the end.

Structs, Unions and Arrays

A record is built one member at a time, and laid out in the same way the platform's C compiler lays it out:

Record Values

A record value is represented as a dictionary of its members, both going in and coming out. A member that's missing from a dictionary going in is set to zero. Nested records are nested dictionaries, and array members are lists, except that an array of char is read as the string it contains, and an array of other bytes is read as bytes:

Through a pointer, get_field() and set_field() read and write a single member, as ptr->name does, and field() returns a pointer to a member, as &ptr->name does. fields() lists the members along with their offsets.

add_bitfield() adds a member with a given width in bits. Bitfields follow the platform's rules for packing them, which are GCC's and Clang's on Linux and macOS and MSVC's on Windows, including a zero-width bitfield that ends a storage unit:

Unions

A union value going in is a dictionary that holds a single member, the one to store. Coming out, it contains every member, each read from the same bytes, because only your program knows which one is meaningful:

Records can be passed to and returned from functions by value, whatever their shape. Which registers a record is passed in depends on its size and the types of its members, and differs on every platform. Enums and Constants

An enum is an integer type with named constants. A value of an enum type is a number, and wherever one is passed in, you can use a constant's name instead:

Declared enums include their constants. A declared enum is stored as an int unless its values need more space, it specifies a type (as in enum x : uint8_t), or GCC's packed attribute asks for the smallest possible type. Every enum constant, #define constant and Rust const becomes a constant of the declarations, and a member of the namespace they're bound to.

Callbacks

A Zuri function passed where a function pointer is expected becomes a C function pointer for the duration of that call:

The arguments are converted from their C types, with pointers becoming Pointer values and records becoming dictionaries, and the return value is converted to the callback's return type. A small integer is widened to a full register, the same way a C compiler returns one.

Long-Lived Callbacks

A library that stores a function pointer and calls it later, such as a signal handler, an event callback or a logging hook, needs a callback that lasts longer than the call that passed it. ffi.callback() creates one:

A long-lived callback lasts until you call release(). Nothing else frees it, because there's no way to know when the library has finished with the pointer, so a callback that's never released lasts as long as the program. After release(), the callback can no longer be passed anywhere, and C code must not call it again.

Errors Inside a Callback

A Zuri error can't unwind through C stack frames, because the C code in between expects to finish. So an error raised inside a callback is caught, C receives a zero (or the callback's error_value), and the error is raised again, unchanged, as soon as the C function returns:

The first error is the one that's raised. Any later calls to the callback during the same C call return the error value.

Callbacks and Threads

C libraries often run their own threads, and those threads can call callbacks. A Zuri isolate runs on a single thread, so a call from any other thread is passed to the isolate that created the callback, and the calling thread waits until the isolate has run it. The isolate responds at its next safepoint, which is the same point where it checks for signals, or immediately if it's inside a foreign call or in ffi.serve().

That covers a library whose threads call back while the program is busy with something else. It doesn't cover a function that blocks the isolate until its own threads have finished calling back. In that case, the isolate would be waiting for the function, the function for its threads, and the threads for the isolate. ffi.threaded() gives that kind of function a version that runs on a helper thread, while the isolate keeps responding to callbacks:

The callback ran on the isolate's own thread, partway through the threaded call. A program that has nothing else to do while it waits for calls from another thread can wait in ffi.serve(timeout), which handles whatever calls arrive and returns how many it handled.

Variadic Functions

A variadic function, such as printf and its relatives, takes its fixed parameters with declared types, followed by any number of other arguments. Each argument after the fixed ones is passed as the type its value suggests:

Value Passed as
A whole number that fits in an int int
A larger whole number long long
Any other number double
A bigint long long, or unsigned long long if necessary
A bool int
A string const char *
A pointer, bytes or nil void *

For anything else, give the value a type with Type.of(). C's usual promotions still apply on top of that, so a float is passed as a double, and a type narrower than int is passed as an int.

The second call shows why of() exists. %.1f with a plain 2 would pass an int, and printf would read a double that was never passed.

Errors and errno

All of the module's own errors are subclasses of FfiError:

Class Raised when
FfiError A type can't be used in the way requested, such as a record without a size passed by value, or a signature that libffi can't call
LoadError A library can't be found or loaded, or a function is called after its library was closed
SymbolError A library doesn't export a symbol
DeclarationError C or Rust source can't be read. line and column point to the problem.
PointerError Memory would be accessed out of bounds, through a null pointer or after being freed, or freed twice
CallbackError A released callback is used
LinkError A static library can't be linked

A value that can't be converted to its C type raises the usual TypeError or RangeError, the same errors any function raises for an invalid argument, and the message names the function, the argument and the type.

errno

C reports failures through errno, which anything that runs afterwards might change. So errno is cleared just before every foreign call and read just after it, and ffi.errno() returns the value that the most recent call on this isolate left there:

34 is ERANGE. On Windows, ffi.last_error() reports GetLastError() in the same way, and it's always zero on other platforms. ffi.set_errno() sets errno, for the rare function that reads it.

Ownership and Lifetimes

Three kinds of memory cross the boundary, and each one has a single owner.

Memory from ffi.alloc() belongs to the program. It's freed when the last pointer to it is garbage collected, or earlier, when you call free(). Pointers created from it with add(), offset(), cast() and field() share the same memory and keep it alive. The one rule to follow is that a pointer must stay reachable for as long as C code holds the address. If C was given some memory and Zuri lost track of it, that memory can be freed while C is still using it.

Memory from ffi.malloc() belongs to whoever frees it. It's never freed by the garbage collector, because the usual reason to allocate it is to pass it to C code that frees it with free(). Otherwise, call free() to release it.

Memory allocated by C belongs to C until your program takes ownership of it with own(), passing the function that releases it, or no function for memory that the C allocator's free() releases:

An owned pointer is released when it's garbage collected, or when you call free(), and every pointer derived from it rejects any access afterwards. A destructor can be any foreign function that takes a single pointer, such as sqlite3_close, png_destroy, or CString::from_raw wrapped in an extern "C" function. Only a pointer to the start of an allocation can free it.

The garbage collector runs destructors in the middle of its own work, when no Zuri code can run, so a destructor that calls a callback during garbage collection always gets zero back, or the callback's error_value. When you call free() yourself, the destructor runs from your program, where callbacks work as they do anywhere else.

Static Libraries

A static library is object code waiting for a linker, so nothing can load it at run time as it is. ffi.link() passes it to the platform's linker, which links every object in it into a shared library, and then loads the result:

On Linux and macOS, the linker is the C compiler, which is cc or whatever $CC names. On Windows, it's MSVC's link.exe, found through the Visual Studio installation. The result is cached under a name based on the contents of the archives and the options, in ffi.default_link_cache() or the directory given in the cache option, so the linker only runs once for a given input, and every time the program starts after that, it loads the cached library.

A Rust staticlib includes the Rust standard library, which in turn needs a few system libraries. An archive that contains Rust code is recognized and linked against them automatically.

On Windows, a static library's functions aren't marked for export, so the linked DLL exports every symbol the archives define with an unmangled name, or exactly the symbols listed in the exports option.

libraries, search_paths and flags pass extra libraries, their directories and raw arguments to the linker, and linker replaces the linker itself. A failure raises a LinkError that includes the linker's own output.

Isolates

Types, pointers, libraries, foreign functions, callbacks and declarations can all be passed to another isolate, and none of them are moved: both sides keep a working handle to the same thing. A type is a description, a library is a handle that the loader shares across threads, and a pointer is an address, so memory written by one isolate can be read by another:

Whatever is in that memory is shared without any synchronization, just as it is between C threads. A callback belongs to the isolate that created it, so if it's passed somewhere else, its calls still run on the original isolate.

Rust in Depth

Every Rust type that has a defined C ABI can cross the boundary, and every other type is rejected with an explanation.

An enum with fields is laid out according to the rules for its representation. A value names its variant, and the rest of the dictionary holds its fields. The fields of a tuple variant are named '0', '1' and so on, and a variant without fields can be passed as just its name:

A slice crosses as the pointer and length that Rust's own FFI convention combines it into, and ffi.slice(type) builds that #[repr(C)] struct:

These are rejected, each with an explanation: &str, &[T], String, Vec and every other type without a stable layout, trait objects, tuples, generic types and functions, Option of a type without a niche, a function without #[no_mangle] or #[export_name], and the extern "Rust" ABI.

A panic that escapes from a function in a Rust library ends the process. A library that catches its panics at its own boundary, or keeps them on its own threads, returns normally. One that lets a panic escape ends the process, even when it's called from an isolate. An extern "C" function aborts immediately. An extern "C-unwind" function unwinds into Zuri, which can't catch a panic from another copy of Rust's runtime, so it aborts. A Rust library built with panic = "abort" ends the process on any panic. This is the only kind of panic that isn't contained within its isolate.

Platform Differences

The module runs on 64-bit little-endian platforms, x86-64 and Arm, on Linux, macOS and Windows, and it follows each platform's C compiler:

Linux x86-64 Linux Arm macOS x86-64 macOS Arm Windows x86-64
long 8 8 8 8 4
char Signed Unsigned Signed Signed Signed
wchar_t 4, signed 4, unsigned 4, signed 4, signed 2, unsigned
long double 80-bit 128-bit 80-bit 64-bit 64-bit
_Complex passed by value Yes Yes Yes Yes No
Enum values larger than int Wider type Wider type Wider type Wider type int, truncated
Bitfield rules GCC GCC Clang Clang MSVC

ffi.platform() reports these values for the running platform. A program that passes records between platforms through files or sockets gets the same layouts that the C compiler on each platform produces, which is what the C code on that platform expects.

Calling conventions follow the platform too: System V on Linux and macOS x86-64, AAPCS64 on Arm, with Apple's variations of it, and the Microsoft x64 convention on Windows. On x86-64, a function type or Library.function() can request abi: 'win64', or abi: 'sysv64' on Unix, for a function compiled for the other convention. Declarations read ms_abi and sysv_abi attributes, and Rust's extern "win64" and extern "sysv64".

128-bit integers can be passed by value, in both directions, under every one of these conventions. The Microsoft x64 convention passes them by reference and returns them in a vector register, the same way rustc, Clang and GCC compile them, so a callback that returns an i128 works there just as it does everywhere else.

What Is Checked

A foreign call runs code that the module can't see into, so its guarantees stop where the C code begins. Up to that point:

  • Every value is converted to its declared type, with integers checked against their range, and every other kind of value checked against its type.
  • Memory allocated by the module is checked against its bounds and rejects any use after free(). Freeing it twice is an error.
  • A null pointer is caught before anything is read or written through it.
  • A write that fails doesn't change anything.
  • A Zuri error inside a callback never unwinds through C code, and a Rust panic inside the module never reaches C code.
  • A callback called from any thread runs on its own isolate.

Beyond that, what C code does is up to C. A declaration that doesn't match the library, a pointer read beyond what the library says is there, a callback that C calls after it was released, or bytes resized by a callback while C writes to them are all undefined behavior in C, and they still are here. Reading declarations from the library's own header or crate, instead of writing them by hand, is the best way to avoid the first of these.

Design Limits

It doesn't run the full C preprocessor. Macros that define values and conditional blocks are evaluated, but including other files and expanding function-like macros aren't supported, and they're rejected where they appear.

It doesn't compile C code. Static libraries are linked by the platform's own linker, which needs a C toolchain on the machine that links them.

It doesn't guess who owns memory. A pointer returned by C isn't freed until your program says how, with own().

It doesn't free callbacks automatically. A callback lasts until you call release(), because only your program knows when the library has finished with it.

It doesn't unwind through foreign stack frames. Errors are caught and raised again once the C code has returned. A panic in a callback is held in the same way, and then continues and ends its isolate. A panic that escapes from a Rust library ends the process, as described in Rust in Depth.
