Chapter 15 · The Big Modules

HTTP

The http module is Zuri's HTTP stack. It contains a client, a server and the building blocks they share. It supports HTTP/1.1 and HTTP/2, over plain connections or TLS, and it's designed to be exposed directly to the internet.

That last point is a deliberate design decision. Many language runtimes include an HTTP server that's fine for development, but expect you to put a reverse proxy in front of it in production to terminate TLS, serve static files, compress responses, enforce request limits and speak HTTP/2 to browsers. All of those features are built into this module.

Introduction

A First Request

get(), post(), put(), patch(), delete(), head(), options() and trace() are all available as module-level functions. They all use one shared client, which keeps its connections open between calls. Request Methods describes each of them.

A First Server

This server already does two things worth noticing. GET /users/42 matches the second route and passes '42' to the handler. And a HEAD / request is handled by the first route, which responds with the headers a GET would have produced but no body, because that's what HEAD means.

Code blocks in this chapter that list several calls together, such as three ways to save, four filters or a family of methods, are reference listings, not programs. They show the form of each call, not a sequence you could run, and some of them would conflict if you pasted them into one file. Anything shown as a complete program in this chapter runs as written.

A Complete Example You Can Run

Most of the examples in this chapter call a host that doesn't exist, or start a server that never returns, so you can't paste them into a terminal and watch them work. This one is different. It runs a real server on a real port and sends real requests to it, using two files.

The server goes in its own file, because a function that uses an imported module can't be spawned from the file that imported it. See Concurrency with Isolates for the details.

There are four details here that are worth using in your own code.

Port 0 asks the operating system for a free port. listen() would bind the port for you, but then there'd be no way to find out which port it got. So the example calls bind() explicitly, reads the bound address, and only then starts accepting connections. Use this pattern for tests and for any process that runs more than one server.

The port is sent over a channel. The client can't know the port in advance, and the two halves run in different isolates with separate heaps, so a shared variable isn't an option.

request.json_body() parses the request body, and response.json(value, status) writes the response. The names don't match because the two methods do different jobs: one decodes what arrived, and the other encodes the response and sets a status.

task.cancel() stops the server. listen() runs until the server is closed, so without that call, the program would never exit.

Making Requests

The Shared Client

The module-level functions use a single HttpClient that exists for the lifetime of the program. It reuses connections, so a second request to a host it has already connected to skips the TCP handshake, and for HTTPS, the TLS handshake as well.

Use http.shared_client() to get that client when you want a setting to apply to every simple request in a program, and create your own client for anything more specific.

Creating a Client

If you give a client a base URL, it's added to the front of any target that isn't already an absolute URL, so the rest of your program can refer to the service by path alone. Every key in the options dictionary is a field of HttpClient, apart from headers, and you can also set any of them later:

Note Create a client once and reuse it. Creating a new client for each request throws away its connection pool, its cookie jar and its TLS configuration, which is most of what a client is for.

Request Methods

Each HTTP method has its own function. Every function is available in two places, with the same signature: on the module, where it uses the shared client, and on any HttpClient you create.

The three methods that send a body take it as their second argument. The others take the options dictionary in that position.

Request Bodies

The second argument to post(), put() and patch() is the body, and its type determines how it's sent:

A dictionary or a list is sent as JSON, with the matching Content-Type. A string or bytes value is sent exactly as it is, with no content type unless you set one.

For other kinds of body, or to be explicit, set it in the options dictionary:

Option Sends Content-Type
body A string or bytes, exactly as given None, unless content_type is set
json Any value, encoded as JSON application/json
form A dictionary application/x-www-form-urlencoded
multipart A MultipartBuilder multipart/form-data, including the boundary
content_type Nothing by itself Overrides the content type set by any of the above

Content-Length is set for you based on the body, and you can't override it. If the client and server disagree about how long a body is, that's a request smuggling vulnerability, not a matter of formatting.

Uploading Files

A file upload is a multipart/form-data body, and MultipartBuilder puts one together for you:

Passing the builder as the body is all you need to do. The Content-Type, its boundary parameter and the Content-Length are all derived from it.

Method What it does
add_field(name, value) Adds a plain form field. Numbers and booleans are converted to strings.
add_file(name, filename, content, content_type) Adds a file. content is bytes or a string, and content_type defaults to application/octet-stream.
content_type() Returns the value of the Content-Type header, including the boundary
boundary() Returns the boundary string
build() Returns the complete body, as bytes
length() Returns how many parts have been added

To send several files under the same field name, call add_file() several times. That's what an <input type="file" multiple> sends:

A filename that isn't plain ASCII is sent twice: once as a transliterated filename, and once as an RFC 5987 filename*. That way, the real name survives even if the recipient only understands one of the two.

If you need the body on its own, for example to sign it, log its size or send it somewhere other than through this client, build it yourself:

Note build() assembles the entire body in memory. For an upload that's large enough for this to matter, send the file as a raw body with its own content type instead. multipart/form-data is only worth its overhead when there are other fields alongside the file.

The boundary is generated from the platform's secure random number generator, not from a timestamp or a counter. If someone else could predict the boundary, they could include it in a field value to forge extra parts.

Reading a Response

raise_for_status() raises a StatusError for a 4xx or 5xx status, and otherwise returns the response, so you can use it inline. The response is still available on the error, which matters because that's usually where an API explains what went wrong:

Compressed response bodies are decompressed automatically, whether they use gzip, deflate, brotli or zstd. Once a body has been decompressed, the Content-Encoding header is removed, so nothing later on tries to decode it again.

Query Parameters and Headers

A list value repeats the parameter, which is how a query string sends more than one value with the same name. Headers set for a request are merged with the client's own headers, and take priority over them.

Authentication

Credentials passed this way only apply to the origin you sent the request to. If the response redirects to a different scheme, host or port, the credentials are dropped. Otherwise, a redirect to a host chosen by someone else would be a way to collect your Authorization header.

Redirects

Redirects are followed by default, up to max_redirects (10 by default), and the response records how many were followed:

When a 303 is followed, the request becomes a GET without a body, and in practice the same happens for a 301 or 302. That's what browsers and other clients do. A server that wants the method and body to be kept should send a 307 or 308, and both of those are followed with the method and body unchanged.

You can turn off redirect following for a single request or for a whole client:

head() doesn't follow redirects by default, because a HEAD request is usually meant to look at the exact response that a redirect would hide.

Cookies

A client with a cookie jar keeps cookies between requests, so logging in and the requests that follow behave as they would in a browser:

The cookie jar follows the matching rules in RFC 6265. A cookie without a Domain is only sent to the host that set it, a cookie with a Domain is also sent to subdomains, a path matches every path below it, and a Secure cookie is never sent over an unencrypted connection. If a server tries to set a cookie for a domain it doesn't control, the cookie is rejected.

Timeouts and Retries

All timeouts are in milliseconds. max_retries retries a failed request, but only for idempotent methods. Repeating a POST could mean charging someone's card twice, so GET, HEAD, PUT, DELETE, OPTIONS and TRACE are retried, and nothing else is.

If the server closed a pooled connection while it was idle, the next write on that connection fails in a way that looks exactly like a network failure. In that specific case, an idempotent request is retried once, even with the default max_retries of zero. Otherwise, every connection that a server closes for being idle would show up as an error.

Streaming a Response

You don't have to hold a large response in memory:

finish() returns the connection to the pool once you've finished with the body. Until then, the connection belongs to you, because the client has no way of knowing when you've finished reading.

TLS and Certificates

By default, certificates are verified against the platform's trusted certificates. To connect to a service with an internal or self-signed certificate, add its certificate authority:

There's also verify = false, which turns off verification completely. It's meant for local development only. With it, the connection is encrypted but not authenticated, which means anyone in the middle can easily intercept it. Everywhere else, use add_ca().

Proxies

A client uses the proxy set in the environment, the same way command-line tools do: HTTPS_PROXY for https addresses, HTTP_PROXY for http addresses, and ALL_PROXY for both. Each variable can be written in uppercase or lowercase. NO_PROXY is a comma-separated list of hosts that are reached directly. A name in the list also covers every name under it, an entry with a port only covers that port, and * covers everything. The machine's own loopback addresses are never reached through a proxy.

A client you create yourself can specify its own proxy, or ignore the environment completely:

An https request is tunneled through the proxy with CONNECT, so the proxy only passes the encrypted bytes along and can't read them, and the certificate that's checked belongs to the destination. An http request is passed to the proxy in full. Any credentials in the proxy address are only sent to the proxy, as a Proxy-Authorization header. The connection to the proxy itself uses plain HTTP, and an https:// proxy address is rejected.

Serving Requests

Routing

A route pattern consists of literal segments, :name parameters and an optional catch-all at the end:

Pattern Matches Captures
/users /users
/users/:id /users/42 id = '42'
/users/:id/posts/:post /users/4/posts/7 id, post
/files/ + *path /files/css/site.css path = 'css/site.css'

A literal segment always takes priority over a parameter, and a parameter always takes priority over a catch-all. So /users/new and /users/:id can both exist, and the more specific route wins, whichever was registered first. Routes are matched using a trie, so a router with a thousand routes costs the same per request as one with ten.

get(), post(), put(), patch(), delete(), head() and options() each register a route for one method. any() registers GET, POST, PUT, PATCH, DELETE and OPTIONS all at once. handle() takes the method as an argument, which is how you add a route for a method that doesn't have its own function, such as PROPFIND or a custom method:

Three kinds of request are answered without a handler:

  • HEAD uses the GET route for the same path, and the body is removed from the response.
  • OPTIONS gets a 204 response with an Allow header that lists the methods the path accepts.
  • A request for a path that only exists for other methods gets a 405 response, again with an Allow header, rather than a 404, which would be wrong.

Forms and File Uploads

A submitted form arrives as the request body in one of two encodings, and you read both through the same methods. The enctype attribute on the <form> decides which one a browser sends: the default, application/x-www-form-urlencoded, for a form with only plain fields, and multipart/form-data for a form that includes a file.

Method Returns
form() Every field as name -> value, keeping the first value of a repeated name
form_all() Every field as name -> [value, ...]
form_field(name, fallback) The first value of one field
files() The uploaded files as name -> [UploadedFile, ...]
file(name) The first file uploaded under name, or nil

The body is parsed the first time you use it and then cached, so reading form() in a middleware and again in the handler only parses it once. A body in neither encoding gives you an empty dictionary instead of raising an error. Use request.json_body() for a JSON body and request.text() for anything else.

A field that can appear more than once, such as a group of checkboxes or a multiple select, needs form_all(), because form() only keeps the first value:

What a Handler Shouldn't Trust

The filename. The client controls it, and it often contains a full local path from a Windows client, .. segments from a malicious one, or a NUL byte intended to cut off a later check. Never join it to a path directly:

safe_name() removes every directory part, with either kind of separator, and reduces the rest to letters, digits, ., - and _. If nothing usable is left, it returns 'unnamed'. Better still, choose the file name yourself and keep the client's name as a label:

The content type. content_type is whatever the client wrote in the part's header, and it doesn't tell you anything about the actual contents. A file that claims to be image/png could be anything. Size Limits

The body is read into memory, up to the server's max_body_size, which is 10 MiB by default. That's intentionally small:

If a request declares a body larger than the limit, it's rejected with 413 Content Too Large before any of the body is read, which is exactly what Content-Length is for. A request that gives a false length is cut off at the limit and also rejected. Either way, the connection is then closed, since a partly read body leaves nothing that can safely be parsed after it.

A client that asks for permission first with Expect: 100-continue gets an answer before it sends anything. The server checks the declared length against the limit and either responds with 100 Continue or rejects the request straight away, so a rejected upload only costs one round trip instead of a whole transfer.

For an upload that's too large to hold in memory, accept it as a raw body and stream it, rather than as a form field. multipart/form-data is only worth its overhead when there are other fields alongside the file.

Request Validation

You can validate a request against a validate schema:

validate() returns the input it checked, so the success path takes one line, and the data you go on to use is the data that was validated. If validation fails, it raises the schema's own validate.ValidationError, which has an errors list of { field, message } entries. group_errors() turns that list into a dictionary keyed by field, which is the format most front ends want:

If you'd rather branch than catch an error, validate the input yourself. There's no separate API for it:

The rules themselves, of which there are around eighty, including rules that compare fields such as confirmed() and required_if(), are part of the validate module, not this one.

What Gets Validated

request.input() is the dictionary that validate() checks. It merges three sources, each overriding the one before it:

  1. Route parameters from the pattern that matched
  2. Query string parameters
  3. The body: the keys of a JSON object, or the submitted form fields

That means one schema works for POST /users with a JSON body, GET /users?… with a query string and /users/:id with a route parameter, and the handler doesn't need to care which one it got.

To use only one of the sources, name it:

Two things are intentionally left out of the merged input:

  • Uploaded files. There's nothing a schema rule could usefully say about a file's bytes. Get files with request.file() and check them as described in Forms and File Uploads.
  • A JSON body that isn't an object. An array or a plain string has no names to merge, so it doesn't contribute anything. Read it with request.json_body().

A body that can't be parsed as JSON also contributes nothing, instead of raising an error. The schema's required rules then report what's missing, which is a more helpful response to a client than a parser error.

Values From Requests Are Strings

Query strings and URL-encoded forms only contain text. ?age=36 gives you the string '36', not the number 36, and that affects which rules apply:

Rule On '36' Why
integer(), numeric(), gt(), gte(), lt(), lte() Treats it as 36 These rules convert the value
size(), min(), max(), between() Treats it as 2 These rules measure size, which for a string is its number of characters

That's how validate is documented to work, not a quirk of this module. min(8) on a password means eight characters. It's only surprising when a schema written for a JSON body is later used for a query string.

If a schema has to work with both, use the rules that check values:

input() doesn't convert anything for you. It would have to guess, and silently turning a postcode like '01234' or a version like '1.0' into a number would be worse than having to choose the right rule.

Repeated fields

A name can legitimately appear more than once in a query string or a form, so those sources arrive as name -> [values]. input() replaces a list holding exactly one value with that value, and leaves a list of several values as it is:

That way, a rule for a single value sees a single value. If a field must always be a list, however many values arrived, read it with form_all() or from request.query directly, and validate it with validate's .* wildcard.

Note The http module doesn't import validate. validate() accepts any object that has a check_or_raise() method and calls it, so a server that doesn't validate anything never has to load a schema engine, and your own schema objects, or ones from another library, work just as well.

The Response Object

Every method that writes a body also sets a suitable Content-Type, and each one returns the response, so you can chain them.

file() streams the file from disk instead of reading it into memory, so serving a large file takes only one line.

content_disposition() tells the browser whether to display the body or save it, and under what name. A name with characters outside printable ASCII, or one that contains a quote, a backslash or a percent sign, is sent as RFC 6266 describes: in full in filename*, with a plain ASCII substitute in filename. download() sends its file name the same way, so a body written from memory and a file from disk are saved under the same name.

Middleware

A middleware function takes (request, response, next) and decides whether the rest of the chain runs:

Middleware runs in the order it was added, with the first one added on the outside, so it wraps everything added after it.

If a handler raises an error, control never comes back there, and the server's error handling later decides on the 500 that's sent to the client. Errors

If a handler raises an error, the client gets a 500, and the error message is never sent to it. Error messages often contain a file path, a query or part of the data being processed, and none of that should be sent to whoever caused the error.

on_error() listeners see every error, including failures on the connection that never reached a handler. error_handler() creates the response body for a failed request. Without one, the server sends a plain 500.

Static Files

That one call handles everything a static file needs to work properly with a browser or a CDN:

  • ETag and Last-Modified headers, and 304 Not Modified for a conditional request that still matches
  • Range requests, answered with 206 and a Content-Range header, and 416 for a range outside the file
  • If-Match, If-Unmodified-Since, If-None-Match, If-Modified-Since and If-Range, evaluated in the order RFC 9110 specifies
  • Content-Type based on the file extension
  • index.html for a request that names a directory
  • With precompressed, a .br or .gz file next to the original, served instead of it when the client accepts that encoding

Every request path is percent-decoded, normalized and joined to the root, and then checked to make sure it's still inside the root. All of these steps are needed, because doing only some of them isn't enough. Dotfiles aren't served at all. Files like .env, .git and .htpasswd end up in a web root at some point in most projects, and none of them should ever be served.

Compression

Responses are compressed on the way out, and compression is on by default. A response is compressed when all of these conditions are met:

  • server.compression is on, which it is by default.
  • The body is at least server.compression_min_size bytes, which is 1024 by default.
  • Its media type benefits from compression. That includes anything starting with text/, as well as JSON, JavaScript, XML, SVG, WebAssembly and the +json and +xml types.
  • The client's Accept-Encoding header accepts br or gzip.
  • Nothing has already set a Content-Encoding.
  • The compressed body is actually smaller than the original.

When the client accepts both, Brotli is used instead of gzip. Vary: Accept-Encoding is added either way, so a shared cache in front of the server can't send a compressed body to a client that didn't ask for one.

To turn compression off, or change the threshold:

The list of media types is an allowlist rather than a denylist on purpose. A JPEG, an MP4 or a zip file is already compressed, and running it through Brotli would use CPU time only to make it slightly larger.

Note Responses created with response.file(), which includes everything serve_files() serves, are not compressed on the fly. They're streamed from disk instead of being held in memory, and compressing them for each request would mean reading them into memory first. Compress those files ahead of time, and let the static file handler pick up the compressed versions:

With this option on, a request for site.css from a client that accepts Brotli is answered with site.css.br if that file exists, or with site.css.gz if that exists and the client accepts gzip. This costs no CPU time per request, and the response gets the correct Content-Encoding and Vary headers.

On the client side, there's nothing to configure. Accept-Encoding: gzip, br, deflate, zstd is sent by default, and compressed response bodies are decoded before you see them.

Setting Cookies

http_only defaults to true and same_site defaults to 'Lax', which is what a cookie containing anything sensitive should have. Pass them explicitly if you want something else. If a cookie's name starts with the __Secure- or __Host- prefix, the rules for that prefix are applied automatically, so the cookie isn't sent in a form that the browser would silently refuse to store.

For state that belongs to a visitor rather than to the browser, use a session. A session keeps the state on the server and only puts an identifier in the cookie. Sessions covers them.

Content Negotiation

best_match() chooses the format the client would most like from the ones you can produce. It takes quality weights into account, and your own order breaks ties. request.accepts('text/html') and request.wants_json() cover the most common cases.

Built-in Middleware

http.middleware contains the middleware that almost every public service ends up needing. Each function returns a middleware, so you call it at the point where you register it:

They're ordinary middleware with no special privileges, so you can read any of them as an example of how to write your own.

None of them raise an error when they're created. That matters for the three that take a verifier, basic_auth(), bearer_auth() and jwt_auth(). For these, passing no verifier disables the middleware. It lets every request through, instead of rejecting requests or failing when you register it.

This is intentional, and it's useful. Setting a verifier to nil turns off its middleware without changing the rest of the chain, which is what you want when you're tracking down which middleware in a stack is causing a request to fail.

A middleware is only disabled when you ask for it, never as a fallback. A verifier that's present and rejects a request still rejects it.

basic_auth()

Requires HTTP Basic authentication.

The first argument is a function that's called with the username and password, and returns whether they're valid. The second argument is the realm named in the challenge, which defaults to 'Restricted'.

If authentication succeeds, the username is stored in request.context['user']. If it fails, the response is a 401 with a WWW-Authenticate header, which makes the browser show its login prompt.

Passing nil instead of a verifier disables the middleware completely, as described in the note above.

bearer_auth()

Requires a bearer token, which is the usual approach for an API.

The verifier is called with the token. It returns a falsy value to reject the token, or a value to attach to the request, which is stored in request.context['user']. You can return the subject, the claims or a complete user record.

A failure produces a 401 with a WWW-Authenticate: Bearer challenge and a JSON body. The realm is the optional second argument, and defaults to 'api'. As with basic_auth(), a nil verifier disables the middleware.

middleware.parse_bearer(header) and middleware.parse_basic(header) are also exported, for code that needs to read an Authorization header without installing a middleware, and request.bearer_token() reads the token directly from a request.

For JSON Web Tokens in particular, use jwt_auth(), which handles the verification, the claims and the RFC 6750 challenges for you, instead of leaving them to the verifier you write here.

jwt_auth()

Requires a valid JSON Web Token, verified with the jwt module.

The first argument is either a jwt.Verifier, or a function that takes the token and returns its claims. The function form lets you use a key set selected by kid, or anything else the jwt module can do that a fixed verifier can't:

Option Default Meaning
realm 'api' The realm named in the challenge
optional false Attaches the claims when a valid token is present, but doesn't reject requests without one
scopes None A list of scopes that every token must include

If verification succeeds, the claims are stored in request.context['claims'], and the sub claim, which is where an issuer usually puts the account the token represents, is stored in request.context['user']:

Failures follow section 3 of RFC 6750:

Situation Response
No token at all 401, with WWW-Authenticate: Bearer realm="api"
The token can't be verified 401, with error="invalid_token"
The token is valid but is missing a required scope 403, with error="insufficient_scope" and the scope that was needed

The last row is the reason for scopes. A token that failed authentication and a token that's authenticated but not allowed to do something are different problems. Responding to both with 401 tells the client to get a new token, when a new token won't help.

Note A challenge never says which check a token failed. An expired token and a forged one get exactly the same error_description. Knowing which it was is useful for your logs and for an attacker, and nobody else. If you need the reason, log it from the verifier you passed in.

optional is for a route that behaves differently when it knows who's making the request, but doesn't require it, such as a public page that shows an edit button to its author:

With optional, a token that's present but invalid is still rejected. If a bad token were ignored, a client could tamper with a token and get the anonymous view instead of an error, which would hide exactly the kind of problem you want to know about.

A nil verifier disables the middleware. Every request passes through without authentication, and request.context['claims'] is never set. Nothing here raises an error when it's created, so you never need a catch around the registration.

Like HttpRequest.validate(), this middleware doesn't import the jwt module. The caller creates the verifier, which leaves the choice of token format to the application, and means a server that doesn't authenticate anything never has to load the module.

etag()

Computes a weak ETag for the finished response body, and responds with 304 Not Modified when the client already has that version.

The only optional argument is the smallest body size worth tagging, in bytes. It defaults to 128, because for smaller bodies, the validator costs more than the body it would save.

Because it works with the finished body, it works with any kind of response, such as a rendered template, a JSON document or a generated report.

Sessions

A session is state that belongs to a single visitor. It's kept on the server and found again through a cookie that the browser sends back. Only the identifier is sent to the browser, so a visitor can't read or change what the session contains, and the cookie is useless to anyone who can't present the exact value that was issued.

session() is a middleware. Register it once, before anything that reads a session, and every handler after it can get its session with request.session().

Sessions Are Created on First Use

A request that never uses its session costs nothing: the store isn't read or written, and no Set-Cookie header is sent. The session record is only created the first time something is written to the session, which stops a crawler working through a public site from filling the store with empty sessions.

A request that only reads an existing session doesn't write anything back either, except to move the idle expiry time forward, at most once every touch_interval seconds.

Signing In

regenerate() is the line you need to get right. It gives the session a new identifier and deletes the record stored under the old one, while keeping everything the session contains.

Without it, an attacker who manages to set a cookie in the victim's browser beforehand, through a forgotten subdomain, an open redirect or a shared computer, knows which identifier the victim will be signed in under, and can simply use it afterwards. This attack is called session fixation, and a new identifier is the entire defense against it. Call regenerate() whenever the meaning of the session changes, such as when a user signs in, becomes an administrator or completes an extra authentication step.

To sign out, call destroy(), which deletes the record and tells the response to expire the cookie:

clear() is the other option. It empties the session without ending it, keeping the identifier and the cookie.

Flash Messages

A handler that does some work and then redirects can't render a message describing what happened. A flash message carries that message to the page that can:

A flash message is used up by the next request that touches the session in any way, whether or not that request reads this particular message. If a page looks at the session without reading the message, the message isn't kept for the page after it. A request that never touches its session, such as a request for a static file or an image, leaves the message waiting.

Where Sessions Are Kept

There are four places a session can be stored, and switching between them means changing one line.

FileStore keeps one file per session. This is the default, because it doesn't need any setup and it's shared between the workers that http.serve() starts. If you don't give it a directory, it uses a private subdirectory of the platform's temporary directory, created with permissions 0700:

The platform clears that directory on its own schedule, which on most systems means every reboot. For sessions that need to survive a restart of the host, specify your own directory:

A session file is a credential, just like the cookie. The directory is created with permissions 0700 and each file with 0600, and a directory that every user on the machine can access is rejected instead of used. That's why the temporary directory itself is never the default. Pass strict_permissions: false to accept such a directory anyway.

SqlStore keeps one row per session. It has its own import, so a program that uses the default store never loads the sql module:

migrate() creates the table and its index if they don't already exist, and it's safe to call every time the program starts. It accepts a sql.Connection or a sql.Pool, and a server should use a pool.

MemoryStore is for tests. Nothing survives a restart, and nothing is shared between workers, so if a browser's next request goes to a different worker, that worker has never heard of its session. It's the right store for tests and the wrong one for real traffic.

You can write your own store. A store has five methods, and none of them sees a session identifier or needs to understand the contents of a session:

touch() has a default implementation built on read() and write(). Override it if your backend can update an expiry time by itself.

The key passed to a store is the SHA-256 hash of the identifier, not the identifier itself. Someone who can read the directory, the table or a backup of either can see what's in the sessions, but can't resume one, because they don't have the value the browser presents.

When a Session Ends

A session has two time limits, and it ends when either one runs out:

Option Default Meaning
idle_timeout 7200 Seconds of inactivity allowed. The limit moves forward while the visitor is active.
lifetime 86400 Seconds the session can last, however active the visitor is

You can set either one to nil to remove that limit, but not both.

The absolute lifetime is what makes a user sign in again after leaving a tab open overnight.

touch_interval is how often a request that only reads the session updates the idle expiry time. It's the difference between writing to the store on every request and writing once a minute. It defaults to sixty seconds, or half of the idle timeout if that's shorter. If you set it yourself, it has to be less than idle_timeout. Otherwise, even a session that's constantly in use would expire, because nothing would ever move its expiry time forward.

Nothing schedules a regular cleanup of expired sessions, so cleanup happens as part of ordinary traffic. gc_probability (0.01 by default) is the chance that a write also cleans up expired sessions. If you'd rather run store.gc() from a cron job, set it to 0.

persistent: false sends a cookie that ends when the browser session ends, which is what a sign-in should usually do. persistent: true sends a Max-Age instead, and moves it forward on every request.

Signing the Cookie

An identifier is 32 bytes from the platform's cryptographic random number generator, which is far too large to guess. Signing doesn't add any protection against guessing, but it helps a lot against high volumes of fake cookies. With a secret set, a cookie that this server didn't issue is rejected after a single HMAC calculation, instead of after a disk read or a database query.

Set a secret on any server that's exposed to the internet, and give every worker the same secret, because otherwise a cookie issued by one worker is rejected by the next. Turning on signing rejects all cookies issued before it, so everyone is signed out once.

What a Session May Hold

A session can hold anything JSON can represent: strings, numbers, booleans, nil, and lists and dictionaries of those values. A class instance can't be represented as JSON, so storing one raises an error when the session is written.

Sessions are meant for identity and small amounts of state, such as who's signed in, which steps of a form have been completed, or what message to show on the next page. If the contents are larger than max_size (65536 bytes by default), a SessionError is raised. If you need to store more than that, put it in a database row and keep the row's key in the session.

Session Limitations

If two requests write the same session at the same time, which usually means parallel requests from the same browser tab, both succeed, and whichever finishes last wins. The file store writes by renaming a file, so a reader never sees half a session, and the SQL store writes in a single statement, but neither one takes a lock. Don't use a session as a counter that several requests increment at the same time.

TLS

Or from strings, which gives you more control:

cert_chain must contain the server certificate followed by any intermediate certificates. Leaving out the intermediates is the most common TLS mistake, and it only fails for clients that don't already have them cached. That means it often looks fine from your own browser.

Note The certificate and key are parsed when the first handshake happens, not when you set them, so an invalid or mismatched pair shows up as a failed connection rather than as an error from use_tls(). If you want to find out early, make a request to the server as part of starting it.

Turning on TLS also advertises h2 through ALPN, so browsers get HTTP/2 without any other configuration.

HTTP/2

You don't need to turn HTTP/2 on. HttpServer uses it when ALPN negotiates h2 over TLS, and when a client on an unencrypted connection starts with the HTTP/2 connection preface. HttpClient uses it whenever a server negotiates h2 for an HTTPS connection. Routes, middleware and handlers are the same code either way, and request.version is '2' when HTTP/2 is in use.

With HTTP/2, a single connection carries every request, headers are compressed with HPACK, and flow control is built in, instead of the six parallel connections a browser has to open with HTTP/1.1.

To turn it off, set server.http2 = false, which also stops h2 from being advertised through ALPN.

http.h2 provides the lower-level pieces, including the frame codec, HPACK and its Huffman coding, for code that needs to work with the protocol directly.

Note Streams are multiplexed on the connection, but they're handled in the order they complete. Each connection is served by one isolate, so a request that arrives while another is being handled is read, buffered and answered next, not in parallel. This affects throughput, not correctness, and http.serve() is how you handle more than one request at a time.

WebSockets

accept() completes the RFC 6455 handshake and takes over the connection, so the server doesn't write a response of its own on it. Once the handler returns, the server's connection loop drives the socket. It calls the on_message() listener with each message, and send() queues a message that the loop sends when the client can take it. While the socket is open, the server keeps answering other requests, on listen() and on each worker of http.serve().

Fragmented messages are reassembled, and ping frames are answered automatically. When the other side sends a close frame, it's answered. The on_close() listener is called once, whichever side closed, with the code and reason of the closing handshake, or with ws.CLOSE_ABNORMAL when the connection ended without one. Messages sent after that are dropped. A listener that raises an error is reported to on_error() listeners, and the socket is closed with ws.CLOSE_INTERNAL_ERROR.

Two options to accept() deal with clients that disappear without closing:

  • ping_interval is the number of seconds between pings to an idle client. If the client sends nothing, including pongs, for twice that long, the connection is closed. Without this option, an idle socket stays open until the client closes it.
  • max_queued is how many bytes can wait for a client that isn't reading, 4 MiB by default. Past that, the connection is closed. write_timeout also applies, so a client that reads nothing for that long is disconnected.

every() runs an action on the same thread for as long as the socket is open, which is how a socket sends something on a schedule:

On the client side, use ws.connect():

As the RFC requires, client frames are masked with a key from the platform's secure random number generator. The mask is what stops a malicious page from tricking a proxy into caching a forged response.

Sending to Every Socket

A chat sends each message to every open socket. On a single isolate, a list of sockets would be enough. Under http.serve(), though, each worker holds its own sockets, so the message has to reach every worker. server.publish() and server.subscribe() do that:

publish() sends a value to every listener subscribed to its topic. Under http.serve(), the value is copied to every worker, the one that published it included, and each worker sends it on to the sockets it holds. On listen(), it's delivered on the same isolate. In both cases the listeners run after the code that called publish() returns. Any handler can publish, including one for an ordinary POST request.

Server-Sent Events

A WebSocket gives you a two-way connection. Server-sent events give you a long-lived response body and nothing else, which is all you need for a live feed of updates, and they work through proxies that would refuse a connection upgrade.

sse.open() sets the headers an event stream needs, and returns the EventStream to send events on. The stream stays open after the handler returns, held by the server's loop the way a WebSocket is, and send() queues each event. It works over HTTP/1.1 and HTTP/2, and on an HTTP/2 connection, the other streams carry on while it's open.

Events can be sent from anywhere on the same thread: from a timer started with every(), from another request's handler, or from a listener given to server.subscribe(), which hears what every worker publishes:

The on_close() listener is called once, when the client goes away or the stream is closed, and an event sent after that is dropped. close() ends the stream, and the connection goes back to serving requests.

A browser's EventSource reconnects automatically and sends the last event ID it received. sse.last_event_id(request) reads it, so a stream can continue where it left off instead of starting over.

Running in Production

Using More Than One Core

listen() serves every connection on the isolate that called it. It watches all of the connections and only does the work for each one that can be done without waiting, so a client that goes quiet, sends half a request or stops reading doesn't hold up anyone else. Neither does an open WebSocket or event stream. A handler does run until it finishes, though, so a slow handler delays every other connection. So does a body given to response.stream() while its producer runs, and a WebSocket that its handler reads with receive().

http.serve() runs the same pipeline across a pool of isolates. A single accept loop hands each connection to whichever worker takes it next.

setup is called once inside each worker, with that worker's own HttpServer. It can be defined in the main script or in a module, and it can use anything it imports. A module it uses is loaded again inside the worker, not shared with it. Once setup registers more than a few routes, it's better to put it in its own module, as shown above.

serve() binds the port first, so a port that's already in use fails at once. It starts accepting connections, and calls on_ready, once every worker has run setup. Connections that arrive before then wait in the operating system's listen backlog. If setup raises an error in a worker, serve() stops the others and raises it.

Isolates don't share memory, so anything a worker needs, such as a cache, a connection pool or a counter, exists separately in each worker. That's the trade-off this model makes: no locks and no garbage collection pauses on a shared heap, in exchange for state that has to be kept either per worker or somewhere outside the process. A message that every worker has to hear, such as one for the sockets each of them holds, goes through server.publish(), as Sending to Every Socket shows.

backlog limits how many accepted connections can wait for a free worker. The limit is intentional. With an unlimited queue, a server under load would accept connections faster than it could serve them and then answer all of them late, instead of letting the kernel's own listen backlog apply backpressure.

Limits

Every part of a request whose size the client controls has a limit:

Setting Default Limits
max_line_size 8 KiB The request line, and each header line
max_header_size 64 KiB The header section
max_header_count 100 The number of header fields
max_body_size 10 MiB The request body
header_timeout 10s How long the client can take to send the whole request head
keep_alive_timeout 5s How long an idle connection is kept open
max_keep_alive_requests 0 (unlimited) How many requests a single connection can serve

header_timeout is the easiest one to forget, and the most important. Without it, a client that sends one byte every few seconds can keep a connection open forever without ever exceeding the timeout of any single read. That's how a slowloris attack works.

If a service accepts uploads, raise max_body_size deliberately, rather than finding out about the limit by accident:

A request that declares a body larger than the limit is rejected with 413 before any of the body is read, which is exactly what the header is for.

Running Behind a Proxy

If there really is something in front of the server, such as a CDN or a load balancer you control, tell the server about it, and tell it which addresses to trust:

request.client_ip(true, server.trusted_proxies) then works through the forwarding chain starting from the proxy's end, and returns the rightmost address that isn't a trusted proxy. Taking the leftmost address instead, which is a common shortcut, lets an attacker claim any client address they like. That matters as soon as you use an address for rate limiting, an allowlist or an audit log.

If you don't configure this, forwarding headers are ignored completely and the connection's address is treated as the client's. That's the right default, because those headers are ordinary request headers, which anyone can fill with anything.

Requests the Module Rejects

Part of this module's job is to reject certain requests. It's worth listing them explicitly, because other implementations would accept each of these:

  • A header field name with whitespace before the colon. Some parsers read Content-Length : 5 as a length and others as an unknown field, and that disagreement can be used to smuggle a request.
  • Two Content-Length fields with different values, for the same reason.
  • A Content-Length together with a Transfer-Encoding.
  • A Transfer-Encoding whose last coding isn't chunked.
  • An obsolete folded header line. RFC 9112 deprecated them, and intermediaries unfold them in different ways.
  • An HTTP/1.1 request with no Host header, or with two.
  • A header value containing CR, LF or NUL, which is rejected at the point it's set. A value that can insert a newline can cause response splitting wherever it ends up.
  • An uppercase header field name in HTTP/2, and any of the connection-specific fields there.
  • A static file path that resolves to somewhere outside the root, before or after percent-decoding, and any dotfile.

Two other standard library modules work with this one without it depending on either of them. HttpRequest.validate() accepts a schema from validate, and middleware.jwt_auth() accepts a verifier from jwt. Both rely on duck typing, so a server that doesn't use them never loads either module.

Every error this module raises descends from HttpError: ProtocolError for a malformed message, ConnectionError for a connection that failed, TimeoutError, TooLargeError, TooManyRedirectsError, StatusError, UnsupportedProtocolError and SessionError.
