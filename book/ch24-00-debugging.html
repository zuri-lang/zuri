Debugging

Something isn't doing what you expected. This chapter is about tracking down why: reading what the runtime tells you, recognizing the few messages that cause most of the confusion, and the techniques that turn a vague "it's broken" into a line number.

Reading an Error Message

An uncaught error prints three things: what went wrong, where it went wrong, and how the program got there.

The error type and message come first, then the source code around the failure, with the line that failed marked, and finally the call stack, starting with the innermost call.

A deep stack is shortened in the middle, because the top and the bottom are the useful parts. The top shows where the error happened, the bottom shows where your program started, and two hundred identical recursive calls in between don't tell you anything.

The process exits with status 1.

Common Error Messages

Every message below is real output. If you run this, you'll see all of them:

Here's what each one usually means in practice:

Message What to look for
undefined global 'x' A typo, or a def that's declared below the top-level line that calls it
undefined key 'x' in dict A key that really isn't there. If it's allowed to be missing, use get(key, fallback).
undefined field 'x' on instance of 'C' A typo in a field name. Classes are sealed, so this can't create a new field.
undefined property 'x' on instance of 'C' Reading a field or method that the class never declared
undefined member 'x' on module m The module doesn't export it, or the import needs an @ to re-export it
object of type nil does not define method 'f' Something earlier in the code returned nil
operator '+' not defined for call signature (nil, number) The same problem, one step earlier
'x' is private and can only be accessed via 'self' or 'parent' A name with a leading underscore, used from outside the class
'x' is already declared in this scope Two var declarations with the same name in the same block
cannot assign to constant 'x' Assigning to a local const
module 'x' could not be found Usually a missing leading . on an import of a sibling module

The two messages about nil are worth remembering. Zuri can't tell you where a nil came from, because by the time it causes a problem, the value has already been passed along. When you see one, don't look at the line that failed. Look at whatever produced the value.

Common Pitfalls

These behaviors produce a wrong result rather than an error, which makes them much harder to track down.

Zero is falsy. var n = count or 10 turns a real 0 into 10, and if index is false for the first position but true for -1, which means "not found". Compare values explicitly.

to_number() returns 0 for text it can't parse. 'eighty', '' and '12abc' all become 0, and so does ' 7 ' with its spaces. There's no NaN and no error to catch, so invalid input silently becomes a valid zero. Validate the text before you convert it.

[] and {} are truthy. if items is true for an empty list. Use is_empty() instead.

sort() changes the list, but reverse() doesn't. var s = items.sort() sorts items as well. If you need both orders, clone the list first.

The result of a string method was thrown away. name.trim() on its own does nothing. Strings are immutable, so you have to assign the result.

A nested def is local. A function declared inside another function is scoped to it, like a var, and nothing outside that scope can call it.

x++ evaluates to the new value, unlike in C and JavaScript.

Writing Code That's Easier to Debug

Three habits pay off the first time something breaks.

Keep decisions separate from side effects. A function that reads a file, parses it and makes a decision based on it is really three functions. Split them up, and you can test the parsing and the decision without needing a file system.

Pass dependencies in. A function that calls time() behaves differently every second, while a function that takes a timestamp as an argument behaves exactly the same every time you call it with the same number. That means you can reproduce a failure instead of waiting for it to happen again.

Return values instead of printing them. An echo inside a function is invisible to the code that called it, and useless to anything that wants to check the result. Return the string, and let the caller decide what to do with it.
