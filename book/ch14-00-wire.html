Chapter 14 · The Big Modules

Wire

Wire is Zuri's built-in template engine. Unlike most template languages, Wire doesn't add its own syntax on top of your markup. Every Wire feature works through attributes on ordinary HTML elements, so anything a designer already knows about HTML still applies, and every valid HTML5 document is already a valid Wire template.

A Wire template is compiled once into a small tree of instructions, instead of being interpreted again on every render. It's parsed with the same WHATWG-conformant parser that the html module uses. One consequence is worth knowing from the start: Wire understands your markup as structure, not as text. It knows that one interpolation is inside a paragraph, another is inside an href and a third is inside a <script> tag, and it escapes each one correctly for where it is. A value passed to a template can never become new markup by accident. If you want that, you have to ask for it explicitly.

Introduction

Wire and Blade

If you've used Laravel's Blade, PHP's best-known template engine, a lot of Wire will feel familiar, even though the syntax is different. Both engines compile templates instead of interpreting them on every request, both let you extend a base layout and override named sections of it, and both escape everything by default, so displaying a user's name can never let that user run a script in someone else's browser.

Where Wire differs from Blade is in how it handles control flow. Blade adds its own directive syntax on top of plain text (@if, @foreach, {{ }}), which a template author has to learn as a second language on top of HTML. Wire expresses everything as attributes on the HTML you'd be writing anyway:

In practice, this means you can give a Wire template to a designer who has never seen Zuri, and they can still read it. It's just HTML with some attributes they can look up. It also means every Wire template is valid HTML5, can be opened directly in a browser to check its structure, and can be processed with the html module's tools (html.format(), a linter, a selector query) without any special handling for Wire.

Rendering Templates

Templates From Files

For anything more than a quick snippet, you'll want to keep templates in files. Create a Wire instance, point it at a directory, and render templates by their path:

The first argument to render() is a path relative to the root. If the path doesn't name an existing file, .html is added automatically, so 'pages/home' finds pages/home.html. A path that already has an extension, such as 'pages/home.wire', is tried exactly as given first. set_extension() changes the extension that's tried when none is given.

Note A Wire instance is meant to be created once, configured, and reused for the lifetime of your program, usually at startup, in the same place you configure the rest of your application. Rendering doesn't change the instance, so it's safe to render from several places at once.

Templates From Strings

render_string() renders a template passed directly as a string, without touching the file system. Apart from that, it behaves exactly like render(), with the same directives, escaping and filters, and any x-include or x-extend in the string is still resolved relative to the configured root.

The third argument names the source in error messages, and defaults to <source>. It's worth passing when the string came from somewhere with its own identity, such as a database row or a file you'd already opened for another reason:

render_string() isn't cached, since there's no file path to use as a cache key. Use render() for anything you render more than once.

The Template Root

Every path, whether it's passed to render() or written in an x-include or x-extend in a template, is resolved inside the configured root directory and nowhere else. This isn't just a convention. The loader enforces it every time it resolves a path, and it matters for security, not only for keeping things organized.

The root directory doesn't have to exist yet. create_root() creates it and tells you whether it needed to:

Wire never creates this directory by itself. If you make a typo in the root path, you should get a "template not found" error, not an empty folder created somewhere unexpected.

Because it compiles a parsed document instead of joining strings together, it always knows exactly what kind of place an interpolation is in, and applies the escaping that place needs:

Where the interpolation is What happens
Text between tags &, < and > are replaced with entities
An ordinary attribute (title, alt, data-* and so on) & and " are replaced with entities
href, src, action and other URL attributes The URL scheme is checked as well
<script>, or an on* event handler attribute The value is encoded as JSON
<style> Any character outside a set that's safe in CSS is removed

That's a much stronger guarantee than simply replacing special characters. A value placed in an href can't sneak in a javascript: URL, and a value placed in a <script> block can't break out of its string literal, close the tag early or start a comment, even though none of those attacks need <, > or &.

If you use either one on anything a user submitted, such as a comment, a profile or a search query, you reopen the cross-site scripting hole that the rest of Wire is designed to close. Only use them on markup that your own code produced.

If you want to display markup as text, for example to show a literal <script> tag in a code sample, a plain interpolation already does that. You don't need to do anything extra.

Wire and JavaScript Frameworks

Wire uses {{ }} for interpolation, which is the same delimiter that many JavaScript template libraries use, including Vue, Angular, Handlebars and Mustache. If a Wire template contains inline script that a browser-side framework is supposed to process, put a % in front of the braces so that Wire leaves them alone:

%{{ produces the literal text {{, and %{! does the same for template function calls. If you find you're escaping braces all the time because most of a template belongs to a client-side framework, consider moving that part into its own file and serving it as is, without Wire.

The Expression Language

Everything between {{ and }}, as well as everything you pass to x-if, x-for, x-attr and the other directives below, is written in Wire's own small expression language. It's intentionally not a full copy of Zuri: there's no assignment, no way to declare anything and no way to access global variables. A template describes a page, and the logic that decides what goes on the page belongs in the code that calls render(), not in the template.

Operators

When either side of + is a string, it concatenates instead of raising an error:

?? and or look similar but do different things, and mixing them up is the most common mistake people make with Wire:

  • ?? checks whether the value was passed in at all, and only uses the fallback for nil.
  • or checks whether the value is worth displaying, using Wire's own rules for truthiness, and uses the fallback for anything falsy: nil, false, an empty string, an empty collection or the number 0.

Use ?? when zero is a valid value that you want to display, and or when you only want to show something if there's actually something to show.

Truthiness

x-if, x-not, and/or, !/not and ? : all follow Wire's own rules for what's truthy and falsy. These rules differ from Zuri's in one place, on purpose, to make templates easier to write:

Value In Wire
nil, false Falsy
0, NaN Falsy
Any other number, including negative numbers Truthy
An empty string Falsy
A non-empty string Truthy
An empty list or dictionary Falsy
A non-empty list or dictionary Truthy
Anything else Truthy

The difference is empty collections. Zuri treats [] and {} as truthy, but Wire treats them as falsy, so x-if="results" hides a section when a search returns nothing.

Security

Why Everything Is Escaped by Default

Part of a template engine's job is to stop values that came from outside your program, such as a form submission, a query string or another user's profile, from turning into markup, a script or a link, unless you explicitly say they're safe. Wire does this by default rather than as an option you have to enable. As soon as escaping is something you have to remember to turn on, the templates where someone forgot are the ones that get exploited.

Every interpolation is escaped for the place where it appears (see the table earlier in this chapter), and there's no template setting that turns this off. The only way around it is the explicit and easy-to-spot raw filter or x-html directive. That's the right amount of friction between displaying a value and trusting it as unescaped markup.

URLs Are Checked, Not Just Escaped

Attributes that a browser treats as URLs, such as href, src, action and several others, get more than entity escaping. Their scheme is checked against an allowlist, and a scheme that isn't allowed is replaced with about:blank instead of being written out:

If profile_link were javascript:alert(document.cookie), the rendered href would be about:blank, not the script URL. A URL without a scheme, which includes every relative link, absolute path and protocol-relative URL, is always allowed, because none of them can refer to a handler.

The default allowlist includes http, https, mailto, tel and a few others, and it deliberately leaves out javascript, vbscript, data and file. If your application needs another scheme, such as a custom app: handler, use set_url_schemes() to replace the list.

srcset and ping each contain a list of URLs, and every URL in the list is checked in the same way. Descriptors such as 2x and 640w, and the separators between entries, are kept exactly as written.

Scripts and Stylesheets

A value interpolated inside a <script> element, or inside an event handler attribute such as onclick, is encoded as JSON instead of just being escaped. This happens automatically, with no filter needed:

This renders the whole user value as a JSON literal, quotes included. Keep this in mind, because it changes how you write the script around it: don't put your own quotes around the interpolation.

In a <style> block, any character outside a conservative set that's safe in CSS is removed rather than escaped. No escape sequence would stop the HTML tokenizer from reading a < while it looks for </style>, so the only safe option is to remove the character.

The Template Root Is a Sandbox

Every path, whether it was passed to render() or written in an x-include or x-extend inside a template, even one built from an interpolated value, is resolved inside the configured root. If it resolves anywhere else, including through .. segments or symbolic links, it's rejected:

If theme ever came from something a request controls, a loader without this check would let an attacker read any file the process can access. Wire's loader treats the root as a strict boundary instead, so the worst a malicious value can do here is fail to find a template.

Extending Wire

Custom Filters

register_filter() adds a new filter, or replaces an existing one with the same name. The value being filtered is always the first argument, followed by any arguments the template passes:

An argument that the template leaves out is nil, which is why words == nil ? 25 : words above provides a default instead of requiring the template to pass a value every time.

When a filter returns a plain value, that value is escaped like any other interpolation. A filter that produces markup should return wire.safe(), and from then on it's responsible for what's inside, just as raw and x-html are.

Globals

A variable with the same name passed to render() takes priority over a global. A global is a default, not a fixed value, so a page can still override site_name if it needs to.

Custom Elements

For the rare cases that the directives can't handle, register_element() takes over an HTML tag name and passes every element with that name to a Zuri function instead of writing it out:

The function receives the Wire instance and a dictionary that describes the element: its tag name, its attributes (already rendered and escaped), its rendered children and the scope it was written in. Return wire.safe(markup) to write markup, any other value to write it as escaped text, or nil to write nothing. Directives still work on a custom element as you'd expect, so <icon x-if="..." /> behaves the way it looks. This feature is meant for markup that really does have to be generated by code, where a partial and x-include aren't enough. Try an include first. It's easier for the next person to read, and they won't have to go looking for the Zuri function behind it.

Configuration

You can pass every setting to the Wire constructor at once, or set each one later with its own method:

Option / method Default What it controls
root / set_root(path) ./templates The directory that every template path is resolved inside.
extension / set_extension(ext) .html The extension tried when a path doesn't name an existing file. Must start with ..
compact / set_compact(bool) false Removes text between tags that's only whitespace.
comments / set_comments(bool) false Whether HTML comments appear in the rendered output.
auto_reload / set_auto_reload(bool) true Whether a cached template is checked against its file before each render, and read again if the file has changed.
url_schemes / set_url_schemes(list) See above Which URL schemes href, src and similar attributes can use.

root() returns the configured root as an absolute path, and create_root() creates the directory if it doesn't exist yet, returning whether it had to.

Compiling and Caching

The first time a template is used, render() compiles it into a tree of instructions and keeps the result for later. Parsing and resolving directives happen once per template, not once per request, and every later render just walks the tree.

When auto_reload is on, which is the default, each render compares the file's modification time and size with the cached values and recompiles the template if either has changed. That costs one file system stat per template per render, which is cheap and exactly what you want while you're editing templates. Once you're running under load and no longer editing templates, turn it off with set_auto_reload(false). A long-running process can then call clear_cache() to pick up a new deployment.

Under zuri run --watch, a template change does more than reload the template. Changing any template the program has rendered restarts the program, just as changing its code does, because Wire tells watch mode about every template file it reads.

compile(path) compiles a template without rendering it and returns the compiled result, or raises an error if the template has a mistake in it. That makes it useful for checking a whole directory of templates at startup, so that a broken template is caught before the first request that would use it:

Error Handling

Every error that Wire raises is a wire.WireError, and each one includes the template path and the line and column of the tag that caused it. That means catching the base class is enough to handle any template failure in one place, whether you turn it into a 500 page, log it with context or do something else your application needs:

Three more specific error classes, all subclasses of WireError, tell you what kind of problem occurred:

Error Raised when
wire.TemplateSyntaxError A template doesn't compile, for example because of an unknown directive, an invalid expression or a broken inheritance chain. It's always raised the first time the template is used, not on a later render.
wire.TemplateNotFoundError A path doesn't name a file, or resolves to somewhere outside the template root.
wire.RenderError Something went wrong because of the values a template received, for example iterating over something that can't be iterated, a filter rejecting its input, or a chain of includes that never ends.

A variable that was never passed in is not an error. It renders as nothing and counts as falsy, by design, so you can write an optional section without guarding every field it uses.

Full Directive Reference

These are all the directives Wire understands. Any other attribute starting with x- fails to compile, because Wire reserves the whole prefix. That way, a typo such as x-fi is caught as soon as the template compiles, rather than silently doing nothing.

Directive Takes Meaning
x-if Expression Renders the element only if the expression is truthy. Starts a chain.
x-elif Expression Continues an x-if chain.
x-else (nothing) Ends an x-if chain.
x-not Expression Renders the element only if the expression is falsy. Can't be part of a chain.
x-for Expression Repeats the element once for each item.
x-value Name Names the value on each pass.
x-key Name Names the key or index on each pass.
x-loop Name Renames the loop metadata variable.
x-text Expression Replaces the children with escaped text.
x-html Expression Replaces the children with unescaped markup.
x-attr Expression (dictionary) Adds attributes to the element.
x-include Path Renders another template in place of this element.
x-with Expression (dictionary) Adds variables for an include.
x-only (nothing) Hides the surrounding scope from an include.
x-extend Path Makes this template extend the named base template.
x-slot Name Declares a region that an extending template can replace.
x-define Name Replaces a region of the base template.
x-override (nothing) Allows a region that's already been defined to be defined again.
x-super (nothing) Renders the definition that this one replaces.

Five elements are shorthand for the directives above, and they're rewritten before the template is parsed:

Element Equivalent to
<include path="p" /> <template x-include="p"></template>
<extend base="p">…</extend> <template x-extend="p">…</template>
<declare name="n">…</declare> <template x-slot="n">…</template>
<define name="n">…</define> <template x-define="n">…</template>
<super /> <template x-super></template>
