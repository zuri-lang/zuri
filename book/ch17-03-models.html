17.3 · The Big Modules

Models

sql works with rows, and a row is a dictionary. That's the right shape for a report or a script, but not for the core of an application, where a post is something with rules: it must have a title, it belongs to an author, and its slug is derived from its title. sql.model gives each table a class. Instances of the class, called records, can save, validate and delete themselves, and can load the records they're associated with.

A First Model

A model is a class that extends Model. Its fields are the columns of its table:

db.model(Post) starts a query over the model's rows. Methods that use the database, such as save(db) and delete(db), take the connection to use as an argument. A record never holds onto a connection itself, so it's saved inside whichever transaction the calling code opened, and a record that's kept after its connection has gone back to a pool can't write through a connection that now belongs to someone else.

Declaring a Model

Every field the class declares, apart from those that start with _, is a column with the same name. Everything else about the model goes in a static define() method, which receives a definition object to describe the model on:

A model's table name is its class name in snake case, made plural using the regular rules of English, so Post becomes posts, BlogPost becomes blog_posts, Category becomes categories and Address becomes addresses. If a word has an irregular plural, set the table name with table().

define() runs once, the first time the model is used, not when the class is declared, so it can refer to models declared later in the same file. Its description is checked against the class at that point. An association without a field to load into, or a cast on a field that isn't a column, raises a ModelError the first time the model is used. A model's primary key is a single column.

Records loaded from the database are created without any arguments, so a model's own @new mustn't require any. If it accepts attributes, it should pass them on with parent(attributes).

Records

Calling the class creates a record, using a dictionary of attributes if you pass one. create() on a query creates a record and saves it:

Saving a new record inserts it. Any column that's still nil is left out of the insert, so the database fills in its default, and those columns are then read back, so the record holds what was actually stored. Saving a record that's already stored only writes the columns that have changed since it was loaded, and writes nothing if none have. That way, a column that another process changed in the meantime isn't overwritten when you save a different column.

A list or dictionary that's changed in place counts as a change. A deleted record keeps its values, and saving it again inserts it as a new row. key() returns the value of the primary key, whatever the column is called.

Assigning Input

fill() assigns attributes from a dictionary, such as one provided by a form or a request body. It only assigns fillable columns, which are the columns the model lists with fillable(), or if it doesn't list any, every column except the primary key and the timestamps. A key that isn't fillable raises a ModelError, so a request can't set a record's primary key, or any other column it was never meant to change, just by sending an extra field.

Validation

A model validates itself before every save, using validate rules, uniqueness checks and its own validate() method. A record that fails validation isn't saved, and save() raises a RecordInvalid error:

RecordInvalid is a validate.ValidationError, and its errors are the same { field, message } list that form validation reports, so the code that responds to an invalid form with a 422 can respond to an invalid record in the same way. is_valid(db) runs the checks without saving, and errors() returns what the last check found.

A uniqueness check reports a value that's already taken along with the other failures. However, only a unique index in the database can stop two records that are saved at the same moment from getting the same value, so a unique column should have a unique index in the database as well.

Hooks

A model can override any of these methods to run code at that point in a record's life cycle. Each one receives the connection or transaction the record is using:

Hook Runs
before_validate(db) Before the record is validated
validate(errors) While it's validated, to add failures of the model's own
after_validate(db) After it's validated, whatever the result
before_save(db) Before it's written, whether it's new or not
before_create(db) Before a new record is inserted
after_create(db) After it's inserted, once it has its key
before_update(db) Before a stored record's changes are written
after_update(db) After the changes are written
after_save(db) After it's written, whether it's new or not
before_delete(db) Before it's deleted
after_delete(db) After it's deleted
after_load() When a record is created from a row

If a model defines any hooks, saving and deleting run inside a transaction, or a savepoint if a transaction is already open, so anything a hook writes is undone along with everything else if something fails. A hook can raise an error to stop the save or the delete:

A model's methods share a namespace with the hooks and with every method a record has, so a model shouldn't declare a method with one of those names for any other purpose. A field can have the same name as any of them.

Queries

db.model(Post) returns a Query. Every method that narrows a query returns a new query and leaves the original unchanged, so you can keep a query and build on it in several different directions:

where() with a dictionary works the same way as the conditions for the CRUD helpers: a value matches itself, nil matches null, a list matches any of its values, and an empty list matches nothing. Anything other than a dictionary is a fragment of SQL, with a ? for each value. The fragment is wrapped in parentheses when it's added, so an or inside it stays inside it. All conditions must be true. where_not() excludes matching rows, and a row whose column is null counts as excluded by any value, since null isn't equal to anything.

A query is iterable, so for post in query reads every record. update() and delete() change every matching row in a single statement without creating records, so no validation or hooks run. update() sets the updated timestamp unless you provide a value for it.

A scope is a reusable part of a query. You declare it with scope() and apply it with query.scope(name, argument).

Associations

There are four kinds of association, which cover the ways tables can refer to each other:

Declared as Means The key is
belongs_to('author', Author) This record holds another record's key author_id in this table
has_one('profile', Profile) Another record holds this one's key, and there's at most one author_id in the other table
has_many('posts', Post) Other records hold this one's key author_id in the other table
belongs_to_many('tags', Tag) A join table holds both keys post_id and tag_id in post_tag

Each name is also the field the association is loaded into, which the class has to declare. Keys are named after the class name in snake case, followed by _id, and the join table is named after both class names in alphabetical order. You can use options to choose different names:

Associations are only loaded when you ask for them. include() loads them along with the records, using one query per association however many records there are, and a dotted name loads an association of an association:

A field that holds an association is nil until the association is loaded. load() loads an association onto a record you already have and returns the record, and query.load(records, names) loads associations onto a list of records, using one query per association. related() returns a query over the records an association refers to, so you can narrow it further instead of loading all of them.

When you assign a record to a belongs_to field, the key that refers to it is set when the record holding it is saved, and the assigned record has to be saved first. attach(), detach() and sync() link records through a belongs_to_many association's join table, and accept either records or keys.

Casts

Most values are read back as the type they were stored as. A cast makes sure a field has the same type on every engine, even where the engines differ, by converting it as it's read:

Cast The field holds
bool true or false, converted from a bool, a number, '0', '1', 'true' or 'false'
integer A whole number
number A number
decimal A sql.Decimal
string Text
json A list or dictionary, decoded from JSON text if necessary
date A date.Date, converted from ISO 8601 text if necessary

MySQL doesn't have a boolean type and returns 1, and MariaDB stores JSON as text, so a model that runs on either of them should cast those columns, for example with cast('published', 'bool') and cast('settings', 'json'). Null stays nil under every cast, and a value that can't be converted is left as it was read instead of being lost.

Records as Output

to_dict() returns a record's columns, except for the ones listed with hidden(), along with every association that has been loaded, converted to dictionaries as well. json.encode() writes a record as its to_dict(), so a record passed to a response doesn't include something like a password hash:

Two records are equal if they belong to the same model and have the same primary key. A record that hasn't been saved yet is only equal to itself.

Design Limits

Associations are loaded explicitly. An association is only loaded by include() or load(), never just by reading its field, so a loop over records never silently runs a query for each record.

Each query creates its own records. If two queries read the same row, you get two separate records for it, which are equal (==) to each other. Nothing is cached between queries, so a record always reflects what the database held when it was read.

Joins are written in SQL. Conditions cover a model's own columns, and related() and include() cover associations. For a join, a union or a window function, write the SQL yourself and pass it to from_sql(), which creates records from whatever the query selects.

Tables are created by migrations. A model maps an existing table. Migrations and Changing the Schema are how you create and change tables.
