Hello, World!

Make a directory, put one file in it, and run it.

Create a file called main.zu. The .zu extension is what the runtime looks for when resolving imports, so get in the habit early.

Run it:

That is the whole program. No main function, no imports, no boilerplate. A Zuri file is a script, and its top level is code that runs.

Anatomy of One Line

echo is a keyword, not a function. You do not write echo(...), you write echo followed by an expression. It prints the value and adds a newline.

Strings are written between single or double quotes, and the two are identical in meaning. Most Zuri code uses single quotes and saves double quotes for strings that contain an apostrophe.

There is no semicolon. Zuri ends a statement at the end of the line. You can write a semicolon if you want two statements on one line, but almost nobody does.

echo and print

There is also a print() function, and the difference is worth learning now because it bites people later.

echo appends a newline; print() does not, and it takes any number of arguments. Use echo for output meant for a human reading a terminal, and print() when you are assembling output character by character.

Running It Again on Every Change

While you work on a program, --watch, or -w for short, keeps it running and starts it again from the top each time a file it uses changes:

The files it uses are the entry file and every module imported from it, the Wire templates it renders, and the project's project.toml and .env files. Zuri learns the first two from the program as it runs, so a module imported only halfway through is watched from the moment it loads. Files the program writes itself, such as logs, databases and uploads, never restart it.

The lines watch mode adds go to standard error, so the program's own output can still be piped on its own. A program that exits waits there for the next change, and one that fails to start because of a mistake is started again as soon as the mistake is fixed. Ctrl+C stops both the program and watch mode.

The flag goes straight after run. After the path it belongs to the program like every other argument, so zuri run . -w hands -w to the program.

Formatting

zuri fmt lays out Zuri source in one house style: two spaces to a level, one statement to a line, an explicit block wherever one belongs, spacing the way a reader expects it, and lines past eighty columns broken where the expression holds together least. Where a line breaks follows the rules of the Dart formatter: a list of arguments or items stays on one line when it fits and otherwise takes one item to a line, a list or dictionary holding another one always opens out, as rooms does below, and a single function or collection among a call's arguments opens out on its own, as in each(items, @{. The layout comes from the code alone, so where you broke a line inside an expression makes no difference, though the blank lines you left between statements stay.

Commands

A first word that is not run names a command instead of a path:

A command is a .zu file, or a directory with an index.zu, sitting in a cmds directory. A project keeps its own in .zuri/cmds, so either of these answers to zuri greet:

The directory wins if both are there, so a command that has outgrown one file takes over the name as soon as its index.zu lands. Until then the directory is not a command, and the file goes on answering.

The commands the runtime itself ships live in the cmds directory beside the executable, and those win over a project's. Everything after the name is forwarded to the command untouched, flags included.
